# Design: perceptual hash manifest comparison (`0.4.0a1` first slice)

Status: implemented and released in improcv 0.4.0a1. This document freezes the contract for the
first `0.4.x` slice; it does not design the rest of the `0.4.x` line.

## 1. User problem

> I have two manifests of the same logical dataset from different points in time, and I want to
> deterministically determine which identifiers were added, removed, or changed, without manually
> comparing mappings and without filesystem access.

This is the one problem this slice solves. It follows directly from `improcv`'s own shipped,
stable contract: `PerceptualHashManifest` has been a snapshot type since `0.3.0a2`
(`from_hashes`/`to_hashes`/`to_json`/`from_json`/`save`/`load`), and every example that uses it
(`examples/image_similarity_manifest.py`, `examples/dataset_manifest_builder.py`) already
demonstrates building, saving, moving a dataset, and reloading a manifest — but nothing in the
public API today can answer "what changed between two manifests" without the caller hand-writing
set arithmetic over two `to_hashes()` mappings.

## 2. Scope

In scope: one pure, in-memory, deterministic function comparing two already-constructed
`PerceptualHashManifest` instances by path identity, plus the minimal result type(s) it needs.

Out of scope (see section 16 for the complete list): anything touching the filesystem, image
decoding, manifest schema v1, any existing public symbol's signature, rename detection, content
identity, perceptual similarity, freshness/caching, incremental rebuilding, grouping, indexed
search, parallelism, progress/cancellation, or any other slice of a future `0.4.x` roadmap.

## 3. Identity semantics

```text
identity = canonical manifest path (PurePosixPath, as already stored on
           PerceptualHashManifestEntry.path)
```

Classification, for every path in `before.entries` union `after.entries`:

```text
added:     path exists only in after
removed:   path exists only in before
changed:   path exists in both, but the hash differs
unchanged: path exists in both, and the hash is identical
```

The algorithm never looks for matching content under a different path. A rename is always
reported as one `removed` entry (old path) plus one `added` entry (new path) — never specially
detected or merged, even when the hash is identical on both sides. An identical hash appearing
under two different paths (in `removed` and `added` respectively) does not establish that a
rename occurred: it may represent renamed content, duplicated content, perceptually similar
content, or a hash collision (perceptual hash collisions are expected and documented in
`improcv.hashing`). This function deliberately does not infer which case occurred — path identity
remains the only identity rule, so the result is always `removed` + `added`. Perceptual similarity
plays no role in this classification at all: `improcv.similarity.find_similar_image_pairs` remains
the only public API for similarity-based comparison, and it operates on a single hash collection,
not on two manifests being compared against each other. `compare_perceptual_hash_manifests` never
calls it and never reproduces any of its logic.

### Example 1 — pure add/remove

| path | before | after | classification |
|---|---|---|---|
| `cats/a.png` | `55aa55aa55aa55aa` | *(absent)* | `removed` |
| `cats/b.png` | *(absent)* | `0f0f0f0f0f0f0f0f` | `added` |

### Example 2 — same path, changed hash

| path | before | after | classification |
|---|---|---|---|
| `cats/a.png` | `55aa55aa55aa55aa` | `95aa55aa55aa55aa` | `changed` |

### Example 3 — rename reported as remove + add

| path | before | after | classification |
|---|---|---|---|
| `cats/a.png` | `55aa55aa55aa55aa` | *(absent)* | `removed` |
| `cats/renamed_a.png` | *(absent)* | `55aa55aa55aa55aa` | `added` |

Note that the hash value `55aa55aa55aa55aa` is identical between the `removed` and `added` rows in
Example 3. This is not treated as a rename anywhere in the classification: the result reports one
`removed` entry and one `added` entry, full stop. There is no cross-referencing of hash values
across categories anywhere in this design.

## 4. Compatibility validation

Required direction (from the task): `before.algorithm == after.algorithm` and
`before.hash_size == after.hash_size`, otherwise `ValueError`.

**Validation order** (resolved): type checks first, then the hash-space check —

1. `before` must be an instance of `PerceptualHashManifest`; subclasses are accepted (checked via
   `isinstance`, not `type(...) is`, matching how `manifest.py`'s own `__post_init__` checks
   `isinstance(entry, PerceptualHashManifestEntry)`/`isinstance(self.algorithm, PerceptualHashAlgorithm)`
   — `type(...) is ...` is reserved in this codebase specifically for `PurePosixPath` on
   `PerceptualHashManifestEntry.path`, not for user-defined dataclasses). Otherwise `TypeError`
   naming the parameter: `f"before must be a PerceptualHashManifest, got {type(before).__name__}"`.
2. `after` must be an instance of `PerceptualHashManifest`; subclasses are accepted. Same check,
   same message shape naming `after`.
3. Only once both types are confirmed: `before.algorithm != after.algorithm or before.hash_size
   != after.hash_size` is checked as **one combined condition**, mirroring
   `PerceptualHash.distance`'s existing `if self.algorithm != other.algorithm or self.hash_size !=
   other.hash_size` pattern exactly (not two separate exception paths for the two mismatch axes).

**Message content** (resolved): mirrors `PerceptualHash.distance`'s existing wording precisely,
so it names both algorithms and both hash sizes and keeps the same `match="algorithm and
hash_size"` substring the existing test suite already relies on (see
`tests/test_similarity.py::test_mixed_algorithms_raise_value_error` and
`test_mixed_hash_sizes_raise_value_error`, both matching on `"algorithm and hash_size"`):

```text
f"cannot compare {before.algorithm.value}(hash_size={before.hash_size}) with "
f"{after.algorithm.value}(hash_size={after.hash_size}) -- comparison requires "
"the same algorithm and hash_size"
```

**No automatic conversion, no coercion, no partial result**: a hash-space mismatch always raises
before any classification work happens — there is no partial `PerceptualHashManifestDiff` for a
mismatched pair, and no attempt to compare only the subset of entries that happen to share a hash
space (a manifest has exactly one hash space for all of its entries by construction, so this
never arises at the entry level, only at the whole-manifest level compared here).

## 5. Decision: `unchanged` in the result

**Chosen: full partition (`unchanged` is part of the public result).** Rejected: differences-only
result with an optional `unchanged_count: int`.

Reasoning:

- A full partition gives the simplest possible invariant set: every path in `before.entries` union
  `after.entries` lands in exactly one of four buckets. A differences-only result would leave that
  as an *implicit* fifth, unreported bucket, which the caller would have to reconstruct by hand
  from `before`/`after` themselves if they ever needed it — exactly the manual comparison work
  this function exists to remove.
- The classification pass must visit every path in the merge-join regardless of whether
  `unchanged` is kept in the output (see section 8's pseudocode) — computing it costs no extra
  time. Only the output list's length differs between the two designs, not the algorithm's
  complexity.
- The memory concern raised for the full-partition design is real but bounded by construction:
  `unchanged`'s element type holds only the bare `PurePosixPath` identifier (see section 7), never
  a duplicated hash — since `before.hash == after.hash` is exactly the classification condition
  for this bucket, storing the hash again would be pure redundancy already recoverable, byte for
  byte, from either input manifest.
- An `unchanged_count: int`-only design discards information (which paths were unchanged) that is
  otherwise free to keep, and is asymmetric with the other three fields being full collections —
  a caller who legitimately wants the *set* of unchanged paths (e.g. to assert dataset stability
  in a test) would have no way to get it from the result at all, only its count.

`unchanged: tuple[PurePosixPath, ...]` is therefore part of the public result, chosen over the
count-only design.

## 6. Decision: result types

**Chosen (Design 1): two new dataclasses** — `PerceptualHashManifestChange` (one path, two
hashes) and `PerceptualHashManifestDiff` (the four classified collections). **Rejected (Design
2): representing `changed` via existing types**, e.g. `tuple[PerceptualHashManifestEntry,
PerceptualHashManifestEntry]`.

Reasoning:

- A bare `tuple[PerceptualHashManifestEntry, PerceptualHashManifestEntry]` is ambiguous in both
  the type hint and at the call site: nothing distinguishes which element is `before` and which is
  `after` without consulting documentation every time. `PerceptualHashManifestChange(path=...,
  before=..., after=...)` is self-describing in the type hint, in `repr()`, and at every access
  site (`change.before`, `change.after`).
- `PerceptualHashManifestEntry` already carries its own `path` field. Reusing it for both halves
  of a `changed` record would store the (identical, by definition) path twice per record, with
  nothing in the type system enforcing that the two entries in the pair actually share a path —
  an avoidable, unchecked invariant. `PerceptualHashManifestChange` stores `path` exactly once and
  `before`/`after` as bare `PerceptualHash` values (the only two things that can differ for a
  `changed` record by definition), eliminating that redundancy entirely.
- The cost of one extra public type (two instead of one) is justified precisely because no
  existing type in `improcv.manifest` can represent "one path, two hashes" without either
  duplicating the path or losing the before/after distinction.

Final result types (see section 8 for the complete contract).

## 7. Decision: `added`/`removed` — entry or path

**Chosen: `tuple[PerceptualHashManifestEntry, ...]` for both `added` and `removed`.** Rejected:
`tuple[PurePosixPath, ...]`.

Reasoning:

- An `added`/`removed` path exists in only *one* of the two input manifests. A bare-path result
  would force any caller who also wants the hash (e.g. to log "removed `cats/a.png` (was
  `55aa...`)", or to check whether a removed hash reappears somewhere else entirely) to look it up
  themselves via `before.to_hashes()[path]` / `after.to_hashes()[path]` — the exact kind of manual
  mapping work this function exists to remove. Returning the entry directly costs nothing extra to
  construct (the entry object already exists, immutably, inside the source manifest's own
  `entries` tuple), and it lets a `PerceptualHashManifestDiff` continue to answer "what hash did
  this removed path have" even if the caller no longer holds a reference to `before`/`after`
  themselves (e.g. after passing the diff to a logging function).
- This is *not* the same reasoning that applies to `unchanged` (see section 5): an unchanged
  path's hash is, by definition, identical in both manifests — no information is lost by keeping
  only the path there, since the (single, shared) hash value remains trivially and unambiguously
  recoverable from either input if the caller still holds it. An `added`/`removed` hash exists in
  exactly one place; dropping it there is a genuine, non-recoverable loss of information once the
  diff outlives its two source manifests.
- Consistency: `added`/`removed` sharing one element type (`PerceptualHashManifestEntry`) with the
  manifests' own `entries` field means no new concept is introduced for these two fields at all —
  only `changed` needs a new type, and only because it must carry two hashes rather than one.

## 8. Exact public API

**Module**: `src/improcv/manifest.py`. No new module. `compare_perceptual_hash_manifests` and its
result types are a comparison operating purely on `PerceptualHashManifest`/`PerceptualHashManifestEntry`
values already defined in this module — the same module that already contains every other
operation on those types (`from_hashes`, `to_hashes`, `to_json`, `from_json`, `save`, `load`). A
new module would only be justified by a different dependency set or a different filesystem
boundary; neither applies here. `src/improcv/dataset.py` is not appropriate either — that module
is reserved for filesystem-touching, decode-and-hash orchestration (`build_perceptual_hash_manifest`),
and this function is explicitly required to do neither.

**Naming** (resolved — one set chosen, not left open):

- `compare_perceptual_hash_manifests` (function) — chosen over `diff_perceptual_hash_manifests`
  (rejected: pairs the verb "diff" with a result type already named `...Diff`, a redundant
  doubling of the same word) and over a shortened form like `compare_manifests` (rejected: breaks
  this codebase's established full-name convention, where every manifest-related symbol spells out
  `perceptual_hash_manifest` in full — `build_perceptual_hash_manifest`, `PerceptualHashManifest`,
  `PerceptualHashManifestEntry`).
- `PerceptualHashManifestDiff` (result type) — chosen over `PerceptualHashManifestComparison`
  (rejected: needlessly long without adding clarity) and over `PerceptualHashManifestDelta`
  (rejected: introduces a new word, "delta", for a concept this codebase already calls "changed"/
  "diff" elsewhere; no other symbol in `improcv` uses "delta").
- `PerceptualHashManifestChange` (per-change record type) — chosen over `ManifestHashChange`
  (rejected: drops "Perceptual" inconsistently with every sibling type) and over `ChangedEntry`
  (rejected: too generic, and easily confused with `PerceptualHashManifestEntry`, an unrelated
  existing type).

**Complete contract**:

```python
def compare_perceptual_hash_manifests(
    before: PerceptualHashManifest,
    after: PerceptualHashManifest,
) -> PerceptualHashManifestDiff:
    """Classify every path in `before`/`after` as added, removed, changed, or unchanged."""


@dataclass(frozen=True, slots=True)
class PerceptualHashManifestChange:
    path: PurePosixPath
    before: PerceptualHash
    after: PerceptualHash


@dataclass(frozen=True, slots=True)
class PerceptualHashManifestDiff:
    added: tuple[PerceptualHashManifestEntry, ...]
    removed: tuple[PerceptualHashManifestEntry, ...]
    changed: tuple[PerceptualHashManifestChange, ...]
    unchanged: tuple[PurePosixPath, ...]
```

Both dataclasses are `frozen=True, slots=True`, matching every other public result type in
`improcv` (`PerceptualHash`, `PerceptualHashManifestEntry`, `PerceptualHashManifest`,
`SimilarImagePair`) — with default dataclass equality and default dataclass repr. **Neither
result dataclass defines a custom `__post_init__`**: they are plain, statically-typed value
objects with no coercion and no runtime field validation of their own.
`compare_perceptual_hash_manifests` is the function that produces a correctly-formed
`PerceptualHashManifestDiff`/`PerceptualHashManifestChange`; manual construction of either type by
hand keeps ordinary, statically-typed dataclass semantics (whatever values are passed are stored
as given, exactly as any plain `frozen=True, slots=True` dataclass without a custom
`__post_init__` behaves) rather than re-validating that the function's own invariants hold.

**`manifest.py`'s own `__all__`** (currently `["PerceptualHashManifest", "PerceptualHashManifestEntry"]`,
already alphabetical) extends to, in this exact order:

```python
__all__ = [
    "PerceptualHashManifest",
    "PerceptualHashManifestChange",
    "PerceptualHashManifestDiff",
    "PerceptualHashManifestEntry",
    "compare_perceptual_hash_manifests",
]
```

This is plain ASCII/alphabetical order (`sorted(__all__)` in Python) for `manifest.py`'s own,
small, five-symbol `__all__`, preserving that module's existing alphabetical convention.

**`src/improcv/__init__.py` changes**:

Import block (extends the existing single-line `from improcv.manifest import PerceptualHashManifest,
PerceptualHashManifestEntry`, which no longer fits one line at this project's 100-column limit):

```python
from improcv.manifest import (
    PerceptualHashManifest,
    PerceptualHashManifestChange,
    PerceptualHashManifestDiff,
    PerceptualHashManifestEntry,
    compare_perceptual_hash_manifests,
)
```

Top-level `__all__` additions (exact local insertion points): the new symbols are inserted at the
explicitly specified local positions used by the existing top-level export list. This design does
not claim that the entire historical top-level `improcv.__all__` is equal to `sorted(improcv.__all__)`
— it is not (e.g. `"Mask"` precedes `"MSERRegion"` in the existing list, the reverse of what a
plain ASCII sort would produce). Only the following local orderings are required:

- `"PerceptualHashManifestChange"` and `"PerceptualHashManifestDiff"`, inserted between the
  existing `"PerceptualHashManifest"` and `"PerceptualHashManifestEntry"` entries (in that order:
  `Manifest` < `ManifestChange` < `ManifestDiff` < `ManifestEntry`).
- `"compare_perceptual_hash_manifests"`, inserted between the existing
  `"classification_metrics_from_confusion_matrix"` and `"confusion_matrix"` entries (verified:
  `"classification_metrics_from_confusion_matrix" < "compare_perceptual_hash_manifests" <
  "confusion_matrix"` under plain string comparison).

## 9. Ordering and invariants

**Sort key** (resolved): `path.as_posix()` string form, **not** direct `PurePosixPath.__lt__`
comparison. This is not a stylistic choice — `PerceptualHashManifest.__post_init__`'s own existing
sort-order invariant is defined exactly this way (`posix_paths = [entry.path.as_posix() for entry
in self.entries]`, then `posix_paths != sorted(posix_paths)` raises `ValueError`), i.e. against
plain Python string comparison of the POSIX form, not against `pathlib`'s own parts-tuple-based
ordering. Those two orderings are not always identical: for example, comparing `"a-b"` against
`"a/b"` as raw strings orders `"a-b" < "a/b"` (`-` is code point 45, `/` is code point 47), while
`PurePosixPath("a-b") < PurePosixPath("a/b")` compares the parsed-parts tuples `("a-b",)` and
`("a", "b")`, which orders the other way. Comparing `PurePosixPath` objects directly inside
`compare_perceptual_hash_manifests` could therefore silently diverge from the exact order the
input manifests are already guaranteed to hold, breaking the merge-join's own precondition (see
section 10). Every comparison in this design is therefore specified against `.as_posix()` strings.

**Entries are pre-sorted** (resolved, and load-bearing): `before.entries`/`after.entries` are
already guaranteed sorted ascending by `path.as_posix()`, with no duplicate paths, by
`PerceptualHashManifest.__post_init__` at construction time — this holds for *every* validly
constructed `PerceptualHashManifest`, regardless of whether it was built via `from_hashes`,
`from_json`/`load`, or directly. `compare_perceptual_hash_manifests` may rely on this invariant
without re-sorting or re-validating it itself.

**Algorithm shape** (resolved): a single-pass **merge-join** over the two already-sorted `entries`
tuples (see section 10's pseudocode) — not two constructed `dict`s. A dict-based approach (build
`dict(before.to_hashes())`/`dict(after.to_hashes())`, then set-difference the keys) was considered
and rejected: it would still be `O(n + m)` in time, but it uses `O(n + m)` *additional* working
memory for the two dicts (on top of the result), and dict key iteration order is insertion order,
not canonical path order, so the combined key set would still need an explicit sort afterward. The
merge-join needs only two integer indices as working state beyond the four output collections,
satisfying the complexity bound in section 10 exactly, and produces already-sorted output as a
direct consequence of walking two already-sorted inputs in lockstep — no separate sort step at
all.

**Required invariants** (all satisfied by the merge-join in section 10):

```text
added, removed, changed, unchanged are pairwise disjoint by path
every path in union(before.entries, after.entries) appears in exactly one category
changed contains only entries where before.hash != after.hash
unchanged contains only paths where before.hash == after.hash
every added path exists only in after
every removed path exists only in before
```

## 10. Complexity and reference pseudocode

```text
time:                                        O(n + m), where n = len(before.entries),
                                              m = len(after.entries)
traversal/control state:                     O(1) (two integer indices)
output storage:                              O(n + m) (the four result collections)
overall peak memory (including output
construction):                               O(n + m)
```

The merge traversal itself needs only two integer indices as control state, independent of `n`/
`m`. The four output collections are unavoidably `O(n + m)` in size (every input path lands in
exactly one of them), and building each one's final immutable tuple from its intermediate list
transiently holds both the list and the tuple in memory at once — an ordinary, unavoidable cost
of materializing an immutable result, not an extra data structure the algorithm chose to build
(unlike the rejected two-dict approach above, which duplicates the input into new dict objects on
top of that same output cost).

```text
function compare_perceptual_hash_manifests(before, after):
    if not isinstance(before, PerceptualHashManifest):
        raise TypeError(f"before must be a PerceptualHashManifest, got {type(before).__name__}")
    if not isinstance(after, PerceptualHashManifest):
        raise TypeError(f"after must be a PerceptualHashManifest, got {type(after).__name__}")

    if before.algorithm != after.algorithm or before.hash_size != after.hash_size:
        raise ValueError(
            f"cannot compare {before.algorithm.value}(hash_size={before.hash_size}) with "
            f"{after.algorithm.value}(hash_size={after.hash_size}) -- comparison requires "
            "the same algorithm and hash_size"
        )

    b = before.entries      # already sorted ascending by path.as_posix(), no duplicates
    a = after.entries       # already sorted ascending by path.as_posix(), no duplicates
    i, j = 0, 0

    added = []
    removed = []
    changed = []
    unchanged = []

    while i < len(b) and j < len(a):
        path_b = b[i].path.as_posix()
        path_a = a[j].path.as_posix()

        if path_b < path_a:
            removed.append(b[i])
            i += 1
        elif path_a < path_b:
            added.append(a[j])
            j += 1
        else:  # same canonical path on both sides
            if b[i].hash == a[j].hash:
                unchanged.append(b[i].path)
            else:
                changed.append(
                    PerceptualHashManifestChange(path=b[i].path, before=b[i].hash, after=a[j].hash)
                )
            i += 1
            j += 1

    # exactly one of these two drains does anything, since one side is already exhausted
    while i < len(b):
        removed.append(b[i])
        i += 1
    while j < len(a):
        added.append(a[j])
        j += 1

    return PerceptualHashManifestDiff(
        added=tuple(added),
        removed=tuple(removed),
        changed=tuple(changed),
        unchanged=tuple(unchanged),
    )
```

This is a complete, unambiguous algorithm description — a future implementer does not need to
re-derive the merge-join, the tie-breaking direction, or the drain step. This is pseudocode, not
Python meant to be copied verbatim into `src/`; the real implementation will use this codebase's
own conventions (e.g. `require_int`-style helpers where applicable, though no numeric validation
is needed here beyond the two `isinstance` checks and the hash-space equality check already
covered above).

## 11. Exception contract

| condition | exception | message requirements |
|---|---|---|
| `before` is not an instance of `PerceptualHashManifest` (subclasses accepted) | `TypeError` | names the parameter (`before`) and `type(before).__name__`, in the form `"before must be a PerceptualHashManifest, got {type}"` |
| `after` is not an instance of `PerceptualHashManifest` (subclasses accepted) | `TypeError` | same shape, naming `after` |
| `before.algorithm != after.algorithm` | `ValueError` | one combined message naming both algorithms and both hash sizes, containing the substring `"algorithm and hash_size"` (see section 4) |
| `before.hash_size != after.hash_size` | `ValueError` | identical message/condition to the row above — algorithm and hash_size mismatches are not distinguished into separate exception paths |

No warnings are raised under any condition. No coercion or automatic conversion is performed for
a type or hash-space mismatch. There is no flag to ignore a hash-space mismatch. There is no
partial result: any raised exception means no `PerceptualHashManifestDiff` is constructed at all.

## 12. Test plan

All tests live in a new `tests/test_manifest_comparison.py` (mirroring how `similarity.py`'s
tests live in their own `tests/test_similarity.py`, separate from `tests/test_manifest.py`, since
this is a distinct operation from manifest construction/serialization even though it lives in the
same source module).

| # | input | expected output | contract protected |
|---|---|---|---|
| 1 | `before`/`after` both empty manifests, same algorithm/hash_size | `PerceptualHashManifestDiff(added=(), removed=(), changed=(), unchanged=())` | baseline correctness on empty input |
| 2 | `before` empty, `after` has N entries | `added` = all of `after.entries`; `removed`/`changed`/`unchanged` empty | pure-add path (right-tail drain) |
| 3 | `before` has N entries, `after` empty | `removed` = all of `before.entries`; others empty | pure-remove path (left-tail drain) |
| 4 | `before`/`after` built independently but with identical path→hash content | `added`/`removed`/`changed` empty; `unchanged` = every path | equality-based (not identity-based) comparison |
| 5 | `before={a,b}`, `after={a,b,c}` | `added=(c,)`, rest `unchanged` | pure-add mid-merge (no removed/changed noise) |
| 6 | `before={a,b,c}`, `after={a,b}` | `removed=(c,)`, rest `unchanged` | pure-remove mid-merge |
| 7 | `before`/`after` share the same path set, exactly one path's hash differs | `changed=(Change(path, before_hash, after_hash),)`, rest `unchanged` | same-path hash-diff detection |
| 8 | `before={a,b,c,d}`, `after={b(changed),c,e}` | `removed=(a,d)`, `changed=(b,)`, `unchanged=(c,)`, `added=(e,)` | full merge-join correctness across all four branches in one call |

| 10 | paths containing non-ASCII text, e.g. `"dane/żółw.png"` (mirrors `test_entry_accepts_valid_unicode_path` in `tests/test_manifest.py`), one such path changed | correct classification, exact Unicode text preserved in the result's `path`/entry fields | Unicode correctness of the merge-join's string comparison |
| 11 | mixed-depth paths, e.g. `"a.png"`, `"a/b.png"`, `"a/b/c.png"`, `"a-b.png"` across `before`/`after` with some added/removed/changed | correct classification and canonical ascending order in every output field | correctness of `.as_posix()` string ordering across nested vs. flat paths (exercises the `-` vs `/` ordering subtlety from section 9) |
| 12 | `before.algorithm=AVERAGE_HASH`, `after.algorithm=PHASH`, same `hash_size` | `ValueError`, message matches `"algorithm and hash_size"` and names both algorithm values | hash-space mismatch validation, algorithm axis |
| 13 | `before.hash_size=8`, `after.hash_size=16`, same `algorithm` | `ValueError`, same message contract as #12 | hash-space mismatch validation, hash_size axis |
| 14 | `before` is `None` / a `dict` / a `PerceptualHashManifestEntry` (wrong type entirely) | `TypeError` naming `"before"` | type validation of `before`, and that it is checked ahead of `after` and ahead of the hash-space check |
| 15 | `after` is `None` / a `str` / an unrelated object | `TypeError` naming `"after"` | type validation of `after`, checked independently of `before` |
| 16 | direct attribute assignment on a constructed `PerceptualHashManifestDiff`/`PerceptualHashManifestChange` | `dataclasses.FrozenInstanceError` (mirrors `test_manifest_is_frozen`/`test_entry_is_frozen` in `tests/test_manifest.py`) | immutability consistency with every other public result type |
| 17 | attempt to set an undeclared attribute on either new type | `AttributeError` (slots enforcement) | memory-layout consistency (`slots=True`) with existing dataclasses |
| 18 | two independently constructed `PerceptualHashManifestDiff`/`PerceptualHashManifestChange` with equal field values; `repr()` of each | `==` compares `True`; `repr()` contains the class name and field values (default dataclass repr) | value-based equality and readable repr, both relied on by tests #8-#11 |
| 19 | `import improcv as im`; access `im.compare_perceptual_hash_manifests`, `im.PerceptualHashManifestDiff`, `im.PerceptualHashManifestChange` | all three resolve without `AttributeError` | top-level re-export completeness |
| 20 | inspect `im.__all__` | contains all three new symbol names at the exact alphabetically-sorted positions described in section 8 | `__all__` maintenance discipline |
| 21 | call `compare_perceptual_hash_manifests(before, after)` twice with the same two manifest instances | both results compare `==` | determinism (no reliance on non-deterministic iteration anywhere internally) |
| 22 | call `compare_perceptual_hash_manifests(before, after)` with `Path.exists`/`Path.stat`/`Path.is_file`/`builtins.open` monkeypatched to raise (mirrors `test_does_not_touch_filesystem` in `tests/test_similarity.py`, line 553) | call succeeds normally, no monkeypatched function is ever invoked | purity / in-memory-only guarantee, matching the user problem's explicit "bez dostępu do filesystemu" requirement |

**Benchmark**: `benchmark not required`. The operation is `O(n + m)` over already-in-memory,
already-validated, already-sorted data with no filesystem access, no image decoding, and no
per-pair comparison loop — nothing about its cost profile is uncertain or contested the way
`find_similar_image_pairs`'s `O(n**2)` cost was when its own benchmark was captured. No realistic
manifest size makes a linear merge-join a credible performance concern.

  next question a reader of that section would ask: "I saved a manifest — now what changed since
  I saved it?"). Must state the path-based identity rule, the rename-as-remove-plus-add rule
  (explicitly, with a short version of Example 3 above), and that this has nothing to do with
  freshness/caching — reusing this document's own "not a cache" framing rather than inventing new
  wording.
- **`examples/README.md`**: one new bullet describing `examples/manifest_comparison.py`, alongside
  the existing `image_similarity_manifest.py`/`dataset_manifest_builder.py` bullets.
- **`examples/manifest_comparison.py`** (exact name, chosen for direct parallelism with
  `examples/image_similarity_manifest.py`): builds two manifests directly via
  `PerceptualHashManifest.from_hashes` from two small, hand-constructed `{identifier: PerceptualHash}`
  mappings (**not** from a written-to-disk dataset) — this example's entire point is that the
  comparison itself needs no filesystem access, so building the two manifests from images on disk
  (as `dataset_manifest_builder.py` does) would dilute that message. A minimal deterministic
  scenario: `before` has `{"cats/a.png": H1, "cats/b.png": H2, "cats/old_name.png": H3}`; `after`
  has `{"cats/a.png": H1, "cats/b.png": H2_changed, "cats/new_name.png": H3, "cats/c.png": H4}` —
  covering unchanged (`a.png`), changed (`b.png`), a rename shown explicitly as remove+add
  (`old_name.png`→`new_name.png`, same hash `H3` on both sides, printed with an explicit comment
  noting it is *not* detected as a rename), and a pure add (`c.png`) in one scenario. Stdout
  prints each category's count and contents, plus one explicit printed line calling out that
  `old_name.png`/`new_name.png` share a hash but are reported as separate `removed`/`added`
  entries — making the non-rename-detection behavior visible in the example's own output, not just
  in a code comment. No `cv2`/`numpy`/temporary directory is needed at all for this example, unlike
  every other `examples/*.py` script, precisely because the operation being demonstrated has no
  filesystem or decoding component — this absence is itself the point being illustrated.
- **`tests/test_examples.py`**: extend the existing example-smoke-test coverage (this file already
  runs every `examples/*.py` script and checks its stdout) with `manifest_comparison.py`.
- **`CHANGELOG.md`**: one `[Unreleased]` entry once implementation actually lands (not in this
  design-only PR, whose own diff must not touch `CHANGELOG.md` at all).

## 14. Explicitly out of scope

This slice explicitly does not include: rename detection; content identity above path identity;
perceptual matching between `added` and `removed` entries; filesystem access of any kind;
freshness detection; caching; incremental rebuild; manifest schema v2; JSON serialization of a
`PerceptualHashManifestDiff`; `save`/`load` for a diff result; duplicate grouping/clustering;
indexed or subquadratic search; parallelism; progress/cancellation; mutating either input manifest
in any way; and any new parameter on any existing public function (`build_perceptual_hash_manifest`,
`PerceptualHashManifest.from_hashes`, `find_similar_image_pairs`, or any other symbol untouched by
this design).

## 16. Alternatives rejected for the first `0.4.x` slice

(Summarized from the prior read-only `0.4.x` direction audit; not repeated in full here.)

- **Incremental rebuild/freshness**: no small first slice exists — any real version touches
  manifest schema v1 (which strictly enforces its exact field set) or a hidden sidecar cache, plus
  the already-stable `build_perceptual_hash_manifest` signature simultaneously.
- **Duplicate grouping**: at least three legitimate, mutually incompatible semantics exist
  (connected components, complete-link, star-around-a-representative) with no single obvious
  public definition and no usage evidence pointing at one over the others.
- **Indexed/subquadratic search**: no realistic dataset size has ever been demonstrated where the
  existing `O(n**2)` `find_similar_image_pairs` is actually a problem (largest captured benchmark:
  300 items / 44,850 pairs).
- **Parallel manifest building**: would change `build_perceptual_hash_manifest`'s long-documented
  sequential-execution contract, and no benchmark has shown sequential decoding/hashing to be a
  real bottleneck at any tested scale.
- **Progress/cancellation**: weakest evidence of any candidate considered, and its natural API
  shape depends on a parallelism model that does not exist yet.
