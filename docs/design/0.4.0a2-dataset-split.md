# Design: deterministic dataset splitting (`0.4.0a2` first slice)

## 1. User problem

```text
Mam deterministycznie odkrytą sekwencję próbek (np. obrazy z discover_images,
albo image/mask pairs z discover_image_mask_pairs) i chcę podzielić ją na
train/validation/test bez ręcznego shuffle+slice, bez utraty próbek i bez
dzielenia atomowej próbki pomiędzy splity.
```

`discover_images`/`discover_image_mask_pairs` (shipped earlier in the dataset-discovery line) return a
deterministic, materialized `tuple[Path, ...]` / `tuple[ImageMaskPair, ...]` and stop there. ROADMAP.md
names the gap explicitly: *"manifests, dataset splits, and batching/loading remain planned, not
started"*; CHANGELOG.md's entry for `discover_image_mask_pairs` states the same exclusion at the moment
that function shipped: *"no dataset splits, manifests, or loading/decoding in this slice"*. This design
closes the "dataset splits" part of that gap with one function, `split_dataset`.

This document is the outcome of a read-only product/architecture audit of the `0.4.x` direction
(covering candidates A–J: dataset splits, batching, image/mask loading, duplicate grouping, incremental
manifest freshness, indexed search, parallel manifest building, progress/cancellation, an evaluation
usability slice, and an open slot for another candidate). `split_dataset` scored highest on toolkit
breadth, workflow completion, and reuse across CV tasks, with the lowest compatibility/implementation
risk of any real candidate, while `load_image_mask_pair` and `batch_items` were identified as the two
next-best alternatives (see §16).

## 2. Scope

In scope for this first slice:

- One function, `split_dataset`, operating entirely in memory on an already-materialized `Sequence[T]`.
- One small, generic result type, `DatasetSplit[T]`.
- Ratio-based train/validation/test split specification, with `test` as the exact remainder.
- A single, frozen, deterministic-given-`rng`-state allocation (rounding) policy.
- Explicit, tested behavior for empty input, single-item input, duplicate values, and every stated
  ratio edge case.

Explicitly out of scope for this slice (full list in §30 of the task / §"Explicitly out of scope"
below): stratification, class labels, grouped/subject-aware splitting, semantic-leakage detection,
duplicate-content detection, exact-count split specification, arbitrary named N-way splits, k-fold /
cross-validation, persistence of a split result, manifest integration, filesystem discovery, image/mask
loading or decoding, batching, collation, any framework `Dataset`/`DataLoader` shape, and any new runtime
dependency.

## 3. Input abstraction

Three candidates were compared: `Sequence[T]`, `Collection[T]`, `tuple[T, ...]`.

- **`tuple[T, ...]`** — rejected. It would reject a plain `list[T]` (a completely ordinary way to hold a
  dataset before splitting it) and would force every caller to wrap their data in a `tuple(...)` call
  first, for no benefit: `split_dataset` never mutates its input and never needs a `tuple`'s specific
  guarantees over any other `Sequence`.
- **`Collection[T]`** — rejected. `Collection` guarantees `__len__` and `__iter__`/`__contains__` but
  *not* `__getitem__` (positional indexing). Splitting by permutation of positional indices (§9, §15)
  requires `items[i]` for an arbitrary integer `i` — a `Collection` that is a `set` or a one-shot
  iterable would not support that, and materializing it defeats the purpose of accepting the caller's
  own sequence type directly.
- **`Sequence[T]`** — accepted. `collections.abc.Sequence` guarantees both `__len__` and `__getitem__`
  by integer index, exactly what the permutation-based split (§9) needs, and is the same abstraction
  `discover_images`/`discover_image_mask_pairs` already produce (`tuple[Path, ...]` and
  `tuple[ImageMaskPair, ...]` are both `Sequence`).

### Concrete input forms (verified empirically against `collections.abc.Sequence`/`Mapping`)

| Input | `isinstance(x, Sequence)` | `isinstance(x, Mapping)` | Accepted? |
|---|---|---|---|
| `list[T]` | `True` | `False` | **Yes** |
| `tuple[T, ...]` | `True` | `False` | **Yes** |
| `discover_images(...)` result (`tuple[Path, ...]`) | `True` | `False` | **Yes** |
| `discover_image_mask_pairs(...)` result (`tuple[ImageMaskPair, ...]`) | `True` | `False` | **Yes** |
| `range(...)` | `True` | `False` | **Yes** (harmless; splits the integers themselves) |
| a custom class implementing the `Sequence` protocol | `True` (if registered/subclassed correctly) | `False` | **Yes** |
| `str` (e.g. `"images"`) | `True` | `False` | **No — explicit `TypeError`** |
| `bytes` | `True` | `False` | **No — explicit `TypeError`** |
| `bytearray` | `True` | `False` | **No — explicit `TypeError`** |
| `dict` / any `Mapping` | `False` | `True` | **No — explicit `TypeError`** |
| a bare generator or other iterator | `False` | `False` | **No — `TypeError`** (fails the generic `Sequence` check) |
| `pathlib.Path` | `False` | `False` | **No — `TypeError`** (fails the generic `Sequence` check; a single `Path` is one sample, not a dataset — see §22) |
| `numpy.ndarray` | `False` | `False` | **No — explicit `TypeError`** (see rationale below) |

`str`/`bytes`/`bytearray` genuinely satisfy `isinstance(x, Sequence)` (a string is a sequence of its own
characters) — accepting them unchanged would silently split a dataset root path or a raw label string
into a "dataset" of single characters, exactly the failure mode `discovery._normalize_extensions`
already guards against for its own `extensions` parameter. This is why they get a dedicated, explicit
`isinstance(items, (str, bytes, bytearray))` check with a specific error message, evaluated *before* the
generic `Sequence` check — the generic check alone would let them through with no explanation of what
went wrong at the type-error stage; the dedicated check names the exact reason.

`dict`/`Mapping` fails the generic `Sequence` check anyway (verified above: `isinstance({}, Sequence)`
is `False`), but gets its own dedicated `isinstance(items, Mapping)` check first, mirroring
`discovery._normalize_extensions`'s own pattern, so a caller who passes a `dict` (e.g. a
`path -> PerceptualHash` mapping by mistake) gets a message that explains iterating a `Mapping` walks
its *keys*, not `(key, value)` pairs — rather than a bare "not a Sequence" message that doesn't explain
why a `dict` (which does support `len()` and `in`) fails.

`pathlib.Path` is **not** registered as a `Sequence` (verified: `isinstance(Path("images"), Sequence)`
is `False` — `Path` has no `__getitem__`/`__len__` as a sequence of path components; `.parts` exists for
that but `Path` itself does not implement it). It is therefore rejected by the same generic check as any
other non-`Sequence` object, with no special case needed — but this is verified explicitly here, not
assumed, per §22.

**`numpy.ndarray` is explicitly rejected**, even though it supports `len()` and integer indexing.
Verified: `isinstance(np.array([...]), Sequence)` is `False` (NumPy arrays are not registered against
`collections.abc.Sequence`), so an unqualified `Sequence` check would already reject it — but the
rejection is made an explicit, named check with a dedicated message rather than left to fall through to
the generic "not a Sequence" error, because a NumPy-heavy audience is exactly the group most likely to
try `split_dataset(np.array([...]), ...)` and be confused by an unexplained rejection. The rejection
itself (not just the message) is deliberate: an `np.ndarray` of *samples* (e.g. object-dtype array of
`Path`s) is genuinely ambiguous with an `np.ndarray` of *stacked pixel data* (e.g. shape `(N, H, W, C)`)
where "split along axis 0" is an equally plausible reading — resolving that ambiguity is explicitly
deferred, not decided silently. The error message directs the caller to `tuple(items)`/`list(items)`
first if they intend the "array of opaque samples" reading.

A bare generator or other one-shot iterator is rejected (fails the `Sequence` check — no `__len__`, no
integer `__getitem__`) — consuming it destructively to get a length would contradict `split_dataset`
never mutating or exhausting its input, and the caller most likely intended a materialized sequence.

## 4. Sample identity: occurrence, not value

This is a mandatory, load-bearing decision. For a generic `Sequence[T]`, **item equality is not sample
identity**. Example:

```python
items = ["a", "a", "b"]
```

The two `"a"` values are two distinct input *positions* (index `0` and index `1`), even though
`items[0] == items[1]`. `split_dataset` makes no assumption that `T` is hashable and no assumption that
`T`'s `__eq__` means anything beyond incidental value equality (an `ImageMaskPair` of two different files
that happen to decode to identical bytes is still two different samples; a `Path` object with a custom
subclass overriding `__eq__` must not be silently merged with another).

The guarantee is stated purely in terms of **input positions** (equivalently, occurrences):

> Every input position (`0 <= i < len(items)`) is assigned to exactly one of `train`/`validation`/`test`.
> No input position is omitted. No input position is assigned twice.

It is explicitly **not** guaranteed that a given *value* of `T` appears in only one split — two equal
values at two different positions may land in two different splits, and that is correct, not a defect.
This is why §9's algorithm permutes *indices*, not the items themselves (see §15), and why the test plan
(§25) requires a case with duplicate values at different positions to prove this distinction in practice,
not just in prose.

## 5. Public API shape

```python
def split_dataset(
    items: Sequence[T],
    *,
    train: float,
    validation: float = 0.0,
    rng: np.random.Generator,
) -> DatasetSplit[T]:
    ...
```

`items` is the sole positional parameter, matching the existing convention that the "main data" argument
of a public function is positional and everything else is keyword-only (`discover_images(root, ...)`,
`find_similar_image_pairs(hashes, *, max_distance)`, `compare_perceptual_hash_manifests(before,
after)`). `train`/`validation`/`rng` are keyword-only. `rng` deliberately has **no default** — matching
`sample_flip`'s own `rng: np.random.Generator` parameter (no default) and `find_similar_image_pairs`'s
`max_distance` (no default): guessing a source of randomness silently would be worse than requiring it
explicitly, and a hidden default would tempt a caller into relying on an undocumented global seed. `train`
also has no default, for the same reason — there is no "obviously correct" default train ratio.
`validation` defaults to `0.0` (no validation split, only train/test), which is a safe, explicit "off"
state, not a guess about magnitude.

### `test` as the exact remainder, not an independent parameter

Two shapes were compared:

- **All three ratios supplied independently** (`train`, `validation`, `test`, each required) — rejected.
  This forces every caller to satisfy a redundant three-way constraint (`train + validation + test ==
  1.0` exactly) on top of each individual range check, which is exactly the kind of constraint that
  floating-point arithmetic makes needlessly fragile (§6) for no expressive benefit: the three ratios are
  never independent in the first place, since they must always sum to the whole dataset.
- **`train`/`validation` supplied, `test` computed as `1.0 - train - validation`** — accepted. This
  matches well-known precedent outside this codebase (e.g. `sklearn.model_selection.train_test_split`
  only ever takes one of `train_size`/`test_size`, never both required simultaneously) and, inside this
  codebase, reduces the ratio-validation surface to exactly two independent range checks plus one sum
  check (§6), instead of three range checks plus an exact-equality check.

This is a deliberate design decision, not left open for the implementer: `split_dataset` takes exactly
`train`/`validation`; `test` is never a parameter.

## 6. Ratio validation — exact rule, no ambiguity

Accepted range, checked in this exact order:

1. `train`/`validation` must each be a real number (`numbers.Real`, matching `require_real_number`'s
   existing acceptance of plain `int`/`float`/NumPy scalar types) and explicitly **not** `bool` — the
   same guard `require_real_number` already applies everywhere else in the codebase, since a `bool` is
   technically an `int` subclass but accepting `True`/`False` here would silently misinterpret a boolean
   as `1.0`/`0.0`. **`int` is accepted** (e.g. `train=1` is legal and equivalent to `train=1.0`), matching
   `require_range`'s existing behavior for every other probability-shaped parameter in the codebase
   (e.g. `sample_flip`'s `horizontal_probability`).
2. `train`/`validation` must each be finite (`not NaN`, `not ±inf`) — `float("nan")`, `float("inf")`,
   `-float("inf")` are all rejected with `ValueError`.
3. `train`/`validation` must each satisfy `0.0 <= value <= 1.0`, checked with an **exact** comparison,
   reusing the existing `require_range(value, 0.0, 1.0, name)` helper unchanged — no new validator is
   introduced. `0.0` and `1.0` are both legal for either parameter (matching `sample_flip`'s own
   `horizontal_probability`/`vertical_probability`, where `0.0`/`1.0` are both explicitly documented as
   legal).
4. `train + validation` must satisfy `<= 1.0`, checked with an **exact** comparison (`train + validation
   <= 1.0` in IEEE 754 double precision) — **no `math.isclose` tolerance**.

### Why exact comparison, not `math.isclose`

`require_range` (used by every other ratio/probability parameter in this codebase, e.g. `sample_flip`'s
probabilities) already performs an exact boundary comparison with no tolerance. Introducing a tolerance
just for the `train + validation <= 1.0` sum check would be the only tolerance-based check in the entire
validation layer (`_validation.py` has none), which would need its own new, unjustified epsilon constant.
Verified concretely (Python `float` arithmetic, the only representation this parameter type uses):

| Expression | Value | `<= 1.0`? |
|---|---|---|
| `0.7 + 0.2` | `0.8999999999999999` | `True` |
| `0.1 + 0.2` | `0.30000000000000004` | `True` |
| `0.8 + 0.2` | `1.0` (exact) | `True` |
| `0.5 + 0.5` | `1.0` (exact) | `True` |
| `1/3 + 1/3` | `0.6666666666666666` | `True` |
| `0.9999999999999999` (a literal) | `0.9999999999999999` | `True` (`!= 1.0`, but well under it) |
| `1.0000000000000002` (a literal) | `1.0000000000000002` | `False` (rejected, correctly — this literal genuinely denotes a value greater than 1.0 in IEEE 754 double precision) |

No case among ordinary decimal ratio literals (checked exhaustively for every `(train, validation)` pair
on a `0.0..1.0` step-`0.1` grid) produces a sum that *should* mathematically be `<= 1.0` but is pushed
strictly above `1.0` by floating-point rounding. The one acknowledged, accepted edge case is the reverse
direction: a caller who mentally intends an *exact* boundary sum (e.g. thirds: `1/3 + 1/3 + 1/3 == 1.0`
conceptually) may observe that the derived `test` ratio differs from the naive expectation at the last
bit of precision — this is documented in §9's rounding-policy discussion, where it has a real, visible
(but still fully deterministic and harmless) effect on which split receives a rounding remainder, not on
whether validation passes.

## 7. Allocation / rounding policy — Largest Remainder Method

**Rejected: independent floor per split.**

```text
n_train = floor(n * train)
n_validation = floor(n * validation)
n_test = n - n_train - n_validation
```

This always routes every fractional unit of rounding error into `test`, regardless of which split's
ideal count was actually closest to rounding up. Concretely, for `n=10, train=0.5, validation=0.25`
(ideal counts `5.0 / 2.5 / 2.5`): independent floor gives `train=5, validation=2, test=3` — `test` silently
absorbs *both* fractional halves, even though `validation`'s ideal count was exactly as close to
rounding up as `test`'s. This is a systematic, undisclosed bias against whichever split is computed last.

**Rejected: naive `round()` per split (`round(n * train)`, `round(n * validation)`).**

Python's `round()` uses round-half-to-even ("banker's rounding"): `round(0.5) == 0`, `round(1.5) == 2`,
`round(2.5) == 2`. Applied independently to `n * train` and `n * validation`, this (a) produces
counter-intuitive jumps for small `n` that depend on whether the rounded value happens to be even or odd,
not on the ratio itself, and (b) does not, by construction, guarantee `n_train + n_validation <= n` — a
defensive clamp would be needed on top, adding complexity without adding correctness, and the composite
behavior would not correspond to any single, statable algorithm.

**Accepted: the Largest Remainder Method** (a well-known, exact-sum-preserving apportionment algorithm),
with a fixed tie-break order:

1. Compute `test = 1.0 - train - validation` (§5).
2. Compute the three *ideal* (real-valued) counts: `ideal_train = n * train`, `ideal_validation = n *
   validation`, `ideal_test = n * test`.
3. Floor each: `floor_train = floor(ideal_train)`, etc. These three floors always sum to `n`, `n - 1`, or
   `n - 2` (never less, since each floor loses less than `1.0`, and there are exactly three buckets).
4. `remainder = n - (floor_train + floor_validation + floor_test)` — an integer in `{0, 1, 2}`.
5. Distribute `remainder` extra unit(s), one at a time, to the split(s) whose *fractional part*
   (`ideal - floor`) is largest. **Ties are broken by fixed priority order: `train`, then `validation`,
   then `test`.** Ties here mean *exact* IEEE 754 equality of the fractional part — no epsilon.

This guarantees, by construction, that `n_train + n_validation + n_test == n` exactly, for every `n` and
every valid `(train, validation)` pair — an invariant independent floor and naive `round()` do not both
provide.

### Why this tie-break order

Preferring `train` first, then `validation`, then `test` is a small, disclosed, and rare bias (it only
applies on an *exact* tie of fractional parts) that favors the split most central to the ratio the caller
specified first. It is fully deterministic and RNG-independent: **which item lands in which split is
randomized (§9); how many items go into each split is a pure, deterministic function of `n`, `train`, and
`validation` alone.** This separation is itself a property worth stating explicitly, since it means the
split *sizes* are exactly reproducible and predictable without even constructing an `rng`, while only the
*membership* depends on it.

### Rounding is not always a "3-way tie" in the way it looks

`test = 1.0 - train - validation` is computed by subtraction, so its float value is frequently not
bit-identical to what a reader mentally expects from the decimal ratio. Two concrete, independently
verified examples (Python `float`, the only representation this parameter type uses):

- `train=0.70, validation=0.15`: `test` evaluates to `0.15000000000000005`, not exactly `0.15`. For
  `n=10`, `ideal_test = 1.5000000000000004`, whose fractional part (`0.5000000000000004`) is
  infinitesimally *larger* than `ideal_validation`'s exact `0.5` — so the single remainder unit goes to
  `test`, not `validation`, giving `(7, 1, 2)`, not `(7, 2, 1)`. A reader expecting `validation` to win an
  apparent "0.5 vs 0.5" tie (by the stated `train`-then-`validation`-then-`test` priority) would be
  surprised without this explanation — the two fractional parts were never actually equal in IEEE 754.
- `train=1/3, validation=1/3`: `test`'s float value (`0.3333333333333334`) is one bit larger than
  `train`'s/`validation`'s own literal (`0.3333333333333333`). For `n=10`, this makes `test`'s fractional
  part (`0.33333333333333437`) infinitesimally larger than `train`'s (`0.33333333333333304`), so the
  single remainder unit goes to `test`, giving `(3, 3, 4)`, not `(4, 3, 3)` as a naive "three equal
  thirds, `train` wins ties" reading might expect.

Both outcomes are accepted, documented behavior, not a bug: each is fully deterministic and reproducible
(the same IEEE 754 arithmetic on any platform improcv supports produces the same bit pattern), neither
violates the `sum == n` invariant, and neither depends on `rng` at all — in both cases, the fixed
`train`/`validation`/`test` tie-break priority never actually gets exercised, because the two candidate
fractional parts were never bit-identical in the first place once one of them was derived by subtraction.
Documenting these two examples concretely (rather than asserting an untested intuition) is preferred to
inventing an epsilon-based "is this really a tie" heuristic, which would need its own arbitrary tolerance
and would not remove the underlying representational subtlety, only hide it.

## 8. Split counts — worked examples

All rows use the Largest Remainder Method from §7. `train`/`validation` are the input ratios; `test` is
always the exact remainder `1.0 - train - validation`.

| `n` | `train` | `validation` | `n_train` | `n_validation` | `n_test` | Note |
|---|---|---|---|---|---|---|
| 0 | 0.70 | 0.15 | 0 | 0 | 0 | empty input, all-empty result (§11) |
| 1 | 0.70 | 0.15 | 1 | 0 | 0 | single item, entirely to the largest ideal count |
| 2 | 0.70 | 0.15 | 2 | 0 | 0 | ideal `1.4/0.3/0.3` — floors already sum to `n` (remainder 0) |
| 3 | 0.70 | 0.15 | 2 | 0 | 1 | ideal `2.1/0.45/0.45(+ULP)` — remainder 1, goes to `test` (see §7's IEEE 754 note) |
| 10 | 0.70 | 0.15 | 7 | 1 | 2 | ideal `7.0/1.5/1.5(+ULP)` — remainder 1, goes to `test`, not `validation` (see §7's IEEE 754 note) |
| 11 | 0.70 | 0.15 | 8 | 1 | 2 | ideal `7.7/1.65/1.65(+ULP)` — remainder 2, goes to `train` (largest fraction) and `test` |
| 10 | 0.80 | 0.10 | 8 | 1 | 1 | exact integers, no rounding remainder at all |
| 10 | 0.50 | 0.25 | 5 | 3 | 2 | ideal `5.0/2.5/2.5` — remainder 1, goes to `validation` (an exact tie here — `test`'s ratio, `0.25`, is not perturbed relative to `validation`'s own `0.25` literal in this particular case) |
| 3 | 1/3 | 1/3 | 1 | 1 | 1 | ideal `1.0/1.0/1.0` — remainder 0 |
| 10 | 1/3 | 1/3 | 3 | 3 | 4 | ideal `3.333.../3.333.../3.333...(+ULP)` — remainder 1, goes to `test` (see §7's IEEE 754 note) |
| 2 | 0.50 | 0.50 | 1 | 1 | 0 | empty `test` split — legal |
| 1 | 1.00 | 0.00 | 1 | 0 | 0 | zero-sized `validation` and `test` — legal |
| 5 | 1.00 | 0.00 | 5 | 0 | 0 | same, larger `n` |
| 5 | 0.00 | 1.00 | 0 | 5 | 0 | zero-sized `train`/`test` — legal (`train=0.0` is explicitly allowed) |

Every row was computed by an independent, throwaway script implementing exactly §7's algorithm (floor
each ideal count, distribute the remainder by largest fractional part, tie-break `train` →
`validation` → `test`), run twice to confirm reproducibility, per this project's own testing discipline
of never hand-copying a single run's output into a written assertion. `n_train + n_validation + n_test
== n` holds exactly for every row, as guaranteed by construction (§7).

## 9. Empty input

`items = []` / `items = ()` is **legal**, not an error: `split_dataset([], train=0.7, rng=rng)` returns
`DatasetSplit(train=(), validation=(), test=())`.

This matches strong, consistent existing precedent across the dataset-discovery/hashing line, not just a
default preference: `discover_images` on an empty directory "returns `()`, not an error"; a `hashes`
mapping with fewer than two entries makes `find_similar_image_pairs` return `()`, not raise;
`build_perceptual_hash_manifest` "returns a well-defined, empty manifest ... not an error" for an empty
dataset. `split_dataset` follows the same rule for `n=0`: an empty collection of samples is a legitimate,
well-defined dataset with a well-defined (entirely empty) split, not an error condition.

## 10. RNG contract

### Consume, don't clone

`split_dataset` **consumes the given `rng` directly** — it advances the caller's own `Generator`'s
internal state exactly as much as its internal draws require, and never constructs an internal copy or
clone of it. This exactly matches the existing precedent in `augmentation.py`: `sample_flip`/
`sample_affine`/`sample_crop`/`sample_perspective` all call methods directly on the `rng` object passed
in (`rng.random()`, `rng.uniform(...)`, `rng.integers(...)`), mutating its state as a side effect, with no
internal state cloning anywhere in that module. `split_dataset` reuses that exact, already-established
pattern rather than introducing a second, inconsistent RNG-handling convention in the same codebase.

This is publicly observable behavior, stated explicitly: **passing the same, not-yet-otherwise-consumed
`rng` object to two separate `split_dataset` calls produces two different results** (the second call
observes the state the first call already advanced), and **two independently constructed `Generator`
instances seeded identically** (e.g. two separate `np.random.default_rng(0)` calls, each not yet consumed
by anything else) **passed to two separate `split_dataset` calls with the same `items`/`train`/
`validation` produce identical results.**

### `rng` type: `np.random.Generator` only, checked by `isinstance`

`rng` must be an actual `numpy.random.Generator` instance, checked by `isinstance` — not duck-typed, and
not a bare `int` seed. A legacy `numpy.random.RandomState`, a bare integer, the `numpy.random` module
itself, or any object merely implementing a compatible interface are all rejected with `TypeError`. This
mirrors `augmentation._require_generator`'s exact contract and message shape. A bare integer `seed`
parameter is explicitly out of scope (§30) — the caller constructs their own `np.random.default_rng(seed)`
and passes the `Generator`, exactly as every `sample_*` function in `augmentation.py` already requires.

No global/ambient RNG (`np.random.seed`, the free functions in the `numpy.random` module, Python's own
`random` module) is read or written anywhere in this function.

## 11. Determinism guarantee — exact scope

The guarantee is deliberately no stronger than what this codebase already promises elsewhere for
RNG-driven functions:

> Same `items` (same positions, same values) + a `rng` in the same internal state + the currently
> supported NumPy/Python implementation stack → the same `DatasetSplit`.

Explicitly **not** guaranteed: that this exact split is frozen forever across every future NumPy/Python
version improcv might someday support. Mirroring `sample_flip`'s own documented policy verbatim in
spirit: *"The exact number and order of internal draws against `rng`, and the specific permutation
algorithm used (`rng.permutation`, §12), are implementation details, not part of the public contract, and
may change between releases without notice."* What changes-between-releases would *not* affect is
`DatasetSplit`'s sizes (§7 is a pure function of `n`/`train`/`validation`, independent of `rng` entirely)
— only *which* items land in which split could shift if a future release changed the permutation
mechanism, and even then only for callers who upgrade improcv between constructing their `rng` state and
calling `split_dataset`.

This is not a new, stronger guarantee than the rest of the library already makes — it is the same one,
applied consistently.

## 12. Permutation semantics

The implementation permutes **indices**, not values:

```python
indices = rng.permutation(len(items))
```

`rng.permutation(n)` returns a NumPy array of the integers `0..n-1` in a random order. Each split's
members are then obtained as `items[i]` for each index `i` in its assigned slice of `indices` — never by
comparing, hashing, or otherwise inspecting the *values* of `items`. This is what makes the occurrence-
based guarantee in §4 correct even for duplicate values, unhashable objects, or objects with an unusual
or absent `__eq__`: the split machinery never needs `T` to be hashable, never needs `T`'s equality to mean
anything, and never builds a `set`. Every element is read from `items` via `__getitem__` exactly once.

## 13. Ordering inside each split

Two options were compared:

- **(A) Permutation order** — each split preserves the order its elements appear in within the shuffled
  index sequence.
- **(B) Source order after assignment** — elements are assigned to splits randomly, but each split is
  then re-sorted back to the original input order.

**Accepted: (A), permutation order.** A split is conceptually a *shuffled* subset of the dataset — most
downstream consumers (a batching step, a training loop) expect a train split's order to already be
shuffled, not to need re-shuffling before use; re-sorting back to source order (B) would silently
reintroduce whatever structure existed in the caller's original ordering (e.g. alphabetical-by-filename,
which frequently correlates with acquisition time or class) into the very split meant to break that
structure. (A) is also strictly cheaper to implement and explain: the split is exactly a contiguous slice
of `indices`, applied to `items`, with no second sort. This is stated explicitly, not left implicit: the
order of items within `train`/`validation`/`test` is the permutation order, never re-sorted to match
`items`'s own original order.

## 14. Leakage semantics — exact disclaimer

Explicitly separated, per this design's own required scope:

**Guaranteed** ("sample occurrence overlap"): every input *position* is assigned to exactly one split; no
position is omitted; no position is used twice (§4).

**Not guaranteed** (all forms of "semantic leakage"):

- That the same *subject* (e.g. the same physical object, scene, or person photographed multiple times)
  does not appear in more than one split.
- That semantically or visually duplicate content (two different files with the same or near-identical
  content) does not appear in more than one split.
- Class balance across splits.
- Any stratification guarantee.
- Any grouped/subject-aware assignment (keeping all samples that share a group key together in one
  split).

This first slice carries no label, group ID, or subject ID concept at all — `T` is an opaque sample
identifier to `split_dataset`, so no promise beyond occurrence-level non-overlap can honestly be made.
A future, separate slice could add label/group-aware splitting; this slice does not attempt it and does
not gesture at it in its public contract.

## 15. `ImageMaskPair` composability

```python
pairs = discover_image_mask_pairs(image_root, mask_root)
split = split_dataset(pairs, train=0.7, validation=0.15, rng=np.random.default_rng(0))
```

Because `split_dataset` treats each element of `Sequence[T]` as one atomic sample (§4, §12), a single
`ImageMaskPair` — one `image: Path` and its `mask: Path` — is never separated across splits: it is drawn
and placed exactly once, as one unit, by the permutation over `pairs`' own indices. No new,
image-specific function (e.g. a hypothetical `split_image_mask_pairs`) is introduced or required for
this: the generic `Sequence[T]` contract already gives the correct behavior for
`Sequence[ImageMaskPair]` with no special-casing anywhere in `split_dataset`'s implementation. This
composability is treated as the primary evidence that the generic `Sequence[T]` abstraction (§3) is not
"too generic" for a CV-focused library: its main documented use cases are exactly the two existing
dataset-discovery outputs, `discover_images` and `discover_image_mask_pairs`.

## 16. Result type

Two shapes were compared against this codebase's own existing multi-field result types (`Features`,
`HomographyResult`, `ImageMaskPair`, `SimilarImagePair`, `PerceptualHashManifestChange`,
`PerceptualHashManifestDiff`):

- **(A) `NamedTuple`** (matching `ImageMaskPair`, `BoundingBox`) — positional tuple unpacking "for free",
  but combining `NamedTuple` with `Generic[T]` relies on a specific typing special case (only supported
  cleanly since Python 3.11, which happens to be improcv's floor, but is a narrower, less orthogonal
  corner of the type system than plain class/dataclass generics).
- **(B) `@dataclass(frozen=True, slots=True)`** (matching the most recently shipped, most structurally
  analogous precedent: `PerceptualHashManifestChange`/`PerceptualHashManifestDiff`, both plain,
  statically-typed value objects with **no custom `__post_init__`**, since neither has a cross-field
  invariant to enforce) — combines with `Generic[T]` with no special casing.

**Accepted: (B).** `DatasetSplit[T]`'s three fields (`train`/`validation`/`test`, each `tuple[T, ...]`)
have no cross-field invariant to validate at construction time (unlike, say, `SimilarImagePair`, which
does need a `__post_init__` to enforce canonical ordering) — so, like `PerceptualHashManifestDiff`, no
custom `__post_init__` is added. Positional tuple-unpacking (`train, validation, test = result`) is
judged **not needed**: none of this codebase's own usage of `PerceptualHashManifestDiff` unpacks it
positionally (call sites use `.added`/`.removed`/etc.), and named-field access is *more* explicit for a
3-tuple where a positional-order mistake (train/test/validation vs. train/validation/test) would be a
real, silent-failure risk. Default dataclass equality (element-wise tuple `==`) is sufficient — unlike
`AugmentedImageMask` (which needs a custom `__eq__` because its fields are raw `np.ndarray`s, and NumPy's
`==` returns an array, not a bool), `DatasetSplit[T]`'s fields are plain tuples whose `==` already
delegates correctly to `T.__eq__` (or falls back to identity comparison if `T` defines none), so no
override is required.

```python
T = TypeVar("T")


@dataclass(frozen=True, slots=True)
class DatasetSplit(Generic[T]):
    train: tuple[T, ...]
    validation: tuple[T, ...]
    test: tuple[T, ...]
```

## 17. Naming

### Function name

Compared: `split_dataset`, `split_samples`, `partition_dataset`.

- `partition_dataset` — rejected: "partition" already carries a distinct, established meaning elsewhere
  in computer vision (image/region partitioning, close to "segmentation"), and reusing it for dataset
  splitting risks a misleading association inside a CV-focused library.
- `split_samples` — a more literally accurate name for a fully generic `Sequence[T]` function, but a
  weaker thematic fit for the `improcv.dataset` module and for ROADMAP.md's own wording ("dataset
  splits").
- **`split_dataset`** — accepted. There is direct precedent in this codebase for a "module/function name
  names the CV domain, implementation is fully generic" pattern: `find_similar_image_pairs` lives in
  `similarity.py`, is named around "image" similarity, and is itself generic over path-like identifiers
  (`_PathIdentifierT`) with no image-specific logic in its body. `split_dataset` follows the same
  pattern: the *name* and *module placement* signal the CV dataset-splitting use case; the
  *implementation* is a fully generic `Sequence[T]` operation, exactly like `find_similar_image_pairs`'s
  own generic-over-`_PathIdentifierT` implementation living inside a domain-named module.

### Result type name

Compared: `DatasetSplit`, `DatasetSplits`, `SplitDatasetResult`.

- `DatasetSplits` (plural) — rejected: one call produces *one* split (into three parts), not multiple
  split objects; the plural reads as if it held a collection of split results.
- `SplitDatasetResult` — rejected: this codebase does use a `*Result` suffix for some multi-field
  outcomes (`HomographyResult`, `MinMaxResult`, `ConfusionMatrixResult`, `FloodFillResult`), but the most
  recent and most structurally analogous precedent — `PerceptualHashManifestDiff`, the result of the
  immediately preceding `0.4.0a1` slice — uses a plain domain noun, not a `*Result` suffix, for exactly
  this shape of type (several tuple fields describing a partition/comparison outcome). Naming
  consistency with the nearest, most recent analog is weighted over the older, more general `*Result`
  convention.
- **`DatasetSplit`** (singular) — accepted, matching `PerceptualHashManifestDiff`'s naming register.

## 18. Module placement

`split_dataset`/`DatasetSplit` are added to `src/improcv/dataset.py`, alongside
`build_perceptual_hash_manifest` — not a new `collections.py`/`utils.py`. `dataset.py` is already the
dataset-workflow orchestration module (ROADMAP.md's own text groups "dataset splits" under the same
"dataset discovery"/"dataset" line as `build_perceptual_hash_manifest`); a generic algorithm living in a
domain-named module already has direct precedent (`find_similar_image_pairs` in `similarity.py`, §17).
Creating a new module for exactly one function would fragment the dataset-workflow story across an extra
file for no benefit, and runs against this project's own stated preference (CLAUDE.md): "Don't grow a
deeply nested module hierarchy ahead of actual need."

## 19. Strings / paths subtlety

Verified explicitly (not assumed), per this design's own requirement:

```python
split_dataset(Path("images"), train=0.7, rng=rng)   # TypeError -- Path is not a Sequence
split_dataset("images", train=0.7, rng=rng)          # TypeError -- str explicitly rejected
split_dataset([Path("a.png"), Path("b.png")], train=0.7, rng=rng)   # OK -- list[Path] is a Sequence[Path]
```

A single `Path` is one sample, not a dataset, and is correctly rejected by the generic `Sequence` check
with no special case needed (§3's table). A bare `str` would otherwise be silently treated as a sequence
of its own characters and gets a dedicated, explicit rejection with a specific message (§3). A `list`/
`tuple` *of* `Path` objects is the intended, supported shape and works with no special handling.

## 20. Exception contract

Validation order (fixed, not left to the implementer): `items` type → `train` type/range → `validation`
type/range → `train + validation` sum → `rng` type.

| Condition | Exception | Message requirement |
|---|---|---|
| `items` is not a `Sequence` (e.g. `int`, custom non-Sequence object, `None`) | `TypeError` | names the actual type |
| `items` is `str` | `TypeError` | dedicated message naming `str`/`bytes`/`bytearray` as rejected, before the generic check |
| `items` is `bytes` | `TypeError` | same dedicated message |
| `items` is `bytearray` | `TypeError` | same dedicated message |
| `items` is a bare `Path` | `TypeError` | generic "must be a Sequence, got Path" (no special case; verified in §19) |
| `items` is a `Mapping` (e.g. `dict`) | `TypeError` | dedicated message explaining a `Mapping` iterates keys only |
| `items` is a generator/iterator | `TypeError` | generic "must be a Sequence, got generator"/`<type>` |
| `items` is a `numpy.ndarray` | `TypeError` | dedicated message, suggests `tuple(items)`/`list(items)` (§3) |
| `train`/`validation` wrong type (`str`, `None`, `complex`) | `TypeError` | names the parameter and the actual type |
| `train`/`validation` is `bool` | `TypeError` | explicit bool rejection, matching `require_real_number` |
| `train`/`validation` is `NaN` | `ValueError` | "must be finite" |
| `train`/`validation` is `+inf`/`-inf` | `ValueError` | "must be finite" |
| `train`/`validation` `< 0.0` | `ValueError` | "must be between 0.0 and 1.0" |
| `train`/`validation` `> 1.0` | `ValueError` | "must be between 0.0 and 1.0" |
| `train + validation > 1.0` (exact comparison, §6) | `ValueError` | names both values and their exact sum |
| `rng` is not a `numpy.random.Generator` (e.g. `int`, `RandomState`, the `numpy.random` module, `None`) | `TypeError` | mirrors `augmentation._require_generator`'s exact message shape |

No warnings, no silent coercion, anywhere in this contract.

## 21. Complexity

For `n = len(items)`:

- **Time**: `O(n)` — one `rng.permutation(n)` call (Fisher–Yates, linear) plus one linear pass to build
  the three output tuples.
- **Output memory**: `O(n)` — the three result tuples together hold exactly `n` references, total.
- **Permutation/index memory**: `O(n)` — `rng.permutation(n)` allocates a new NumPy integer array of
  length `n`; this is genuine additional memory, not reused from the input, and is not `O(1)`.
- **Overall additional memory (beyond input and output)**: `O(n)` — dominated by the permutation array;
  no larger structure (no set, no dict, no `O(n^2)` intermediate) is built anywhere in this algorithm.

No step in this design is `O(1)`; none is claimed to be.

## 22. Test plan

### Core

- `n=0` (empty `items`) → `DatasetSplit((), (), ())`, no error.
- `n=1` — every ratio combination that puts the single item in each of the three splits.
- Small (`n=2,3`) and a larger deterministic dataset (`n=100`, fixed seed).
- `train=0.0` — legal, `train` split empty.
- `train=1.0` — legal, `validation`/`test` splits empty.
- `validation=0.0` (the default) — no validation split.
- `train + validation == 1.0` exactly — `test` split empty.
- Zero-sized `train`, zero-sized `validation`, zero-sized `test` splits (each reachable via a distinct
  ratio/`n` combination from §8's table).

### Rounding

One test per row of §8's worked-examples table, asserting the exact `(n_train, n_validation, n_test)`
triple.

### Occurrences

- Duplicate equal values at different positions (`items = ["a", "a", "b"]` or `[Path("x"), Path("x")]`)
  — both occurrences must appear across the result exactly once total, at their own respective (possibly
  different) splits.
- Unhashable values (e.g. a plain mutable object with no `__hash__`) — must not raise, must not be
  deduplicated.
- Objects with a custom, non-default `__eq__` (e.g. one that always returns `True`) — must not be
  deduplicated or merged; every input position still appears exactly once, proving the split logic never
  relies on `__eq__`/`__hash__` (§12).
- Every input occurrence appears exactly once, verified by index identity (e.g. tagging each input
  position with its own index as a sentinel value, then checking the multiset of returned sentinels
  equals `range(n)` exactly).

### RNG

- Two independently constructed `np.random.default_rng(seed)` instances with the same `seed`, each not
  yet consumed by anything else, produce identical `DatasetSplit` results.
- The same `Generator` instance used twice in a row: the second call's result may differ from the first
  (state was consumed), demonstrating consumption, not cloning.
- A `Generator`'s saved/restored `bit_generator.state` reproduces the same result when replayed.
- Wrong `rng` type (`int`, `np.random.RandomState`, the `numpy.random` module, `None`) → `TypeError`.
- No hidden global RNG: monkeypatching `np.random.seed`/the free functions on the `numpy.random` module
  to raise on any call, then calling `split_dataset` with an explicit `rng`, must still succeed.

### Ordering

- Exact expected output order for one frozen `(items, train, validation, rng-state)` triple, asserted
  literally (not just membership) — proves permutation order (§13), not source order.
- Property-style tests asserting membership/counts (§23) independent of the specific permutation.

### Types (input abstraction)

- `list[T]`, `tuple[T, ...]`, a minimal custom `Sequence` subclass, `tuple[Path, ...]` (a real
  `discover_images` result), `tuple[ImageMaskPair, ...]` (a real `discover_image_mask_pairs` result) —
  all accepted.
- `str`, `bytes`, `bytearray`, a bare `Path`, a `dict`, a generator, a `numpy.ndarray` — all rejected with
  `TypeError`, matching §3/§20 exactly.

### Result type

- `DatasetSplit` is frozen (`FrozenInstanceError`/equivalent on attribute assignment) and uses `__slots__`
  (verified via `DatasetSplit.__slots__`, not by attempting an undeclared-attribute assignment — see this
  project's own known CPython `frozen=True, slots=True` quirk where that specific approach raises a
  confusing, version-dependent error instead of a clean one).
- Equality compares by value (two `DatasetSplit`s with equal `train`/`validation`/`test` tuples compare
  equal).
- `repr` is the default dataclass repr (no custom override).
- `Generic[T]` typing — a static-typing check (e.g. a Pyright snapshot in CI, not a runtime test) that
  `split_dataset([Path(...)], ...)` is inferred as `DatasetSplit[Path]`.
- Top-level exports: `improcv.dataset.split_dataset`, `improcv.dataset.DatasetSplit`,
  `improcv.split_dataset`, `improcv.DatasetSplit` — all importable, all identical objects (`is`) across
  both import paths.

### No I/O

Monkeypatch `pathlib.Path.open`/`os.stat`/`os.scandir`/`builtins.open` to raise on any call; run
`split_dataset` against a `tuple[Path, ...]` of *non-existent* paths (never opened) and confirm it still
succeeds — proving no filesystem access occurs anywhere in this function.

### No global RNG

Covered above (RNG section) via monkeypatching `numpy.random`'s free functions.

Property/differential testing is covered separately in §23 — no `Hypothesis` dependency is introduced;
this reuses the same stdlib-`random`-with-a-fixed-seed technique already used elsewhere in this
project's own test suite for differential smoke testing.

## 23. Property / differential test design

A fixed-seed (e.g. `20260807`, matching this project's own dated-seed convention), deterministic,
stdlib-`random`-driven test generates at least **2000** combinations of:

- `n` (dataset size, including `0`, `1`, and larger values),
- `train`/`validation` (random valid ratios, including exact-boundary and near-boundary values),
- a mix of unique and duplicate values in `items` (some generated cases deliberately repeat values at
  different positions).

For every generated case, verify:

- The exact `(n_train, n_validation, n_test)` triple matches an independently written reference
  implementation of §7's Largest Remainder Method (not the function under test's own internals).
- Every input position (by index) appears in exactly one of the three result tuples — no omissions, no
  duplications — checked via index identity, not value equality, so this holds even for the
  duplicate-value cases.
- `len(train) + len(validation) + len(test) == n` exactly.
- The function's behavior does not depend on `T` being hashable or defining `__eq__` meaningfully (the
  generated `items` include a custom class with no `__hash__` and a always-`True` `__eq__` in a fraction
  of cases).

No `Hypothesis` (or any other property-testing library) dependency is introduced — the same
plain-stdlib-`random`-with-fixed-seed technique already used for this project's own differential smoke
testing elsewhere is reused here.

## 29. Alternatives rejected (from the preceding product audit)

- **Image/mask pair loading** (`load_image_mask_pair`) — a real, valuable next step, but more
  opinionated: it must fix a default image color-decode mode and a mask/image dimension-matching
  validation policy, both genuine open design questions this document does not need to answer, and it
  touches `cv2.imdecode` across the OpenCV 4/5 compatibility surface, which `split_dataset` avoids
  entirely.
- **Batching / iteration** (`batch_items`) — the smallest possible next step, but with the least unique
  value: a correct "handle the last partial batch" utility is a few lines a caller can trivially write
  themselves, and it is the least CV-specific of the three ROADMAP-named candidates.
- **Duplicate/similarity grouping** — the underlying semantic question (what does "a group" mean when
  similarity is not transitive — see `find_similar_image_pairs`'s own explicit non-transitivity
  documentation) remains unresolved, and no new evidence appeared after `0.4.0a1` to change that.
- **Incremental manifest rebuild / freshness** — no correct first slice exists without leaning on a
  freshness heuristic (mtime/size) that cannot actually guarantee correctness, which this project's own
  audit explicitly refused to accept as a substitute for a real guarantee.
- **Indexed/subquadratic similarity search, parallel manifest building** — no benchmark or real-world
  report demonstrates that the existing `O(n^2)` search or sequential build is an actual bottleneck for
  any real user; both remain explicitly evidence-gated, not evidence-supported, candidates.
