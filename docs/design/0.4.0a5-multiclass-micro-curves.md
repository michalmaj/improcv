# Design: micro-averaged multiclass ROC and precision-recall curves (`0.4.0a5` first slice)

Status: design only. Not implemented, not released.

## 1. User problem

```text
improcv already computes multiclass_roc_auc_score(..., average="micro")
and multiclass_average_precision_score(..., average="micro") -- one
scalar summarizing the flattened one-vs-rest ranking problem. It does
not expose the curve that scalar is the area under. A caller who wants
to inspect or plot that curve has no public route to it: they would
have to re-derive the private flattening (_flatten_multiclass_ovr)
from scratch -- getting the C-order raveling and, in particular, the
np.repeat (not np.tile) sample-weight expansion exactly right -- purely
to reach a curve improcv already knows how to build internally.
```

This is not primarily an argument from API symmetry. `improcv.evaluation` already ships the
per-class curve family (`multiclass_roc_curve`/`multiclass_precision_recall_curve`, `0.4.0a3`)
alongside the per-class/macro/weighted/micro scalar family (`multiclass_roc_auc_score`/
`multiclass_average_precision_score`). Micro-averaged ROC/PR curves are a standard technique in
their own right -- used specifically when a single, global operating-point curve is wanted for an
imbalanced multiclass problem, independent of whether per-class curves happen to exist. What makes
this worth doing *now*, rather than a hypothetical future release, is that the underlying
computation is fully resolved today (unlike macro/weighted curves, §33) and reuses an existing,
already-shared, already-tested private helper with zero new type or signature risk (§4, §9).

Frozen central invariant this design exists to specify precisely, not just implement:

```text
C-order flattening
binary target construction
sample-weight expansion (np.repeat, not np.tile)
positive-label convention (always 1, a flattening artifact)
reuse of existing binary curve semantics (roc_curve/precision_recall_curve unchanged)
```

Evidence level: ROADMAP item / maintainer design-doc note (`ROADMAP.md`, `docs/design/
0.4.0a3-multiclass-curves.md` §13) -- external evidence is zero, stated plainly, not inflated.

```python
multiclass_roc_curve_micro
```

## 4. Exact signatures and return types

```python
def multiclass_roc_curve_micro(
    y_true: Sequence[int] | npt.NDArray[np.integer],
    y_score: npt.NDArray[np.floating] | npt.NDArray[np.integer],
    *,
    labels: Sequence[int] | npt.NDArray[np.integer],
    sample_weight: Sequence[float]
    | npt.NDArray[np.floating]
    | npt.NDArray[np.integer]
    | None = None,
) -> RocCurve: ...


def multiclass_precision_recall_curve_micro(
    y_true: Sequence[int] | npt.NDArray[np.integer],
    y_score: npt.NDArray[np.floating] | npt.NDArray[np.integer],
    *,
    labels: Sequence[int] | npt.NDArray[np.integer],
    sample_weight: Sequence[float]
    | npt.NDArray[np.floating]
    | npt.NDArray[np.integer]
    | None = None,
) -> PrecisionRecallCurve: ...
```

Return types are the **existing** `RocCurve`/`PrecisionRecallCurve` types -- not
`MulticlassRocCurve`/`MulticlassPrecisionRecallCurve`. This is not a shortcut; it is the honest
representation of what micro-averaging produces: flattening collapses the multiclass structure
into exactly one binary ranking problem, so the result *is* one binary curve, not a
multiclass-shaped container holding one curve. No `average=`, `positive_label=`, `grid=`, or
`interpolation=` parameter is added to either signature -- "micro" is each function's entire,
fixed purpose, exactly the same reasoning that already gives `multiclass_roc_curve` no `average`
parameter (`evaluation.py`, `multiclass_roc_curve`'s own docstring: *"There is no `average`
parameter: this always returns the full per-class collection... no micro curve in this function...
a separate, later API decision"*) -- this document is that later decision, exercised as two new
functions, not as a parameter on the existing ones (§32).

## 5. Why separate functions, not `average="micro"` on the existing curve functions

Three concrete reasons, not a stylistic preference:

1. **Avoids changing a shipped signature.** `multiclass_roc_curve`/`multiclass_precision_recall_
   curve` are already public, already released (`0.4.0a3`). Adding a parameter to them is a
   signature change to shipped API, which this slice does not need in order to deliver the value.
2. **Avoids a union return type.** `multiclass_roc_curve` returns `MulticlassRocCurve` today.
   Making it conditionally return `RocCurve` instead for `average="micro"` would require widening
   its return annotation to a union and re-deriving `@overload` branches on a function that
   already has real callers -- unnecessary risk for an additive feature.
3. **Avoids touching per-class support validation.** The existing per-class curve functions
   unconditionally require positive effective support for *every named label*
   (`_compute_effective_class_support`, called unconditionally in both `multiclass_roc_curve` and
   `multiclass_precision_recall_curve`). Micro-averaging explicitly does **not** need this (§10).
   Threading a micro branch through the existing functions would mean either running that
   unnecessary check anyway (wrong, wastes work and rejects legal micro inputs) or forking
   validation behavior inside one function based on a parameter value (a worse contract than two
   functions each with one behavior).

This document freezes only that **this `0.4.0a5` slice does not add `average=` to the existing
curve functions.** It does not attempt to bind a future maintainer decision permanently; it simply
does not add that parameter here, and does not need to for this slice's value to stand on its own.

## 6. Labels semantics

`labels` is explicit, required, never inferred from `y_true`, and never sorted -- identical
semantics to every other multiclass function in this module (`_normalize_explicit_labels` is
reused unchanged). `y_score`'s column order follows `labels`' own order when constructing the
one-hot target during flattening (§8): column `j` corresponds to `labels[j]`, in exactly the order
given. Because the micro result is a single flattened binary curve, `labels`' original order and
identity are **not** preserved in the return value in any form: `RocCurve.positive_label`/
`PrecisionRecallCurve.positive_label` is always the literal `1` (§15), never one of the caller's
original multiclass labels, and no `labels`/`original_labels` field is added to either result type
(§22).

## 7. Minimum labels and `y_true`

Verified directly against the current code (identical wording appears, unchanged, in all four
existing multiclass functions -- `multiclass_roc_auc_score`, `multiclass_average_precision_score`,
`multiclass_roc_curve`, `multiclass_precision_recall_curve`):

```python
labels_tuple = _normalize_explicit_labels(labels)     # -> ValueError "labels must not be empty"
                                                        # -> ValueError "labels must not contain
                                                        #    duplicate values"
if len(labels_tuple) < 2:
    raise ValueError("multiclass ranking scores require at least 2 labels")

true_list = _normalize_label_sequence(y_true, "y_true")
if len(true_list) == 0:
    raise ValueError("y_true must not be empty")
```

Frozen for both new functions, reusing these exact existing helpers and exact existing message
strings, not a weaker or different minimum inherited accidentally from `_flatten_multiclass_ovr`
itself (that private helper performs no validation of its own -- it assumes already-validated
inputs, per its own body). Concretely: **0 labels is invalid, 1 label is invalid, 2+ labels is
eligible**, subject to the remaining checks below.

## 8. Exact flattening semantics

`_flatten_multiclass_ovr(true_list, labels_tuple, score_matrix, weights)` (`evaluation.py`) is
reused **unchanged**, by direct call -- see §9 for why no modification is needed.

Frozen contract, quoted from its own docstring and confirmed by direct empirical test (a 7-sample,
3-class case with a zero-weight row) against the real function:

- **Binary target**: a dense `(n_samples, n_classes)` one-hot matrix, flattened in C-order. Flat
  cell `i * n_classes + j` is `1` (positive) iff `true_list[i] == labels_tuple[j]`, else `0`
  (negative) -- exactly one positive cell per sample row, `n_classes - 1` negative cells.
- **`flat_true`**: `np.int64`, shape `(n_samples * n_classes,)`.
- **`flat_score`**: `score_matrix.ravel(order="C")` -- a **view**, not a copy, since
  `_normalize_score_matrix` already guarantees C-contiguity.
- **Sample-weight expansion**: `np.repeat(weights, n_classes)`, confirmed **not**
  `np.tile(weights, n_classes)`, verified both by reading `_flatten_multiclass_ovr`'s own comment
  and by direct execution: `np.repeat([w0, w1, w2], 3)` gives `[w0, w0, w0, w1, w1, w1, w2, w2,
  w2]` -- a sample's single weight applies identically to every one of the `n_classes` cells that
  sample contributes, matching the C-order layout above. (`np.tile` would instead match an
  F-order/class-major flatten, which this is not.)

## 9. `_flatten_multiclass_ovr` reuse decision

**No helper-contract change is required.** The existing function already returns exactly
`(flat_true, flat_score, flat_weight)`, ready to feed directly into `roc_curve`/
`precision_recall_curve` the same way `multiclass_roc_auc_score`/`multiclass_average_precision_
score` already feed it into `roc_auc_score`/`average_precision_score`. It is called identically
(same arguments, same order) by both existing score functions today, so it is already proven to be
shared safely by two callers; a third and fourth caller (the two new curve functions) add no new
requirement on it. `_flatten_multiclass_ovr` is **not** made public, and its visibility is
**unchanged** -- both new public functions call it as an internal implementation detail, exactly
as the two existing public score functions already do.

## 10. Effective-support semantics: micro vs. per-class curves

This is the central behavioral difference from the already-shipped per-class curve functions.

`multiclass_roc_curve`/`multiclass_precision_recall_curve` call `_compute_effective_class_support`
**unconditionally**, requiring every named label to have positive effective support before any
curve is built. The two new micro functions must **not** copy this check. Verified directly from
`multiclass_roc_auc_score`'s own docstring, which already states the identical rule for the
existing micro *score* path (reused verbatim as the frozen rationale here, since the flattening is
byte-for-byte the same operation):

> "`average="micro"` does *not* require per-class effective support -- a class absent from
> `y_true` (or present only in zero-weight rows) contributes purely negative cells to the flattened
> problem below, which is mathematically well defined as long as `y_true` is non-empty, `labels`
> has at least 2 entries, and every `y_true` value is one of `labels` (all already required
> unconditionally above); a single effectively present class is likewise legal for `"micro"`."

The reason, stated precisely: **the flattened binary problem, not any individual original class,
is the unit of support validation for micro.** A class with zero effective support still
contributes real negative cells to the flattened array; it does not need its own positive support
to make the flattened ROC/PR computation well-defined.

## 11. Flattened-problem support requirements (ROC vs. PR differ -- verified, not assumed)

Read directly from `roc_curve`/`precision_recall_curve`'s own current contracts, which the
flattened call inherits unchanged (`positive_label=1` on the flattened arrays):

- **`roc_curve`** requires **at least one effective positive AND at least one effective negative**
  sample, or raises `ValueError` (its own docstring: *"Requires at least one positive sample...
  and at least one negative sample -- with either missing, FPR or TPR would be an undefined
  `0/0`"*).
- **`precision_recall_curve`** requires **only at least one effective positive** sample; a `y_true`
  with zero effective negatives is legal (precision is `1.0` at every real threshold) -- explicitly
  *not* the same requirement as ROC (its own docstring: *"unlike `roc_curve`, a `y_true` with no
  (effective) negative sample is legal"*).

**Both requirements are structurally guaranteed to already hold for the flattened problem**, given
only the unconditional checks already performed before flattening (`labels_tuple` has ≥2 entries,
`true_list` is non-empty, and -- when `sample_weight` is given -- `_normalize_sample_weight`
already guarantees at least one strictly positive weight). Proof, and independently confirmed by
direct execution on a synthetic example:

- Effective positive count in the flattened array = the number of effectively-present original
  samples (each contributes exactly one positive cell). This is `len(true_list)` when
  `sample_weight` is `None` (already guaranteed ≥1, since `y_true` must be non-empty), or the
  count of samples with strictly positive weight when `sample_weight` is given (already guaranteed
  ≥1 by `_normalize_sample_weight`'s own "at least one positive value" requirement). **Empirically
  confirmed**: a 7-sample/3-class/1-zero-weight-row test case produced exactly 6 effective
  positive flattened cells, matching the 6 non-zero-weight input samples exactly.
- Effective negative count in the flattened array = (effective positive count) × `(n_classes - 1)`,
  since every effectively-present sample contributes exactly `n_classes - 1` negative cells
  alongside its one positive cell. This is zero only if `n_classes == 1` (impossible, `labels`
  requires ≥2) or the effective positive count is zero (already shown impossible above).
  **Empirically confirmed**: the same test case produced exactly `6 * 2 = 12` effective negative
  flattened cells.

Consequently: **`roc_curve`'s own positive/negative-support check on the flattened array is a
second line of defense that is never expected to trigger, exactly the same relationship
`multiclass_roc_curve` already documents for its own per-class case** ("`roc_curve`'s own per-class
negative-support check remains in place as a second line of defense but is never expected to
trigger here"). `precision_recall_curve`'s single positive-support requirement is likewise always
satisfied by construction and never expected to trigger.

## 12. Zero-weight and degenerate-weighting semantics

- **Zero-weight rows**: removed from the flattened problem entirely, via the same weight-repetition
  mechanism (§8) -- a zero-weight original sample contributes `n_classes` zero-weight flattened
  cells, which `roc_curve`/`precision_recall_curve`'s own existing weighted path already treats as
  "removed before thresholds are built" (their shared documented behavior, unchanged, reused here).
- **A class with no effective support after weighting**: legal for micro (§10) -- it simply
  contributes no positive flattened cells for that class's column, only negative ones.
- **A single effective original class after weighting**: legal for micro (§10, explicitly named in
  `multiclass_roc_auc_score`'s own docstring: *"a single effectively present class is likewise
  legal for `"micro"`"*).
- **All-zero `sample_weight`**: already rejected unconditionally by `_normalize_sample_weight`
  ("`sample_weight` must contain at least one positive value") **before** flattening is ever
  reached -- this is existing, shared, unmodified behavior, not a new rule.
- **No per-class effective-support precheck does not mean the flattened binary problem can be
  degenerate.** §11 proves it structurally cannot be, given the checks already performed; this is
  stated explicitly so the absence of a precheck is not mistaken for an absence of any guarantee.

## 13. Non-finite value semantics

No new policy. `_normalize_score_matrix` and `_normalize_sample_weight` (via
`_normalize_nonnegative_weight_sequence`) already reject NaN/Inf **unconditionally, before
flattening is reached at all** -- regardless of which row or class a non-finite value belongs to,
and regardless of that row's own weight (a NaN in a zero-weight row is rejected exactly the same
as a NaN in a nonzero-weight row, since finiteness is checked over the whole array before any
weight-based removal happens). Both new functions reuse these exact existing normalization
functions unchanged, so this policy is inherited verbatim, not reinvented.

## 14. Validation order (frozen, verified against the current code)

Identical opening sequence to all four existing multiclass functions (confirmed by direct reading
of `multiclass_roc_auc_score`, `multiclass_average_precision_score`, `multiclass_roc_curve`,
`multiclass_precision_recall_curve` -- all four perform these same six steps, in this same order,
before diverging):

```text
1. labels_tuple = _normalize_explicit_labels(labels)
   -> TypeError (wrong container type) / ValueError ("labels must not be empty",
      "labels must not contain duplicate values")
2. if len(labels_tuple) < 2: ValueError ("multiclass ranking scores require at least 2 labels")
3. true_list = _normalize_label_sequence(y_true, "y_true")
   -> TypeError / ValueError (container/dtype issues)
4. if len(true_list) == 0: ValueError ("y_true must not be empty")
5. membership: for each y_true value not in labels_tuple:
   ValueError (f"y_true[{index}] = {value} is not present in labels")
6. score_matrix = _normalize_score_matrix(y_score, len(true_list), len(labels_tuple))
   -> TypeError / ValueError (shape, dtype, NaN/Inf)
7. weights = _normalize_sample_weight(sample_weight, len(true_list)) if sample_weight is not None
   -> TypeError / ValueError (container/dtype/length/negative/all-zero)
8. flat_true, flat_score, flat_weight = _flatten_multiclass_ovr(
       true_list, labels_tuple, score_matrix, weights)
9. delegate to roc_curve(flat_true, flat_score, positive_label=1, sample_weight=flat_weight)
   or precision_recall_curve(...) -- ValueError from this step is caught and re-raised with
   micro-specific context (§19)
10. return the resulting RocCurve/PrecisionRecallCurve directly (no wrapper-level postcondition
    beyond what roc_curve/precision_recall_curve already check on themselves)
```

Step 9 does **not** call `_compute_effective_class_support` (§10) -- this is the one point where
the new functions' sequence diverges from the existing per-class curve functions, which insert
that call between steps 7 and 8.

## 15. `positive_label` -- exact value and exact meaning

Both new functions produce a result with `positive_label == 1`, always -- the same fixed value
`multiclass_roc_auc_score`/`multiclass_average_precision_score`'s own micro path already uses
internally (`roc_auc_score(flat_true, flat_score, positive_label=1, ...)`).

**Precise meaning, to be carried into the implementation's docstring verbatim in spirit:** `1` is
the positive label of the *derived, flattened* binary problem, not one of the caller's original
multiclass labels. It means "this flattened cell corresponds to the sample's true class" -- every
flattened cell where the one-hot target is `1`. It is not arbitrary or meaningless: it is the
well-defined positive marker of the one-hot encoding constructed in §8. It must not be interpreted
as, compared against, or confused with any value in the caller's own `labels` argument.

No new field (`original_labels`, `micro`, `average`, or otherwise) is added to `RocCurve` or
`PrecisionRecallCurve` to carry the original `labels` -- the flattened result genuinely has no
per-original-class structure left to store (§22).

## 16. ROC scalar relationship -- frozen as an exact (bit-for-bit) guarantee, verified empirically

```python
curve = multiclass_roc_curve_micro(y_true, y_score, labels=labels, sample_weight=sample_weight)
auc(curve.false_positive_rate, curve.true_positive_rate)
```

is **bit-for-bit identical** to

```python
multiclass_roc_auc_score(y_true, y_score, labels=labels, average="micro", sample_weight=sample_weight)
```

for the same legal inputs, in the same environment. This is not "numerically close" -- it is exact
equality, and this document states it as an exact equality deliberately because the underlying
implementation guarantees it structurally: both paths flatten via the same
`_flatten_multiclass_ovr`, then both delegate to the same shared binary ranking core
(`multiclass_roc_auc_score`'s micro path calls `roc_auc_score` on the flatten; `roc_auc_score` and
`roc_curve` share the same underlying ranking-core arithmetic that already gives the existing
per-class relationship `auc(curve.false_positive_rate, curve.true_positive_rate) ==
multiclass_roc_auc_score(..., average=None)[i]` its own documented bit-for-bit guarantee). This is
the same class of guarantee already shipped for the per-class curves, applied to the micro case.

**Empirically verified**, not just reasoned: on a synthetic 7-sample, 3-class, non-trivial-weight
example (one zero-weight row, non-uniform positive weights), `auc(curve.false_positive_rate,
curve.true_positive_rate) == multiclass_roc_auc_score(..., average="micro", sample_weight=...)`
evaluated to `True` under plain Python `==`, both sides equal to `0.66375`.

## 17. PR relationship -- trapezoidal area is explicitly NOT average precision

`multiclass_precision_recall_curve_micro`'s result is the precision-recall curve for the exact
same flattened binary problem `multiclass_average_precision_score(..., average="micro")`
summarizes as a scalar. **No equality is promised between a trapezoidal integration of this curve
(e.g. `auc(curve.recall, curve.precision)`) and `multiclass_average_precision_score(...,
average="micro")`.** This is not a gap in this design -- it mirrors an existing, already-documented
distinction: `average_precision_score`'s own docstring states plainly that its weighted-recall-
increment definition "is not linear interpolation and not the trapezoidal area under the PR curve,
which is a distinct quantity... depending on the shape of the curve and its ties, the trapezoidal
area can be larger or smaller than this average precision, never consistently one or the other."
The micro curve does not change this relationship; it inherits it unchanged, because both micro
average precision and the micro PR curve are computed from the same flattened arrays through the
same existing binary functions (`average_precision_score`/`precision_recall_curve`), whose own
already-shipped, already-documented non-equality applies identically here.

## 18. Direct binary-equivalence invariant (differential-test contract)

For the same legal inputs, after **independently** constructing the identical flattened arrays
(not by calling `_flatten_multiclass_ovr` itself, to keep the check a genuine, independent
oracle -- see §37):

```python
multiclass_roc_curve_micro(y_true, y_score, labels=labels, sample_weight=sample_weight)
```

must be **bit-for-bit equal** (via `RocCurve.__eq__`, i.e. `np.array_equal` on each array plus
`positive_label` equality) to

```python
roc_curve(flat_true, flat_score, positive_label=1, sample_weight=flat_weight)
```

and analogously,

```python
multiclass_precision_recall_curve_micro(y_true, y_score, labels=labels, sample_weight=sample_weight)
```

must be bit-for-bit equal to

```python
precision_recall_curve(flat_true, flat_score, positive_label=1, sample_weight=flat_weight)
```

This holds by construction (§9: the new functions call the exact same `_flatten_multiclass_ovr`
and the exact same public `roc_curve`/`precision_recall_curve`, with no intermediate
transformation), and is the central invariant the differential test plan (§37) exists to verify
against an independently-built oracle, not merely assert from the implementation's own internal
consistency.

## 19. Error-wrapping policy (frozen precisely, not just "same vocabulary")

**Validation errors raised before the flattened binary computation** (`labels`, `y_true`,
`y_score`, `sample_weight`, membership) **are the existing multiclass validation errors, used
as-is -- never repackaged, never given additional micro-specific context.** These come directly
from `_normalize_explicit_labels`/`_normalize_label_sequence`/`_normalize_score_matrix`/
`_normalize_sample_weight`, exactly as they already propagate, unmodified, from the four existing
multiclass functions.

**A `ValueError` raised by the binary computation itself** (i.e. from the `roc_curve`/
`precision_recall_curve` call on the already-validated flattened arrays -- structurally not
expected to trigger per §11, but a real code path, not dead code, exactly like the existing
per-class curve functions' own per-column error wrapping) **is caught and re-raised with
micro-specific context**, mirroring the exact existing pattern from `multiclass_roc_auc_score`'s
own micro branch:

```python
try:
    return roc_curve(flat_true, flat_score, positive_label=1, sample_weight=flat_weight)
except ValueError as exc:
    raise ValueError(f"failed to compute micro-averaged multiclass ROC curve: {exc}") from exc
```

```python
try:
    return precision_recall_curve(flat_true, flat_score, positive_label=1, sample_weight=flat_weight)
except ValueError as exc:
    raise ValueError(
        f"failed to compute micro-averaged multiclass precision-recall curve: {exc}"
    ) from exc
```

**`raise ... from exc` is used, not a bare `raise ValueError(...)`**, matching the existing style
exactly (`multiclass_roc_auc_score`'s own micro-wrapping line uses `from exc`; the module's
per-column error wrapping in the per-class curve functions also uses `from exc` throughout). No
new exception type is introduced anywhere in this design.

## 20. Existing scalar APIs remain unchanged

`multiclass_roc_auc_score`/`multiclass_average_precision_score`: **zero changes** -- signature,
return type, validation, error messages, and behavior are all frozen exactly as they exist today.
The new curve functions consume the *same underlying semantics* (the same `_flatten_multiclass_
ovr`, the same flattening definition) but do not refactor, wrap, or otherwise touch either scalar
function's own public entry point. No internal deduplication that would risk observable behavior
change is proposed; §9 already confirms the shared helper needs no modification.

## 21. Existing curve APIs remain unchanged

`multiclass_roc_curve`/`multiclass_precision_recall_curve` remain **per-class-only**. No `average=`,
`micro=`, or `include_micro=` parameter is added to either. Their return type
(`MulticlassRocCurve`/`MulticlassPrecisionRecallCurve`), validation (including the unconditional
per-class effective-support requirement, §10), and documented behavior are all unchanged by this
design.

## 22. Existing dataclasses remain unchanged

Zero changes to `RocCurve`, `PrecisionRecallCurve`, `MulticlassRocCurve`, or
`MulticlassPrecisionRecallCurve`. In particular, no `micro`, `average`, `labels`, or `metadata`
field is added to any of them. This repeats, deliberately, the exact compatibility rationale
`docs/design/0.4.0a3-multiclass-curves.md` already froze for these same types:

> "Adding a new public field to a frozen dataclass can affect: manual positional construction
> (today's single-positional/keyword-argument shape would change), the generated `repr`, the
> generated `__eq__` (a new field participates in equality unless deliberately excluded),
> `dataclasses.fields()`/other introspection, structural pattern matching (`__match_args__` grows
> to include the new field), and any caller who has made their own serialization assumptions about
> the object's current shape. Any such future addition would still need its own, separate
> compatibility review at the time it is actually proposed -- this design does not pre-approve
> one."

This is precisely why micro-averaging is delivered as two new functions returning the existing
*binary* result types, not as a new field on the existing *multiclass* result types.

## 23. Minimum class-count edge cases

Frozen, per §7:

```text
0 labels: invalid (ValueError, "labels must not be empty")
1 label:  invalid (ValueError, "multiclass ranking scores require at least 2 labels")
2 labels: eligible, subject to the remaining checks (§11-§14)
```

The micro flattening cannot be used to bypass the multiclass 2-label minimum -- that check runs
unconditionally, before any flattening logic is reached (§14, step 2).

## 24. `y_true` membership

- **`y_true` contains a label absent from `labels`**: rejected unconditionally, before flattening,
  by the existing membership loop (`ValueError`, `f"y_true[{index}] = {value} is not present in
  labels"`) -- identical to all four existing multiclass functions.
- **`labels` contains a class not present in `y_true`** (raw presence): legal. This class simply
  contributes zero positive flattened cells (all of its column's cells are negative).
- **The same class, absent after effective-support weighting** (i.e. present in raw `y_true` but
  only at zero weight): also legal, for the same reason -- distinguished explicitly from *raw*
  presence because §10/§12 already establish that effective (weighted) absence, not just raw
  absence, is tolerated for micro. Both cases are confirmed identical to the existing micro scalar
  behavior (`multiclass_roc_auc_score(..., average="micro")`), which this design reuses via the
  same flattening, not a freshly assumed policy.

## 25. `y_score` contract

Identical to the existing multiclass score-matrix contract, reused via `_normalize_score_matrix`
unchanged:

- 2-D `ndarray` only (a nested `Sequence`-of-`Sequence`s is rejected with a clear `TypeError`, not
  silently converted).
- `shape == (len(y_true), len(labels))`.
- Accepted dtypes: `float16`/`float32`/`float64`, or any integer dtype whose every element is
  exactly representable as `float64`; `bool`/complex/object/wider-than-`float64` floating dtypes
  are rejected.
- All values finite (no NaN/Inf).
- **No** probability-simplex requirement, **no** `[0, 1]` range requirement, **no** row-sum-to-`1`
  requirement -- none of these exist in the current multiclass score contract, and this design
  does not add any. (Unlike `None`/`"macro"`/`"weighted"`, which tolerate an independent strictly
  increasing transform per column, the micro path -- exactly like the existing micro scalar path --
  assumes columns share a common, comparable scale, since it compares raw values across columns
  directly after flattening; this is an existing, already-documented assumption of "micro" as a
  concept, not a new requirement this design introduces.)

## 26. `sample_weight` contract

Identical to the existing ranking `sample_weight` contract, reused via `_normalize_sample_weight`
unchanged: `None`, a `Sequence[float]` (explicitly excluding `str`/`bytes`/`bytearray`), a 1-D
floating `ndarray` (`float16`/`float32`/`float64`), or a 1-D integer `ndarray` whose every element
is exactly representable as `float64`. Non-negative; at least one strictly positive value;
length must equal `len(y_true)`.

After this existing multiclass-level normalization, one original sample's weight `w_i` is expanded
(§8) to apply identically to **all `n_classes` flattened cells that sample contributes** -- this
expansion is the *only* place `sample_weight` is touched again after normalization; there is no
second, different normalization applied after flattening that could change its semantics. The
already-validated `w_i` is simply repeated, verbatim, `n_classes` times.

## 27. Complexity (precise, not oversimplified)

```text
Flatten construction (_flatten_multiclass_ovr):
  O(N * C) time (building the one-hot target and repeating weights)
  O(N * C) additional memory for flat_true/flat_weight
            (flat_score is a view, not a copy, given C-contiguous input)

Binary curve computation (roc_curve/precision_recall_curve on the
flattened arrays):
  the existing binary ranking core's own complexity, applied over
  N * C flattened observations -- this core sorts by score, so the
  dominant term is O((N * C) log(N * C)), not O(N * C) alone.

Overall: O(N * C) to flatten + O((N * C) log(N * C)) for the binary
curve, i.e. O((N * C) log(N * C)) overall, dominated by the sort.
```

This is not simplified to a single `O(N*C)` bound for the whole function -- the binary curve's own
sort dominates for realistic `N`/`C`.

## 28. Determinism

No RNG is used anywhere in this path. Given the same validated inputs, in the same runtime
environment, both new functions are deterministic -- exactly the same guarantee already made,
unchanged, by `roc_curve`/`precision_recall_curve`/`multiclass_roc_auc_score`. The bit-for-bit
relationships in §16 and §18 hold **within the same runtime inputs/environment and shared
implementation contract** -- this design does not promise cross-version, cross-build, or
cross-platform floating-point bit identity beyond whatever the existing binary/scalar functions
already promise (which is: none beyond within-environment determinism).

## 29. Mutation

Neither function mutates `y_true`, `y_score`, `sample_weight`, or `labels`. This already follows
from reusing `_normalize_explicit_labels`/`_normalize_label_sequence`/`_normalize_score_matrix`/
`_normalize_sample_weight` unchanged, all of which already return new, independent arrays/lists
without touching their inputs (verified in their own docstrings, e.g. `_normalize_score_matrix`:
*"The input is never mutated, and the returned array never aliases it"*). The future implementation
PR's test plan must include explicit no-mutation assertions (§36) as a regression guard, not merely
rely on this transitive guarantee.

## 30. Module placement

Both new functions are added to the existing `src/improcv/evaluation.py` -- no new module. This
document does not change `evaluation.__all__`, `improcv.__init__`, or the top-level `__all__`; see
§42 for the exact future placement, not executed here.

## 31. Naming review

Considered for the ROC function (analogous choices apply to the PR function):

- `multiclass_roc_curve_micro` -- **chosen**. Matches the existing `<domain>_<subject>` naming
  already used by `multiclass_roc_curve` itself, with the averaging mode appended as a suffix
  qualifier -- the same pattern `classification_metrics_from_confusion_matrix` already uses
  (appending its own qualifier rather than front-loading it).
- `micro_multiclass_roc_curve` -- rejected: breaks the existing `multiclass_roc_curve` prefix a
  reader would search for or autocomplete from; every other multiclass function in this module
  starts with `multiclass_`.
- `multiclass_roc_curve(..., average="micro")` -- rejected in §5 (existing-signature-change,
  return-type-union, and support-validation-forking risk), not chosen for stylistic reasons.

Chosen names: **`multiclass_roc_curve_micro`**, **`multiclass_precision_recall_curve_micro`**.

## 32. Scope of the "no `average=` on existing functions" freeze

This document freezes only that the `0.4.0a5` slice described here does not add an `average=`
parameter to `multiclass_roc_curve`/`multiclass_precision_recall_curve`. It does not assert that
`average="micro"` will *never* be supported on those functions as a permanent product guarantee --
that would bind a future maintainer decision this document has no authority over. What is frozen,
precisely: for this slice, "micro" is delivered exclusively as the two new, separate functions in
§3/§4.

## 33. Relationship to macro/weighted curves

Micro-averaged curves establish **no** interpolation, common-grid, or endpoint-handling semantics
for a hypothetical macro/weighted curve. Macro/weighted curves remain blocked by a genuinely
unresolved question this design does not attempt to resolve: what common threshold grid two or
more curves with different, non-aligned threshold axes would be averaged over, how duplicate
x-values on that grid are handled, and what weighting semantics apply -- none of which micro's
flatten-then-delegate approach has any bearing on, since micro never averages curve *points* at
all; it computes one curve for one already-flattened problem. No interpolation helper, shared-grid
utility, or other foundation piece for a future macro/weighted curve is introduced, sketched, or
implied by this design.

## 34. Relationship to classification report / plotting

Explicitly out of scope and untouched by this design: a structured classification-report type, a
public plotting API, confusion-matrix plotting, and ROC/PR plotting of any kind. `demos/
classification_report.py` is not modified by this design document (a future implementation PR may
choose to extend it, as a separate, later decision -- not sketched here). No report type is
introduced as a byproduct of adding the two curve functions.

## 35. Benchmark requirement

**Not required for acceptance.** The new code path composes two already-existing, already-tested
pieces (`_flatten_multiclass_ovr` and the binary `roc_curve`/`precision_recall_curve`) with no new
algorithmic complexity class beyond what's already documented in §27. Concretely: `benchmarks/
benchmark_evaluation.py` today benchmarks `confusion_matrix`, `classification_metrics`, and the
macro-averaged scalar score functions -- it does **not** benchmark even the already-shipped
per-class curve functions (`multiclass_roc_curve`/`multiclass_precision_recall_curve`) at all, so
requiring a benchmark for the micro curve variant specifically would be a new, inconsistent
standard relative to the existing curve family. A future implementation PR **may** add micro-curve
cases to the existing benchmark file for consistency, at the implementer's discretion -- this is
not a requirement, and this feature's acceptance is not gated on it.

## 36. Future test plan (not executed in this design PR)

To be written alongside the future implementation PR. At minimum:

**Public API basics**: both symbols exported (once implemented); exact signatures; exact return
types (`RocCurve`/`PrecisionRecallCurve`, never the multiclass wrapper types); `positive_label ==
1` on every successful result.

**Minimum labels**: 0 labels, 1 label, 2 labels (per §23).

**Labels**: unsorted `labels`; integer labels of varying magnitude; confirmation that `labels`'
order changes which score column is interpreted as which class during flattening; duplicate labels
rejected; an unknown `y_true` label rejected (per §7/§24).

**Score dtype**: `float16`, `float32`, `float64`, and accepted integer dtypes.

**Score memory layout**: C-contiguous, F-contiguous, and a non-contiguous slice/view input, all
producing identical results (verifying `_normalize_score_matrix`'s own explicit copy-and-relayout
guarantee is exercised correctly by the new functions).

**Weights**: `None`; floating; integer; zero-weight rows; a non-contiguous weight array.

**Effective support**: a class with zero raw support; a class zeroed out entirely by weighting;
confirmation the flattened problem's own ROC support and PR support requirements are satisfied by
construction (per §11) across these cases, not merely by coincidence in one example.

**Failure ordering**: invalid `labels`, then invalid `y_true`, then invalid `y_score`, then invalid
`sample_weight`, then (only reachable in principle, per §11) a binary-computation failure -- each
tested to fail at the expected step, per §14's frozen sequence.

**Mutation**: all four inputs (`y_true`, `y_score`, `sample_weight`, `labels`) confirmed unchanged
after the call.

## 37. Future differential test plan (no Hypothesis; not executed in this design PR)

An **independent** oracle, deliberately not calling `_flatten_multiclass_ovr` itself (to keep the
check genuinely independent, not circular): construct the one-hot binary target matrix, the
C-order `flat_true`/`flat_score`, and the repeated `sample_weight` by hand, using different code
from the implementation under test, then compare:

```text
multiclass_roc_curve_micro(...) == roc_curve(flat_true, flat_score,
    positive_label=1, sample_weight=flat_weight)

multiclass_precision_recall_curve_micro(...) == precision_recall_curve(flat_true, flat_score,
    positive_label=1, sample_weight=flat_weight)
```

using each result type's own `__eq__` (array-value equality, not identity).

Minimum future sweep: **at least 3000 deterministic multiclass cases**, fixed seed, covering
combinations of: sample count `N`, class count `C`, `labels` order, score dtype, score memory
layout, `sample_weight` dtype, and the presence of zero weights. The report must distinguish
**generated multiclass cases** from **ROC comparisons** and **PR comparisons** separately -- one
multiclass case produces one ROC comparison and one PR comparison (two curve calls), which must
not be double-counted as two "cases."

## 38. Future scalar-relationship test plan

**ROC**: for every legal differential case (§37), `auc(micro_curve.false_positive_rate,
micro_curve.true_positive_rate)` must equal `multiclass_roc_auc_score(..., average="micro")`
**exactly** (`==`), not `np.isclose`/`allclose` -- per §16's frozen exact guarantee.

**PR**: no trapezoidal-equals-AP test is written (per §17, that equality is explicitly not
promised). Instead: `multiclass_precision_recall_curve_micro(...)` is compared against the
independent flattened oracle's own direct `precision_recall_curve(flat_true, flat_score,
positive_label=1, sample_weight=flat_weight)` call (§37), and, separately,
`multiclass_average_precision_score(..., average="micro")` is compared against a direct
`average_precision_score(flat_true, flat_score, positive_label=1, sample_weight=flat_weight)` call
on the same independently-built flatten -- this second comparison exercises the *existing* scalar
function's own already-documented exact relationship to the flattened binary problem, verified
fresh rather than assumed, since it is directly relevant evidence for why the new curve function's
own analogous relationship (§18) is trustworthy.

## 39. Future validation-differential plan

A future implementation PR should compare error behavior of the two new functions against the
existing scalar micro functions (`multiclass_roc_auc_score`/`multiclass_average_precision_score`,
`average="micro"`) for the same invalid multiclass inputs: invalid `labels`, invalid `y_true`,
invalid `y_score`, invalid `sample_weight`, membership violations, shape mismatches, non-finite
values. Validation **before** flattening (§14, steps 1-7) is shared, reused code and must produce
identical error text to the existing scalar functions for the same bad input, since both call the
same normalization helpers. A binary-computation failure (§11, structurally not expected to
trigger) is **not** required to produce an identical final message to the scalar functions' own
micro-wrapping text, since each new function adds its own micro-curve-specific context (§19) --
only the *shared, pre-flattening* validation is required to match.
