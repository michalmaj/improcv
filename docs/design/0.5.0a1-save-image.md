# Design: `save_image` (`0.5.0a1` first slice)

Status: design only. Not implemented, not released.

## 1. Status / scope

This is the first feature slice of the `0.5.0` line. A fresh, skeptical product audit
(2026-08-15, this development line) selected exactly one candidate that cleared the public-API-
density gate: a Unicode-safe single-image write primitive, `save_image` — the direct write-side
counterpart to `load_image` (`0.4.0a4`).

This document freezes the exact contract before any implementation. It is normative: an
implementation PR must not silently redefine anything frozen here. If empirical evidence during
implementation contradicts a decision below, that is a STOP condition (§25), not something to
route around quietly.

The design **downgrades** the naively-symmetric premise in one material way (§7): full delegation
of dtype/channel acceptance to `cv2.imencode` is **not** adopted, because direct experimentation
(§2) found it silently corrupts data for realistic inputs. The public-symbol budget still holds:
one function, zero new types.

## 2. Product rationale and current repository evidence

The owned invariant is narrow and precise:

> Encode image bytes through OpenCV **in memory**, then cross the filesystem path boundary
> through Python's own Unicode-capable path/file APIs — **never** by passing the destination
> filename to `cv2.imwrite`.

This is not "symmetry with `load_image`" as a goal in itself. It is the same class of bug,
independently verified to exist on the write side:

- `src/improcv/dataset.py`'s own shipped docstring already asserts, as established fact (not
  speculation introduced by this design): *"`cv2.imwrite` are not reliable for paths containing
  characters outside the active code page"* on Windows — the exact class of limitation
  `load_image` was built to fix for reads.
- A fresh sweep of `examples/`+`demos/` (`rg 'cv2\.imwrite|cv2\.imencode'`) found **5** real image-
  write call sites. **4 of 5** use plain `cv2.imwrite` directly:
  `examples/image_similarity_manifest.py`, `demos/pairing_diagnostics.py`,
  `examples/discovery_and_augmentation.py`, `examples/image_similarity.py`. The **5th**,
  `examples/dataset_manifest_builder.py`, already hand-rolls the exact fix this design proposes
  to centralize (`cv2.imencode(".png", pixels)` + `Path.write_bytes(...)`), with a docstring
  explaining *why*: its dataset root name (`żółw-dataset`) contains non-ASCII characters. This is
  concrete, already-shipped evidence that (a) the underlying bug is real, and (b) the safe
  workaround is non-obvious enough that 4 of 5 sibling examples do not use it.
- `io.py`'s own module docstring and `0.4.0a4-load-image.md` §13 explicitly named the module
  `io.py` (not `loading.py`) *because* a future `save_image` was anticipated as the natural write-
  side counterpart crossing the same filesystem boundary.

`improcv` should own this because: cross-platform filename-encoding behavior is inconsistent
otherwise (OpenCV's own C++ file-opening code path is shared between `imread`/`imwrite` and uses
the same non-Unicode-safe API on Windows for both), and the library has already fixed this exact
bug class once, in the same module, for the opposite direction.

## 3. Exact public API

```python
def save_image(path: str | os.PathLike[str], image: Image) -> None: ...
```

- Module: `src/improcv/io.py` (already hosts `load_image`/`ImageReadMode`; no new module).
- No keyword-only parameters in this slice. No default values to freeze beyond "none exist."
- Public-symbol budget: **1 new function, 0 new types** — matches the product audit's budget
  exactly.

Explicitly **not** added: `ImageWriteMode`, `ImageWriteOptions`, an encoder/writer object, a
result dataclass, a batch API, or any alias/synonym. See §22 for why no write-mode `Literal` is
introduced merely because `ImageReadMode` exists.

## 4. Path contract

**Decision: reuse `io.py::_normalize_path` unchanged.** `save_image` and `load_image` cross the
identical filesystem-path boundary in the same module; there is no semantic reason for the two
functions to accept a differently-typed `path`. This design does not modify `_normalize_path`.

Verified behavior (`Path.write_bytes()`, the write-side counterpart to `load_image`'s
`Path.read_bytes()`), freshly tested in a throwaway script, not assumed:

| Input | Behavior |
|---|---|
| `str` | Accepted. |
| `pathlib.Path` | Accepted. |
| `os.PathLike[str]` | Accepted (via `os.fspath()`, exactly as `_normalize_path` already does). |
| bare `bytes` / a `PathLike` whose `__fspath__()` returns `bytes` | Rejected — `TypeError`, identical to `load_image`'s existing message (`_normalize_path` is reused unchanged). |
| empty string | Rejected — `ValueError`, identical to `load_image`'s existing message. |
| relative path | Accepted, never resolved/made absolute — verified `Path("relative_test_file.png").is_absolute()` is `False` and stays that way; matches `load_image`'s "never resolved, expanded, or made absolute" contract. |
| absolute path | Accepted, used exactly as given. |
| symlink destination | **Writes through to the symlink's target** — verified directly (`os.symlink` to a target file, then `Path.write_bytes()` on the link path modifies the target's content). This is `Path.write_bytes()`'s own ordinary semantics; `save_image` performs no symlink-specific handling, mirroring `load_image`'s own "ordinary symlink-following semantics" policy exactly. |
| directory destination | `IsADirectoryError` (verified on this platform) — a native `OSError` subtype, propagates unchanged (§10). Per the existing project precedent for `load_image`'s own read-side testing, the exact `OSError` subtype at this call site may differ on Windows (`load_image`'s own test suite already tolerates this platform difference for the analogous read-side case; `save_image`'s test plan, §16, must do the same rather than assert one exact exception type). |
| missing parent directory | `FileNotFoundError` (verified directly) — propagates unchanged. |
| NUL-containing string | **Not pre-validated by `save_image`.** Verified directly: Python's own `Path.write_bytes()` raises `ValueError: embedded null byte` natively, *before* any improcv code needs to check for it — exactly matching why `_normalize_path` (reused unchanged, §4) does not pre-check for NUL on the read side either. No new validation is added for this case. |
| existing regular file | **Silently overwritten** — verified directly (`write_bytes()` called twice on the same path replaces the content). This directly informs the overwrite decision (§8). |

## 5. Format-selection contract

**Decision: the destination's `Path(path).suffix` (the *last* suffix component, with its leading
dot) is passed directly as `cv2.imencode`'s `ext` argument. No hardcoded extension allowlist.**

Verified directly against the installed OpenCV build (5.0.0):

- `Path.suffix` already returns only the last suffix component for multi-dot names (verified:
  both `"photo.backup.png"` and `"archive.tar.png"` encode successfully as PNG — `cv2.imencode`
  and `Path.suffix` agree on "the extension is whatever follows the last dot").
- Extension matching is case-insensitive (verified: `.PNG`/`.Png` both succeed identically to
  `.png`).
- A leading dot is required by `cv2.imencode` itself (verified: passing `"png"` without a leading
  dot raises `cv2.error: could not find encoder for the specified extension` — the *same* failure
  path as a genuinely unknown extension).
- An empty suffix (`Path("photo").suffix == ""`, i.e. no extension at all), an unrecognized
  extension (`.xyz`), and a missing leading dot all raise `cv2.error` with the identical message
  shape (`could not find encoder for the specified extension...`) — there is no separate `ok=False`
  path for this failure mode (verified directly, see §6).
- Widely-supported extensions verified to succeed on this build without any improcv-side special
  casing: `.png`, `.jpg`, `.jpeg`, `.tif`, `.tiff`, `.bmp`, `.webp`.

No allowlist is hardcoded because codec availability is a property of the installed OpenCV build,
not something `improcv` can promise uniformly (mirroring `load_image`'s own §15 "format and
extension behavior" stance: decode/encode capability is delegated to OpenCV's own codec set,
never independently re-implemented or promised beyond what the installed build actually
supports).

## 6. Encode failure semantics

**Decision: any encode failure — whether `cv2.imencode` raises `cv2.error` or returns
`(False, ...)` — is mapped to `ValueError` naming the destination path, with `raise ... from exc`
when a native `cv2.error` was caught.** This exactly mirrors `load_image`'s own decode-failure
mapping (`cv2.imdecode` raising `cv2.error` *or* returning `None` are both mapped to the same
`ValueError`).

Verified directly, across every failure case actually reproduced in this build (unsupported/
missing extension, 2-channel input, 5-channel input, zero-sized input): **every failure raised
`cv2.error`; `ok=False` was never observed** in this build (5.0.0). `ok=False` is still defended
against in the implementation (mirroring how `load_image` still checks `decoded is None` even
though `cv2.imdecode` failures were likewise observed to raise, not return `None`, for most
tested cases) — this must be re-verified against the floor build (OpenCV 4.9.0.80) during
implementation, not assumed identical, per this project's own standing practice of testing
against the actual floor version rather than assuming newer-build behavior generalizes downward.

## 7. Dtype/channel policy — the material downgrade from the naive premise

**The originally-provisional "Option B: full delegation to `cv2.imencode`" default does NOT
hold.** Direct experimentation found it produces a **silently successful, silently corrupted**
result for realistic inputs:

| Input | `cv2.imencode(".png", ...)` result | Round-tripped content |
|---|---|---|
| `float32` array, value `0.5` | `ok=True` (no exception, no visible failure) | Decodes back as `uint8`, value `0` — **the actual float data is silently discarded**, replaced with a meaningless downcast. |
| `uint16` array (PNG) | `ok=True`, **and** genuinely preserves the 16-bit value | Correct — PNG's own uint16 support is real and lossless here. |
| `uint16` array (JPEG) | `ok=True` (no exception) | Decodes back as `uint8`, silently clamped/truncated — **silent corruption**, not merely "delegated OpenCV behavior." |
| 1-D `uint8` array, shape `(8,)` | `ok=True` | Silently reinterpreted as a `(1, 8)` single-row image — the caller's array shape is not what gets encoded. |
| 0-D `uint8` scalar | `ok=True` | Silently "succeeds" on a nonsensical input. |
| Non-contiguous `uint8` array | `ok=True`, content verified byte-identical to a contiguous copy | **Safe to delegate** — no corruption, no special-casing needed. |

A caller passing, say, `load_image(path, mode="unchanged")`'s output (which may be `uint16` or
another non-`uint8` dtype per `load_image`'s own documented contract) straight into
`save_image(dest, image)` targeting a destination whose extension happens to route to a codec
that does not support that depth would get **no exception at all** and a silently corrupted file
— a materially misleading public contract, not a thin, honest delegation.

**Decision: narrow rejection, not conversion.** `save_image` validates two properties before
encoding, reusing **already-existing, already-pervasively-used shared internal validators** —
no new validation code, no new policy is invented:

```python
require_image_ndim(image, ndims=(2, 3))   # already used by "every public function" (its own docstring)
require_dtype(image, (np.uint8,), "image")
```

- `require_image_ndim(image, ndims=(2, 3))` (`_validation.py`) already rejects the 1-D and 0-D
  traps directly, and already rejects an empty array (`image.size == 0`) — this is the *same*
  function `restoration.py`, `regions.py`, and others already call for exactly this purpose; it
  is not written for this design.
- `require_dtype(image, (np.uint8,), "image")` (`_validation.py`) restricts accepted input to
  `uint8` — the **one** dtype verified safe across every codec tested in this build (PNG, JPEG,
  TIFF, BMP, WebP all handle `uint8` correctly with no silent fallback observed). This is a
  **rejection gate**, not a conversion: nothing is cast, clipped, or normalized. A `uint16`/
  `float32` caller gets a clear `TypeError` naming the accepted dtype, not a silently wrong file.
- Channel count (2-channel, 5-channel, etc.) is **not** separately pre-validated: `cv2.imencode`
  itself already raises `cv2.error` for these (verified directly), which the encode-failure
  mapping (§6) already converts to a clear `ValueError`. Adding a redundant improcv-side channel
  check would duplicate OpenCV's own already-adequate rejection for no added clarity.
- `(H, W, 1)` is accepted identically to 2-D grayscale (verified directly) — no special-casing
  needed; `require_image_ndim`'s `ndims=(2, 3)` already permits both, and OpenCV encodes both
  identically.

This keeps the contract small: **two lines, both reusing existing shared validators**, not a new
image-normalization/conversion layer (§25's STOP condition 9 does not apply — nothing is
converted; unsafe inputs are rejected, not silently coerced). `uint16`/`float`-format support
(e.g. 16-bit PNG, which *is* genuinely lossless per the table above) may be added later,
compatibly, as this project's own established pattern already does elsewhere (`create_dnn_blob`'s
`output_dtype` deferral, `0.4.0a4-load-image.md`'s own precedent of shipping a deliberately
narrow first slice) — not attempted in this slice, since it would require a real per-format
dtype-compatibility policy this design explicitly declines to invent now.

## 8. Overwrite decision

**Decision: Option A — ordinary writer semantics. No `overwrite` parameter in this slice.**
`save_image(path, image)` overwrites an existing regular file, exactly like `cv2.imwrite`,
`Path.write_bytes()` (verified directly: calling it twice on the same path replaces the content),
and the existing repository workaround in `examples/dataset_manifest_builder.py` (which performs
a plain, unconditional `Path.write_bytes(encoded.tobytes())` with no no-clobber check).

`PerceptualHashManifest.save()`'s `overwrite=False` default is **not** adopted here (§9
explicitly forbids copying it automatically). That default exists because a manifest is a
curated, hand-meaningful snapshot where accidental overwrite has real narrative cost. A single
processed/generated image does not carry the same "accidental data loss of a curated artifact"
risk profile, and there is zero repository evidence of demand for no-clobber image-write
semantics — every existing write call site (`cv2.imwrite`, the manual `dataset_manifest_builder.py`
pattern) already overwrites unconditionally. Freezing `overwrite=False` now would add a permanent
contract dimension with no evidence behind it.

## 9. Atomicity decision

**Decision: Option A — no atomicity guarantee.** `save_image` fully encodes the image in memory
*before* touching the destination path (`cv2.imencode` runs first; `Path.write_bytes()` is called
only with the complete, already-encoded byte buffer). This guarantees an **encode failure never
touches the destination at all**. It does **not** guarantee that a filesystem-level write failure
(disk full, process killed mid-write) leaves an existing destination file unchanged — `Path.
write_bytes()` itself provides no such guarantee, and neither does `cv2.imwrite`.

`manifest.py`'s temp-file + `fsync` + atomic-rename machinery (`_write_temp_manifest_file`,
§23) is **not** imported into this design. That machinery exists for a text-mode JSON snapshot
where partial-write corruption on crash is a real, previously-considered risk for a
should-be-durable artifact. There is no repository evidence of equivalent demand for images, and
importing that machinery would substantially enlarge this feature's contract (temp-file naming,
permissions, same-directory-publish requirements, cleanup-on-failure semantics) for a benefit
nothing in this audit found evidence for. Atomic image writes are an explicit non-goal (§14).

## 10. Filesystem failure semantics

**Decision: native `OSError` subclasses propagate unchanged** — never wrapped into `ValueError`.
Verified directly: `FileNotFoundError` for a missing parent directory, `IsADirectoryError` for a
directory destination (platform-dependent exact subtype, per §4's table), `ValueError` (native,
from Python's own path-encoding layer, not improcv code) for an embedded NUL byte. This exactly
mirrors `load_image`'s own read-vs-decode split: a filesystem-level problem is a categorically
different failure mode from an encode-level problem, and gets a categorically different (native,
unwrapped) exception family.

## 11. Unicode / Windows strategy

The structural guarantee, not a per-platform patch: **`cv2` never receives a filename in this
implementation, on any platform.** `cv2.imencode`'s first argument is a short extension *string*
(e.g. `".png"`), never a path; the actual filesystem write happens entirely through
`Path.write_bytes()`, which is CPython's own Unicode-capable path API (the same one `load_image`
already relies on for reads via `Path.read_bytes()`). Because OpenCV's filename-based
Windows-code-page limitation can only manifest when a *path* reaches OpenCV's own C++ file-opening
code, and this design never does that, the failure mode this feature exists to prevent is
**structurally impossible**, not merely "usually avoided."

Per this task's own explicit guidance (§18): the test plan does **not** need to reproduce
`cv2.imwrite`'s own failure on a specific Windows/OpenCV/code-page combination (that behavior is
already documented in this project as unreliable, not guaranteed to fail identically everywhere).
The regression test instead verifies the **positive** contract: a `save_image` call to a path
containing non-ASCII characters succeeds and produces byte-correct content, on every CI platform
including Windows — proving the feature *works*, not that the bug it avoids is reproducible on
demand.

## 12. Byte-level oracle

**Primary oracle (mandatory, not a generic round-trip check):**

```python
expected = cv2.imencode(suffix, image)[1].tobytes()
save_image(path, image)
assert path.read_bytes() == expected
```

Verified directly that this is a valid, deterministic oracle: `cv2.imencode` was verified to
produce **byte-identical output across repeated calls with identical input**, for both PNG
(lossless) and JPEG (lossy but deterministic given identical default parameters) — confirmed with
two independent calls on the same array producing `tobytes()`-identical buffers. This proves
`save_image` adds *only* Unicode-safe filesystem-path handling, and encodes exactly what
`cv2.imencode` itself would produce — never a different byte stream. A generic `save_image` →
`load_image` → pixel-equality round trip is explicitly **not** the primary oracle, because it
would be invalid for lossy codecs (JPEG); it may still be used as a secondary, PNG-only lossless
round-trip check.

## 13. Mutation / ownership semantics

**`save_image` never mutates `image`.** Verified directly: `cv2.imencode` does not modify its
input array in place (before/after equality checked for both PNG and JPEG encode calls, on freshly
random arrays). `save_image` itself performs no in-place operation of any kind beyond calling
`cv2.imencode`. No ownership transfer; the caller's array is unaffected regardless of success or
failure.

## 14. Return semantics

**Decision: `None`.** No `bool`, `bytes`, `Path`, encoded buffer, size, or result object is
returned. `cv2.imencode`'s own `bool` success flag is an implementation detail of an
exception-based public failure contract (§6) and must not leak into the public return type — this
mirrors `load_image`'s own precedent of raising rather than returning a sentinel/flag for
failure.

## 15. Relationship to `load_image`

**Symmetric:** both cross the local filesystem <-> decoded-array boundary through Python's own
Unicode-capable path/file APIs; both delegate the actual encode/decode work entirely to OpenCV's
in-memory codec (`cv2.imencode`/`cv2.imdecode`), never a filename-based `cv2.imwrite`/`cv2.imread`
call; both split failures into a native, unwrapped `OSError` family (filesystem-level) versus a
`ValueError` (codec-level, with `from exc` chaining where a native `cv2.error` was caught); both
add no metadata framework and no batch behavior of any kind; both reuse `io.py::_normalize_path`
for `path` handling.

**Asymmetric, deliberately:** `load_image`'s decode format is *content-detected* by
`cv2.imdecode` (the file's actual bytes determine what it decodes as, regardless of extension —
`load_image`'s own docstring states this explicitly: *"The file's extension/suffix is never
inspected"*). `save_image`'s encode format necessarily requires an explicit encoder choice, since
there is no equivalent "detect the format from raw pixel data" operation — the destination's
extension is the only available signal, and this design adopts it directly (§5). `load_image`
exposes three read *modes* (`color`/`grayscale`/`unchanged`) because OpenCV's own decode API
genuinely offers three meaningfully different decode policies; `save_image` v1 does **not**
introduce an equivalent `ImageWriteMode` merely for symmetry — there is no analogous "genuinely
different write policy" OpenCV exposes that this slice needs to select between (§22 elaborates).

## 16. Relationship to `PerceptualHashManifest.save`

`manifest.py`'s `save()` is useful **precedent**, not a template to inherit wholesale:

- **Adopted:** careful, precise filesystem-exception taxonomy (native errors propagate rather
  than being wrapped); no automatic parent-directory creation (§9 of this document, mirroring
  manifest.py's own explicit "The parent directory is never created automatically").
- **Not adopted, deliberately, each justified independently for the image-write use case:**
  `overwrite=False` (§8 — no evidence of demand, and every existing image-write call site already
  overwrites unconditionally); atomic temp-file + `fsync` + rename publishing (§9 — no evidence of
  demand, and it would substantially enlarge the contract for images specifically, which are not
  precious curated snapshots the way a manifest is).

## 17. Dependency / compatibility analysis

**Zero new dependency.** `cv2.imencode` (already used, base OpenCV, no `opencv-contrib`
requirement — verified none of the extensions tested required contrib modules) and `pathlib`
(stdlib, already used by `load_image`) are the only moving parts. No `Pillow`, `imageio`,
`networkx`, `scipy`, `pandas`, or `scikit-learn` involvement of any kind.

**Compatibility risk: low.** Scored 2/5 on the compatibility-regret scale (1 = obviously stable,
5 = likely redesign). The core contract — path in, `uint8` image in, Unicode-safe write out — is
a leaf-level, framework-agnostic operation with no coupling to any future dataset-loading
framework, `augmentation.Compose` pipeline, similarity-indexing layer, DNN inference API, or
video/3D phase; writing one already-decoded array to one path does not need to know about any of
those. The main residual risk is that a future dtype/format-parameter extension (§7's deferred
`uint16`/float support, or format-specific encode parameters) would be additive (new
keyword-only parameters, mirroring `create_dnn_blob`'s own precedent), not breaking.

**Cross-version matrix:** must remain correct across Python 3.11-3.14, NumPy 1.24.x/2.x, and
OpenCV 4.9.x/5.x. This design's empirical findings (§2-§9) were gathered against the currently
installed OpenCV 5.0.0 build only. **The encode-failure-mode findings (§6, particularly whether
`ok=False` is ever actually reachable) and the format-support findings (§5) must be independently
re-verified against the floor build (OpenCV 4.9.0.80) during implementation** — this project's
own standing practice (never assume a newer build's behavior generalizes downward) applies
directly here, exactly as it did for `load_image`'s own floor-version verification.

## 18. Test plan (bounded, for the future implementation PR)

**Path** (mirroring `load_image`'s own path-contract test suite, reusing `_normalize_path`'s
already-tested behavior where possible rather than re-deriving it): `str`, `Path`,
`os.PathLike[str]`, rejected `bytes`/`PathLike[bytes]`, empty string, relative path, Unicode path,
missing parent directory, directory destination (platform-tolerant assertion, per §4).

**Encoding:** PNG grayscale, PNG BGR, PNG BGRA, PNG `(H, W, 1)`, JPEG (byte-oracle + default-
parameter case only, no pixel-equality requirement), unsupported/no extension, multi-dot filename
extension resolution, uppercase extension, a reproducible `cv2.error` path (unsupported channel
count) and — if it can be made reproducible via monkeypatching the internal `cv2.imencode` call
rather than fabricating a real environment where it occurs — a synthetic `ok=False` path,
following this project's own existing precedent for testing "structurally not expected but still
defended" branches (mirroring the `multiclass_roc_curve_micro` error-wrapping monkeypatch tests
from `0.4.0a5`).

**Rejected input:** non-`uint8` dtype (`TypeError`, at least `float32` and `uint16`), 1-D array,
0-D array, empty array (all via the reused `require_image_ndim`/`require_dtype` — confirming
`save_image` wires them correctly, not re-deriving their own already-tested internal behavior).

**Filesystem:** overwrite of an existing regular file; native `OSError` propagation for a missing
parent and a directory destination; encode failure leaves an existing destination file byte-for-
byte unchanged (proving the "encode before touching destination" ordering from §9).

**Semantics:** the exact direct-`cv2.imencode` byte oracle (§12) for every representative
supported case; no-mutation check (§13); `save_image(...) is None` (§14).

**Typing:** `assert_type(save_image(path, image), None)`, accepted `path` type variants,
following `test_io.py`'s own existing typing-regression pattern (`assert_type` + a note that
Pyright, not just runtime, checks the file).

**Platform:** a Windows-specific non-ASCII path test (mirroring `load_image`'s own Windows CI
test), verifying success and byte-correctness — not a `cv2.imwrite`-failure assertion (§11).

This must not create thousands of pytest items — a bounded, explicit list per case, matching this
project's own established test-file style throughout `tests/test_io.py`.

mechanically replace every `cv2.imwrite` call — only sites where doing so genuinely demonstrates
or exercises the public contract, per this table.

## 20. Explicit non-goals (this slice)

- Batch/multi-image write of any kind.
- Animated/multipage format writing.
- Mask-specific semantics; image/mask *pair* writing (`save_image` writes one decoded array to
  one path, with no notion of what that array represents).
- URL/network destinations — `path` is always a local filesystem path, mirroring `load_image`.
- File-like-object destinations (a public in-memory `encode_image` API is a separate, later
  decision, not part of this slice).
- Format-specific encoder parameters of any kind: JPEG quality, PNG compression level, WebP
  quality, or any other `cv2.imencode` parameter passthrough (no untyped `params: Sequence[int]`
  escape hatch — OpenCV's own default encoding parameters are used, unconditionally, for every
  supported format).
- Metadata: no EXIF writing or preservation, no ICC profile preservation, no metadata copied from
  any "source" (this function does not know where its input array came from).
- Any image transformation: no orientation normalization, no RGB/BGR conversion, no alpha
  manipulation, no color-management layer, no resize, no dtype conversion/clipping/normalization
  of any kind (§7 — rejection, not conversion).
- Automatic parent-directory creation (§9 — `parents=True`-style behavior is out of scope).
- Atomic write/publish machinery (§9 — Option A won; explicitly not imported from `manifest.py`).
- A no-clobber/`overwrite` mode (§8 — Option A won; ordinary overwrite semantics apply
  unconditionally).
- Async/parallel writing.
- `uint16`/`float`-dtype support, despite PNG's own genuine (verified) uint16 losslessness — a
  real future extension candidate, deliberately deferred rather than solved with a partial,
  format-specific dtype matrix in this slice (§7).

## 21. Alternatives considered

- **Full delegation to `cv2.imencode` for dtype/channel acceptance ("Option B," the originally-
  provisional default).** Rejected — empirically shown to silently corrupt data for `float32` and
  `uint16`-into-JPEG inputs while still reporting success (§7). This is the one place this design
  materially diverges from its own starting premise, on direct evidence rather than assumption.
- **`overwrite=False` by default, mirroring `PerceptualHashManifest.save()`.** Rejected — no
  repository evidence of demand for image-specific no-clobber semantics; every existing write call
  site in the repo already overwrites unconditionally (§8).
- **Atomic same-directory publish, mirroring `manifest.py`'s temp-file machinery.** Rejected — no
  evidence of demand, and it would substantially enlarge the contract for a benefit not found in
  this audit (§9).
- **A hardcoded extension allowlist.** Rejected in favor of delegating codec-availability
  awareness to the installed OpenCV build, matching `load_image`'s own established stance that
  `improcv` does not re-promise OpenCV's own codec support independently (§5).
- **An `ImageWriteMode` `Literal`, mirroring `ImageReadMode`.** Rejected — there is no genuinely
  different write *policy* analogous to `load_image`'s three meaningfully different decode
  policies; adding one now would be symmetry for its own sake (§15, §22).
- **A generic `save_image` → `load_image` round-trip as the primary correctness oracle.**
  Rejected — invalid for lossy codecs; the direct-`cv2.imencode`-bytes oracle (§12) is used
  instead, with round-trip checks retained only as a secondary, PNG-only check.

## 22. Naming review

`save_image` is narrow and truthful: it saves *one* already-decoded array to *one* filesystem
path. It does not claim mask semantics (unlike a hypothetical `save_mask` or `save_image_pair`,
which this design explicitly avoids), does not claim format-specific quality control, and does
not claim atomicity unless a future design explicitly adds and documents it. It directly mirrors
`load_image`'s own already-established, already-accepted naming precedent in the same module.

## 23. Complexity

`O(1)` calls into OpenCV's own encoder (whose own internal complexity is not characterized here,
matching `load_image`'s own stance of not characterizing `cv2.imdecode`'s internal cost) plus
`O(n)` for the filesystem write itself, where `n` is the encoded byte count. No additional
temporary allocation beyond what `cv2.imencode` itself performs internally and the one
`Path.write_bytes()` call.

## 24. Determinism

`cv2.imencode` was verified directly, in this design, to produce byte-identical output across
repeated calls with identical input, for both a lossless codec (PNG) and a lossy one (JPEG, given
identical default parameters) — this underpins the byte-level oracle (§12) and is not assumed by
analogy with `load_image`.

## 26. STOP conditions (for the future implementation PR)

An implementation PR must STOP and report, rather than silently adapting, if any of the following
is found:

1. The floor-build (OpenCV 4.9.0.80) re-verification (§17) finds `cv2.imencode` behavior
   materially different from what this design documents for the 5.0.0 build used here (e.g.
   `ok=False` becomes reachable, or a dtype found "safe" here silently corrupts on the floor
   build).
2. `cv2.imencode` is found to mutate its input on some platform/build not tested here.
3. The byte-level oracle (§12) is found to be non-deterministic on any supported platform/build.
4. Any tested `uint8` case is found to silently misbehave on the floor build the way `float32`/
   `uint16`-into-JPEG did here.
5. Implementing the frozen contract turns out to require a new public type, a second public
   function, or a format-specific parameter after all — the public-symbol budget (§3) would no
   longer hold, and the feature must be re-scoped rather than forced through.
