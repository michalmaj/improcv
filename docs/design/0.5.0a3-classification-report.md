# Design: structured classification-evaluation report (`0.5.0a3` feature slice)

Status: implemented and released in `0.5.0a3` (`src/improcv/evaluation.py`). See §21 below for
two implementation clarifications (no frozen decision was altered). See §22 for the demo
migration §13 deferred, now completed as a follow-up.

## 1. Status / scope

This is the selected next feature slice of the `0.5.0` line, per the `0.5.0a3` product audit
(base `71f68d46378ad89f53190e3fbc879f091ba8c8c9`, `0.5.0a3.dev0`, `__all__` count 196), which
ranked "public classification-report API" first among five audited candidates.

This document does not treat that audit as a specification. Its own signature sketch (a single
function bundling confusion-matrix, classification-metrics, and ROC/AP ranking fields, modeled
directly on `demos/classification_report.py`'s private `ClassificationReport`) is re-examined
here from first principles, and rejected in its bundled form — see §4 for the full analysis and
§5 for the correction this makes to the audit's own recommendation.

## 2. Product rationale — the demo as evidence, not specification

`demos/classification_report.py` (681 lines, read here in full from the current base SHA) and
`tests/test_demos.py` (the `test_compute_classification_report_*`/`test_build_classification_*`
tests, read here in full) are real, working, tested code — strong evidence that *something* in
this area has value. But the demo is a rendering script for one fixed PNG figure, not a proposed
public contract: it says so itself, four separate times (`demos/classification_report.py:25-27`,
`356-358`, `398-399`, and implicitly at `21-24`), e.g. "This remains a demo script rendering one
fixed report figure, not a public plotting API." Its private `ClassificationReport` NamedTuple
was shaped by what one PNG figure needed to render, not by an independent analysis of what a
public result type should contain. §4 does that independent analysis.

## 4. Abstraction boundary — three options compared

**Option A — prediction-only report.** `classification_report(y_true, y_pred, *, labels=None,
zero_division=0.0, sample_weight=None) -> ClassificationReport`, containing only what is
derivable from hard predictions: confusion matrix, per-class metrics, macro metrics. No `y_score`
parameter at all.

**Option B — fully bundled prediction + ranking report.** `classification_report(y_true, y_pred,
y_score, *, labels, sample_weight=None, zero_division=0.0) -> ClassificationReport`, containing
AUC/AP/curve fields as the demo's private object does today. This is the shape the `0.5.0a3`
audit's own signature sketch (§9 of that audit) implicitly assumed by treating the demo as a
near-complete prototype.

**Option C — two-layer composition.** A prediction-only result (identical in shape to Option A)
plus a conceptually separate ranking-summary layer, composed by the caller (or, in a later,
separately-designed slice, by a second named function) rather than bundled into one type.

Answering the required question set for each:

| Question | Option A | Option B | Option C |
|---|---|---|---|
| Can a user get an ordinary report without `y_score`? | Yes — no such parameter exists | **No** — `y_score` is a required positional parameter; a caller with only `y_pred` (e.g. a classifier that never emits scores, or a pipeline that discards them) cannot call this function at all | Yes, identical to A |
| Does `y_score` become artificially mandatory? | No | **Yes** | No |
| Does the result mix two statistically distinct concepts? | No — confusion/per-class/macro metrics all summarize one fixed decision rule (the labels actually predicted) | **Yes** — hard-prediction metrics (from `y_pred`, a single fixed decision) and ranking metrics (from `y_score`, a threshold-independent sweep) are different statistical objects; nothing in the demo's data or in `evaluation.py` asserts or requires `y_pred == argmax(y_score, axis=1)` or any other reconciliation between them, so bundling them implies a coherence the type never actually checks | No — kept structurally separate, so no implied coherence is smuggled in |
| Does it duplicate existing ranking APIs merely for convenience? | N/A (no ranking involved) | **Partially** — the 9 ranking-related fields are a thin, bundled re-export of `multiclass_roc_auc_score`/`multiclass_average_precision_score`/`multiclass_roc_curve` output; the only real value added is "one call instead of five," which is genuine but modest, and is exactly the acceptance-gate #2 risk (§14) of merely renaming a sequence of obvious existing calls | No new ranking API surface in this slice at all |
| Behavior when `y_pred` is available but scores are not? | Fully supported — this is the primary case | **Impossible** — must use a different, undesigned API instead, defeating the "one call" premise for a large, legitimate use case (classical/rule-based classifiers, post-hoc-relabeled predictions, discarded scores) | Fully supported, identical to A |
| Behavior when scores are available but `y_pred` came from a policy that can't be reconstructed from them? | N/A | Legal but semantically confusing: the report would present a confusion matrix from one decision rule next to AUC/AP from an unrelated ranking, with no stated relationship between the two — coherent only under an unstated assumption (`y_pred` derived from `y_score` by argmax or similar) that this project's own ranking functions never require (`multiclass_roc_auc_score`'s docstring, line 1983, explicitly notes `y_score` need not even be a probability simplex) | N/A — never bundled, so this ambiguity never arises |
| Would future calibration/top-k/ranking additions turn this into a growing god object? | Low risk — 3 fields, each independently justified (§6); a future ranking companion would be a separate type, not a field added here | **Real risk** — once `y_score` is already a required parameter and 9 of 12 fields are ranking-related, "add one more ranking field" (top-k accuracy, a calibration curve, per-class precision-recall curves) has an obvious, tempting path with nothing in the type's own contract to stop it | None — by construction, ranking growth has nowhere to attach to this type |
| Stable reason to exist beyond one demo figure? | **Yes, and more universally applicable than B**: "give me confusion matrix + per-class and macro precision/recall/F1/support in one call" is a workflow need independent of whether ranking scores exist at all — many classifiers (template matching, rule-based, thresholded classical CV pipelines) never produce scores | Weaker — the only concrete evidence found for this exact bundle is the one demo figure itself; no call site independent of rendering that PNG needs exactly this combination | Yes, identical to A for the layer actually being designed here |

**Decision: Option A**, with Option C's separation as the intended long-term architecture (a
future ranking-summary companion type is an explicitly out-of-scope, not-designed possibility —
see §13 — not something this document invents prematurely). Option B is rejected: it fails the
"no artificially mandatory `y_score`" test outright, and its main justification is that the demo
already does it, which §12 of the requesting task explicitly disallows as a reason.

## 5. Correction to the `0.5.0a3` audit

The audit's own tentative signature sketch (its §9) modeled `classification_report` on the demo's
full 12-field object, implicitly assuming Option B. That sketch was explicitly marked
non-frozen and flagged naming/bundling as open questions for "a design PR" — this is that design
PR, and it resolves those questions against the audit's own sketch: the smallest coherent public
result is the 3-field, prediction-only Option A (§6), not the 12-field bundle. This mirrors the
precedent set by `docs/design/0.5.0a2-expand-perspective-canvas.md` §4, which similarly corrected
a "0 changed public types" claim in its own predecessor audit — auditing for *which* candidate to
build is a different exercise from freezing *what it should actually contain*, and the two are not
expected to agree in every detail.

This correction does not conflict with `docs/design/0.4.0a3-multiclass-curves.md` §20 ("A prior
audit stated the future 'evaluation report' candidate is 'hard-blocked' on multiclass curve
types. That claim is not accepted here... classification-report API remains a separate future
candidate; multiclass curve types may make it richer... but are not a technical prerequisite for
it to exist.") — verified directly at that file's lines 643-651. That correction only established
that curve types are not a *prerequisite* for a report to exist; it never asserted a report
*must* bundle curves, or ranking data at all. Option A is fully consistent with it: no curve
dependency, because no ranking dependency.

## 6. Result-type design

Existing precedents inspected directly (`src/improcv/evaluation.py`):

- `ConfusionMatrixResult`/`ClassificationMetrics` (lines 89-174): `@dataclass(frozen=True,
  slots=True, eq=False)` with a hand-written `__eq__` — required because these types hold raw
  `ndarray` fields directly, and the default dataclass equality would hit NumPy's "truth value of
  an array is ambiguous" error comparing them with bare `==`.
- `MulticlassRocCurve`/`MulticlassPrecisionRecallCurve` (lines 2230-2282): `@dataclass(frozen=True,
  slots=True)` with **no** `eq=False`, i.e. the plain dataclass-generated `__eq__`/`repr`. Their
  own docstring states why this is safe (line 2240-2243): "correct here because `RocCurve.__eq__`
  already returns a plain `bool`... so tuple equality over `curves` delegates to that per-element
  comparison without any special handling." Both explicitly set `__hash__ = None` anyway "for
  consistency with `RocCurve`/`PrecisionRecallCurve`/`ConfusionMatrixResult`/`ClassificationMetrics`,
  all of which are explicitly unhashable in this module" (line 2243-2245).

The new type composes `ConfusionMatrixResult` and `ClassificationMetrics` — both already have safe,
plain-`bool`-returning `__eq__` — and holds **no raw `ndarray` field of its own**. This is exactly
the `MulticlassRocCurve` situation, not the `ConfusionMatrixResult` situation:

```python
@dataclass(frozen=True, slots=True)
class ClassificationReport:
    confusion: ConfusionMatrixResult
    per_class: ClassificationMetrics
    macro: ClassificationMetrics

    __hash__ = None  # type: ignore[assignment]
```

- No custom `__eq__` — default dataclass equality is already safe, by the same reasoning
  `MulticlassRocCurve` documents.
- `__hash__ = None` set explicitly for the same "consistency" reason `MulticlassRocCurve` states,
  even though it would already be effectively unhashable at runtime the moment `hash()` reached an
  unhashable nested field.
- `repr`/`__match_args__` stay the plain dataclass-generated ones (positional `ClassificationReport(confusion=..., per_class=..., macro=...)`, matching this module's existing style).
- Ownership: none of the three fields is a raw array — each is itself an existing, already-documented
  read-only result object. No new ownership/mutability contract is introduced by this type.
- **Strong default followed**: existing public result objects are composed directly
  (`confusion`/`per_class`/`macro` are themselves `ConfusionMatrixResult`/`ClassificationMetrics`
  instances, not copies of their numeric contents into new fields). No new numeric representation
  is invented for data that already has one.

Only 3 fields, not the demo's 12 — a materially smaller, independently-justified surface per §4.
No `weighted`/`micro` field for the classification-metrics side is included: the demo never
computes `classification_metrics(..., average="weighted")` or `average="micro"`, and no other
repository evidence calls for it. Per the acceptance gate (§14 criterion 4, "every field has a
durable reason to belong"), a field is not added merely for symmetry with the ranking side's
macro/weighted/micro triad — that triad belongs to a different, out-of-scope layer (§4).

## 7. Naming

`classification_report`/`ClassificationReport` is reconsidered explicitly, per the requesting
task's instruction not to assume the demo's name survives.

The concern raised in the task — "does the widespread ecosystem expectation that a
'classification report' usually means a structured/textual summary of precision/recall/F-score
and support from `y_true`/`y_pred`, not necessarily ROC/AP curves" — actually now argues *for*
keeping the name, not against it, because §4 narrowed the scope to exactly that: confusion matrix
plus per-class/macro precision/recall/F1/support, with no ranking data at all. Under the rejected
Option B, the name would have been a real risk (bundling ROC/AP under a name that, ecosystem-wide,
usually does not include them); under the adopted Option A, the name's ecosystem meaning and this
type's actual contents now match closely.

Alternatives considered, per the task's instruction to compare only credible names without
bikeshedding:

- **`classification_report` / `ClassificationReport`** (adopted) — scope now matches the name's
  common meaning.
- **`classification_summary` / `ClassificationSummary`** — also reasonable, marginally more
  distant from any sklearn-specific expectation, but no repository evidence was found that
  `classification_report` actually causes confusion in this project (no issue, no prior internal
  note, no test asserting a different expectation) — per this project's own no-bikeshedding-
  without-evidence rule, this is not sufficient reason to prefer it over the name already in use
  by the existing (private) prototype.
- **`evaluate_classification` / `ClassificationEvaluation`** — rejected: the containing module is
  already named `evaluation`; `evaluate_classification`/`ClassificationEvaluation` collides
  conceptually with the module's own name while being vaguer about what the return value actually
  contains than `classification_report` already is.

**Decision: keep `classification_report`/`ClassificationReport`.** The public docstring must state
explicitly, as a non-goal, that this does **not** promise: sklearn-compatible text/table
formatting, a `dict`/JSON-style output mode, a `target_names` parameter, multilabel support, or
any other sklearn-equivalent behavior — this is a same-named but independently-designed function,
not a compatibility shim (consistent with this project's standing rule against claiming
`imutils`-successor status for unrelated reasons; the same discipline applies here to sklearn).

## 8. Avoiding redundant computation

**Demo's actual call count** (verified against `demos/classification_report.py:145-151` and each
called function's own documented behavior): the demo issues 3 independent top-level calls —
`confusion_matrix(...)`, `classification_metrics(..., average=None)`, and
`classification_metrics(..., average="macro")`. `classification_metrics`'s own docstring (line
370-372) states it "Builds the confusion matrix internally... and delegates to
`classification_metrics_from_confusion_matrix`" — i.e. each of the two `classification_metrics`
calls independently re-resolves labels and rebuilds the confusion matrix from raw `y_true`/`y_pred`
from scratch. The demo therefore performs the O(N) label-resolution-and-matrix-build work **three
times** for what is conceptually one confusion matrix.

`classification_metrics_from_confusion_matrix` (line 454) exists specifically to consume an
already-built `ConfusionMatrixResult` and skip that rebuild — it is not new logic invented for
this design, it is an existing public function built for exactly this composition.

**Decision: share the confusion matrix, via the existing composition seam — not the demo's naive
pattern, and not a new internal helper.**

```
confusion = confusion_matrix(y_true, y_pred, labels=labels, sample_weight=sample_weight)
per_class = classification_metrics_from_confusion_matrix(confusion, average=None, zero_division=zero_division)
macro     = classification_metrics_from_confusion_matrix(confusion, average="macro", zero_division=zero_division)
```

This computes the O(N) sample-level pass exactly once, then two cheap O(C) (C = number of labels)
reductions over the already-built matrix, instead of the demo's O(3N). It changes **zero**
constituent public functions (`classification_metrics_from_confusion_matrix` already exists and
is already public) and preserves full compositional identity (§11) — this is reuse of an existing
seam, not the "share validated/intermediate computation internally" alternative the requesting
task raises as something to justify carefully; here it requires no new internal logic at all, so
there is nothing to justify beyond citing the existing function.

Complexity: **O(N) time, O(N) memory** for the confusion-matrix build (dominated by `_build_confusion_matrix`/`_build_weighted_confusion_matrix`, unchanged, existing behavior) plus
**O(C)** additional time and memory for the two reductions — asymptotically identical to a single
`confusion_matrix` call alone, since `C ≤ N` always and the reduction cost does not depend on `N`
beyond what is already summarized in the matrix.

## 9. Parameter propagation (frozen)

`classification_report(y_true, y_pred, *, labels=None, zero_division=0.0, sample_weight=None)`

- **`labels`**: optional, exactly `confusion_matrix`'s own contract — `None` infers the sorted
  union of observed `y_true`/`y_pred` values (or, with `sample_weight`, only the effective
  positive-weight ones); an explicit sequence fixes row/column/array order and must contain every
  observed value (unlike scikit-learn's silent-drop, `ValueError` otherwise). Resolved **once**,
  inside the single `confusion_matrix` call (§8) — `per_class`/`macro` never re-resolve it, so
  `report.confusion.labels == report.per_class.labels == report.macro.labels` always holds by
  construction, not merely by coincidence of deterministic inputs.
  There is no requirement of at least 2 labels — that requirement belongs only to the ranking
  functions (`multiclass_roc_auc_score`'s docstring line 2065-2066: "multiclass ranking scores
  require at least 2 labels"), which this design never calls (§4). A single-label report is legal.
- **`sample_weight`**: one value, forwarded to the single `confusion_matrix` call only —
  `classification_metrics_from_confusion_matrix` has no `sample_weight` parameter of its own (the
  weight is already baked into the matrix it consumes), so both `per_class` and `macro` are
  automatically, consistently weighted by construction, never by re-passing the same weight to two
  independent functions that could in principle diverge.
- **`zero_division`**: one value, forwarded identically to both
  `classification_metrics_from_confusion_matrix` calls (`per_class`, `macro`). Has no meaning for
  `confusion_matrix` itself (that function accepts no such parameter — confusion counts are always
  well-defined, no ratio is ever computed there).
- **No `average` parameter** on `classification_report` itself: unlike `classification_metrics`,
  this function always returns exactly the two fixed views (`per_class` = `average=None`, `macro` =
  `average="macro"|`) — there is nothing for a caller to select.

**Validation/error ordering (frozen)** — mirrors `classification_metrics`'s own order exactly
(verified at `evaluation.py:403-451`), since `classification_report` performs a strict superset of
that same validation and adds no new check of its own:

1. Normalize `zero_division` (same normalization `classification_metrics` uses).
2. Normalize `y_true`/`y_pred` into label sequences; raise `ValueError` if lengths differ.
3. Raise `ValueError` if `y_true`/`y_pred` is empty — **unconditionally, even with explicit
   `labels`.** This is a deliberate, frozen choice, not silently inherited from whichever
   constituent is laxer: `confusion_matrix` alone *would* tolerate empty input with explicit
   `labels` (an all-zero matrix), but `classification_metrics` never does, for a documented reason
   (line 375-377: "`zero_division` resolves an undefined value for one class among others, not the
   complete absence of any observation to evaluate at all"). Since this report always includes a
   `classification_metrics`-shaped view, it adopts the *strictest* constituent's rule uniformly —
   per the requesting task's own instruction that "the report must not create subtly different
   validation semantics from its constituent APIs," picking the laxer of two conflicting
   constituent rules would itself be a subtly different (accidentally permissive) semantics, so the
   stricter one is the only choice that avoids inventing a third behavior.
4. If `sample_weight` is given: validate it (same non-negative, length-matching, accepted-dtype
   checks `confusion_matrix` already runs), then require at least one positive value —
   **unconditionally, again adopting `classification_metrics`'s stricter rule** (line 433-434 there)
   over `confusion_matrix`'s laxer one (which permits an all-zero weight, producing a well-defined
   all-zero matrix) for the same reason as step 3.
5. Resolve `labels` (explicit, validated against every raw observed value; or inferred).
6. Build the confusion matrix once (§8).
7. Derive `per_class`/`macro` via `classification_metrics_from_confusion_matrix` (§8).
8. Return `ClassificationReport(confusion, per_class, macro)`.

## 10. Edge-case matrix

| Case | Behavior (frozen) | Basis |
|---|---|---|
| Empty `y_true`/`y_pred` | `ValueError`, unconditionally (even with explicit `labels`) | §9 step 3 — adopts `classification_metrics`'s stricter rule |
| One-class input | Legal — confusion is `1x1`, `per_class`/`macro` arrays/scalars of length 1 | No ≥2-label requirement applies outside the ranking functions (§9) |
| Explicit zero-support label | Legal — all-zero row/column in `confusion`; corresponding `per_class` ratios resolved via `zero_division` | Inherited unchanged from `confusion_matrix`/`classification_metrics_from_confusion_matrix` |
| Label absent from `y_true` only | Legal — zero-support row, well-defined column; `zero_division` fills undefined ratios | Same as above |
| Label absent from `y_pred` only | Legal — zero-support column, well-defined row; `zero_division` fills undefined ratios | Same as above |
| Prediction/true value not in explicit `labels` | `ValueError` naming the offending value | Inherited unchanged from `confusion_matrix`'s documented departure from scikit-learn's silent-drop |
| `y_score` shape mismatch | **Not applicable** — this design has no `y_score` parameter (§4) | Option A rejects ranking data entirely |
| Non-finite scores | **Not applicable**, same reason | — |
| All-zero `sample_weight` | `ValueError`, unconditionally | §9 step 4 |
| Integer vs. float `sample_weight` | Both accepted, exactly `confusion_matrix`'s existing contract | Inherited unchanged |
| `zero_division` = `0.0` / `1.0` / `"nan"` | All three accepted, forwarded unchanged to both `classification_metrics_from_confusion_matrix` calls | Inherited unchanged |
| Arbitrary / non-contiguous label values | Legal — no contiguity requirement anywhere in `confusion_matrix`/`classification_metrics` | Inherited unchanged |
| Reordered explicit `labels` | `confusion`/`per_class`/`macro` all reflect the given order identically, always in agreement (§9) | New guarantee, but composed entirely from existing per-function ordering guarantees |

No case above invents handling different from an existing constituent function's own documented
behavior; the two "unconditional strictness" choices (empty input, all-zero weight) are the only
new decisions this document makes, and both are justified as picking the *strictest* already-
existing constituent rule rather than inventing a fourth behavior (§9).

## 11. Curves question — decided independently

Per the requesting task's instruction, this is decided independently of the demo's asymmetric
choice (one rendered curve type, chosen for one PNG figure, not for API completeness):

**Decision: this report excludes all curves, and all ranking data of any kind.** Not "curves are
deferred pending the macro/weighted interpolation question" (§12's exclusion of aggregate curve
*objects* is a separate, narrower reason that would only matter for Option B) — the ranking layer
as a whole (`roc_curve`, `precision_recall_curve`, scalar AUC/AP, and any future curve type) is out
of scope for this slice because it belongs to a conceptually different layer than "classification
report" now names (§4, §7). This is the valid design outcome the requesting task explicitly
allows: "a valid design outcome is: 'structured report deliberately excludes all curves.'"

## 13. Demo migration (decision recorded, not executed here)

Because the public result (§4, §6) is intentionally narrower than the demo's current private
12-field object, full replacement is not possible without either widening the public API (rejected,
§4) or dropping ranking data the demo still needs to render (not desired). The recommended shape
for the future implementation PR, per the requesting task's explicit instruction not to widen the
public API merely to eliminate every private line from the demo:

- Replace the demo's own 3 separate calls (`confusion_matrix`, `classification_metrics` ×2,
  lines 145-151) with one call to the new public `classification_report(...)`.
- Keep computing the 9 ranking-related fields (`auc_*`, `ap_*`, `roc_curves`) exactly as today, via
  the existing separate `multiclass_roc_auc_score`/`multiclass_average_precision_score`/
  `multiclass_roc_curve` calls — unchanged.
- The demo's private `ClassificationReport` NamedTuple would then hold the new public
  `ClassificationReport` as one field (or unpack its three sub-fields) alongside its own 9 ranking
  fields, composing the public report with existing ranking calls rather than the public API
  absorbing them.

## 21. Implementation notes (added post-implementation; clarifications only, no contract change)

Two facts surfaced during implementation, both handled within the frozen contract, not by
revising it:

1. **`zero_division` must be forwarded raw, not pre-normalized.** §9's frozen validation order
   requires validating `zero_division` before building the confusion matrix (step 1), for
   error-ordering parity with `classification_metrics`. The implementation validates it early via
   `_normalize_zero_division` purely for that ordering check, but passes the caller's *original*
   `zero_division` argument — not the normalized return value — into both
   `classification_metrics_from_confusion_matrix` calls. Passing the already-normalized value
   would break the `zero_division="nan"` case: `_normalize_zero_division` converts the string
   `"nan"` to `float("nan")`, and `classification_metrics_from_confusion_matrix` normalizes its own
   `zero_division` argument again internally — renormalizing an already-converted `float("nan")` is
   rejected, since only the literal string `"nan"` is an accepted raw input, not a NaN float. This
   is an implementation detail of satisfying §9's frozen ordering correctly, not a change to what
   is validated or when errors fire.
2. **Demo migration (§13) is deferred to a follow-up**, not performed in the implementation PR.
   Beyond the reasons already on record in §13 (the public result is intentionally narrower than
   the demo's private object), migration would also need to address a name collision: the demo's
   existing private `ClassificationReport` (`demos/classification_report.py:84`, a 12-field
   `NamedTuple`) shares its exact name with the new public `improcv.evaluation.ClassificationReport`
   — not a real Python namespace collision (the demo's is module-local; the public one is accessed
   as `im.ClassificationReport`), but a confusing coincidence a migration would need to resolve
   (e.g. renaming the demo's private type) as its own decision, not one this design freezes.
   Keeping the implementation PR scoped to the frozen §4/§6 contract, with migration as an
   independent follow-up, matches §13's own "left to that PR's own scope judgment" language.

## 22. Demo migration (§13) — completed as a follow-up

`demos/classification_report.py` now calls the public `im.classification_report(...)` directly
for its hard-prediction section (`compute_classification_report` returns `im.ClassificationReport`
unchanged, not a copy) — the demo no longer calls `confusion_matrix`/`classification_metrics`
itself. This resolves the §13/§21-item-2 name collision by removal rather than rename: the demo's
private `ClassificationReport` `NamedTuple` no longer exists at all.

The 9 ranking-related fields (`auc_*`, `ap_*`, `roc_curves`) were **not** nested inside the public
report as one of §13's suggested shapes described ("hold the new public `ClassificationReport` as
one field... alongside its own 9 ranking fields") — instead they live in a new, fully independent
demo-local `RankingSummary` `NamedTuple`, computed by a separate `compute_ranking_summary` function
and passed to `build_classification_figure`/`render_classification_report` as its own parameter.
Both shapes were already explicitly left open by §13 ("or unpack its three sub-fields... not frozen
here"); the fully-separate shape was chosen for less private glue and a cleaner mapping to the same
prediction/ranking boundary the public API itself draws (§4), not because the nested shape was
found unworkable.

Numerical output (confusion matrix, per-class/macro metrics, all AUC/AP scalars, ROC curve arrays,
and every rendered text panel) was verified bit-for-bit/text-identical against the pre-migration
demo for the same fixed example — zero intended delta.
