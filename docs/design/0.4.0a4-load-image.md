# Design: public, Unicode-safe single-image loading (`load_image`, `0.4.0a4` first slice)

Status: implemented on the 0.4.0a4 development line; not yet released.

## 1. User problem

```text
discover_images/discover_image_mask_pairs give me Path objects, but improcv
has no public function to turn one of those paths into a decoded NumPy
image. I either call cv2.imread(str(path), ...) myself, which is not
Unicode-safe on Windows, or hand-roll Path.read_bytes() + np.frombuffer +
cv2.imdecode myself every time, including handling a None result on
failure. improcv already solves this internally (dataset.py's private
_decode_grayscale) but never exposes it.
```

This is not hypothetical: `examples/discovery_and_augmentation.py:65-66` does exactly the unsafe
thing this design fixes, in the project's own example code:

```python
image = cv2.imread(str(first_pair.image), cv2.IMREAD_COLOR)
mask = cv2.imread(str(first_pair.mask), cv2.IMREAD_UNCHANGED)
```

`examples/image_similarity.py:111` and `examples/image_similarity_manifest.py:119` do the same
with `cv2.imread(str(path), cv2.IMREAD_GRAYSCALE)`. All three convert a `Path` to `str` and hand it
to `cv2.imread`, which is exactly the pattern `dataset.py`'s own `_decode_grayscale` docstring
identifies as unreliable on Windows: *"on Windows that handling is Unicode-capable, unlike
`cv2.imread`, whose filename-based handling is not reliable for paths containing characters outside
the active code page."* `discover_images`/`discover_image_mask_pairs` return `Path` values with no
restriction on their characters; nothing before this design closes the gap between "have a `Path`"
and "have a decoded array," safely, as public API.

`docs/design/0.4.0a3-multiclass-curves.md` §28 already flagged this exact candidate for a future
slice and recorded a tentative shape (`load_image(path, *, mode=cv2.IMREAD_COLOR)`). **That shape is
not normative.** This document re-derives the mode representation, the exact mode set, return
typing, path contract, error semantics, module placement, and every other design question from the
current codebase and from OpenCV's own documented/verified behavior, from scratch.

First slice scope, frozen: **exactly one path in, one decoded image out.** Not dataset iteration
(no directory walking -- that is `discover_images`' job), not pair loading (`load_image_mask_pair`
is a separate, unstarted, future candidate), not mask interpretation, not batching.

## 3. Mode representation: Enum vs. `Literal` vs. raw `cv2` flags

Three ways `load_image` could accept "how to decode":

**(A) A public `Enum`/`StrEnum` class**, e.g. `class ImageReadMode(StrEnum): COLOR = "color"; ...`.
Precedent check: the codebase has exactly **one** real `Enum`, `PerceptualHashAlgorithm(StrEnum)`
in `hashing.py`. Its use case is a field stored inside a persisted, serialized JSON manifest
(`PerceptualHashManifestEntry`) -- an `Enum` gives it a stable, explicit serialization identity
that a bare string union does not need. `mode` has no such persistence requirement; it is a plain,
transient function parameter.

**(B) A `Literal[...]` string-union type alias**, validated at runtime via the existing
`_validation.require_one_of` helper. Precedent check, recounted directly against the current
source (`rg -n "^[A-Za-z_]* = Literal\[" src/improcv/*.py`, cross-checked against `__init__.py`'s
`__all__`): **fourteen** other "closed choice" *public* types in this codebase are exactly this
shape -- `FeatureMethod`, `DescriptorNorm`, `StitchMode`, `InpaintMethod`, `SeamlessCloneMode`,
`RetrievalMode`, `ApproxMethod`, `DistanceType`, `TemplateMatchMethod`, `HoughCircleMethod`,
`FastType`, `Connectivity`, `SortOrder`, `DistanceMaskSize` -- all validated the same way, via
`require_one_of(value, allowed, name)`, which raises `ValueError` (never `TypeError`) for any value
not in `allowed`, including a value of the wrong type entirely. (Three further `Literal` aliases
exist in the source -- `ThresholdMethod`, `FlipDirection`, `PadMode` -- but are not exported in
`__all__`, so they are not counted as public precedent here.) This is the dominant, established
convention (14 real precedents vs. 1 real counter-example whose counter-example is explained by a
use case that doesn't apply here).

**(C) Raw `cv2.IMREAD_*` integers passed straight through**, e.g. `load_image(path, mode=cv2.
IMREAD_COLOR)`. Rejected: this would let a caller pass an *arbitrary* `int` OpenCV flag (including
combinations like `cv2.IMREAD_IGNORE_ORIENTATION | cv2.IMREAD_COLOR`, or `cv2.IMREAD_REDUCED_*`),
which directly conflicts with this slice's frozen, curated three-mode scope (§4) and its exclusion
of arbitrary flag passthrough (§20). It also leaks an OpenCV implementation detail (numeric flag
values) into the public signature where every other closed-choice improcv parameter uses a curated
string space instead.

**Decision: (B), a `Literal[...]` type alias**, validated via `require_one_of`, consistent with 14
of 15 existing public closed-choice parameters in this codebase.

## 4. The central decision: exact mode set

Two candidate sets were compared, as required:

- **Variant 1**: `{"color", "unchanged"}` (2 modes).
- **Variant 2**: `{"color", "grayscale", "unchanged"}` (3 modes).

The disqualified argument for Variant 1 -- "`grayscale` is redundant because `ensure_gray` already
exists" -- was tested empirically rather than assumed, because `IMREAD_GRAYSCALE` and `IMREAD_COLOR`
+ `cv2.cvtColor(..., COLOR_BGR2GRAY)` are two independent code paths inside OpenCV with no
contractual promise of matching output:

```text
Source: a genuinely color 12x12 uint8 BGR PNG (random per-channel values).
  cv2.imdecode(buf, IMREAD_GRAYSCALE)  vs.
  cv2.cvtColor(cv2.imdecode(buf, IMREAD_COLOR), COLOR_BGR2GRAY)
  -> differ by up to 1 in pixel value (not bit-identical), verified on both
     OpenCV 4.14.0 and 5.0.0.

Source: a genuinely grayscale 12x12 uint8 PNG.
  Both paths agree exactly with each other and with the original array.
```

So for real color images, `ensure_gray(load_image(path, mode="color"))` and a genuine
`IMREAD_GRAYSCALE` decode are **not** interchangeable -- this refutes the redundancy argument
directly, with evidence, as required, rather than by assertion.

That said, "not redundant" alone would not be sufficient justification either -- OpenCV having a
flag is not a reason to expose it. The positive case for keeping `grayscale` as a genuine third
mode:

- **Existing internal precedent**: `dataset.py`'s private `_decode_grayscale` already commits to
  exactly the `IMREAD_GRAYSCALE` policy for the entire perceptual-hashing/manifest pipeline
  (`build_perceptual_hash_manifest`). A public `load_image(path, mode="grayscale")` documents and
  exposes a policy the library already depends on internally, rather than inventing a new one.
- **Frequency**: grayscale is the required or default input shape for a large share of existing
  public functions in this library (`ensure_gray`, `average_hash`/`phash`'s grayscale path,
  `auto_canny`, `hough_lines`/`hough_circles`, `find_contours` via `threshold`, `detect_fast_
  keypoints`/`detect_blob_keypoints`, `nl_means_denoise`) -- a caller loading an image specifically
  to feed one of these has a real, common reason to ask for the codec's own grayscale decode
  directly, without a separate `ensure_gray` call and without the (now proven) risk of assuming
  it's interchangeable with one.
- **API budget cost is zero**: mode-set members are values of one `Literal` alias, not separate
  top-level public symbols (§19) -- adding a third value does not consume any additional public
  symbol budget.
- **Typing cost is one `@overload`**, trivially small (§8).
- **Safe to add later, but not free to add later**: had it been deferred, a caller with a genuine
  `IMREAD_GRAYSCALE` need would have no public route to it except doing exactly the unsafe
  `cv2.imread` pattern this design exists to remove -- undercutting the design's own motivation for
  the second most common decode target after `color`.

**Decision: Variant 2 -- `{"color", "grayscale", "unchanged"}`.**

```python
ImageReadMode = Literal["color", "grayscale", "unchanged"]
```

## 5. Per-mode frozen contract

All three modes were verified identically on OpenCV 4.14.0 and 5.0.0 (both within this project's
`>=4.9,<6` supported range); nothing below is version-specific.

### `mode="color"` (the default)

- OpenCV flag: `cv2.IMREAD_COLOR`.
- Output: always exactly 3 channels, order **BGR** (per OpenCV's own confirmed documentation text:
  *"the decoded images will have the channels stored in B G R order"*).
- Output dtype: always `uint8`, regardless of the source file's own bit depth.
- Verified behavior by source type: a 16-bit grayscale or 16-bit BGR/BGRA source is downcast to
  8-bit 3-channel; a grayscale source is promoted to 3 identical channels; a BGRA source has its
  alpha channel dropped. **The specific downcast/promotion/alpha-drop algorithm itself (rounding,
  gamma, or channel-replication rule) is not frozen by this design** -- only the resulting
  dtype/channel-count guarantee is public contract; the pixel-value transformation is delegated to
  OpenCV's own codec and color-conversion internals, which this design does not reproduce or
  override.
- EXIF orientation: applied automatically by OpenCV's own JPEG decode path when an orientation tag
  is present (§9) -- delegated behavior, not something `load_image` implements or can disable in
  this slice.

### `mode="grayscale"`

- OpenCV flag: `cv2.IMREAD_GRAYSCALE`.
- Output: always exactly 2-D (no channel axis), dtype always `uint8`.
- This is the codec/OpenCV's own grayscale decode policy -- **not** a promise of bit-for-bit
  equality with `ensure_gray(load_image(path, mode="color"))`; §4 already demonstrated these two
  paths can differ by up to 1 per pixel for a genuinely color source. This document explicitly
  states that such equality is **not** part of `load_image`'s contract, in either direction.
- Verified behavior by source type: identical downcast/alpha-drop pattern to `color` (16-bit
  sources downcast to `uint8`, alpha dropped), landing on a single channel instead of three.
- EXIF orientation: applied automatically, identically to `color` (verified empirically, §9).

### `mode="unchanged"`

- OpenCV flag: `cv2.IMREAD_UNCHANGED`.
- This mode **returns the ndarray produced by OpenCV's `IMREAD_UNCHANGED` decode policy; this is
  still a decoded representation, not the encoded file's raw pixel/storage representation or
  metadata.** It does not guarantee: preservation of a palette/indexed color table as an index map
  (verified false, below); preservation of any file metadata (EXIF, ICC profile, text chunks, etc.
  -- `load_image` returns only pixel data, never metadata, for any mode); the encoded file's
  compressed/raw byte representation; or bit-identical output across different codecs/formats
  encoding "the same" image.
- Verified per-source-type behavior (PNG, both OpenCV versions, exact `np.array_equal` match to the
  pre-encode array unless noted):

  | Source | UNCHANGED result shape/dtype | Notes |
  |---|---|---|
  | 8-bit grayscale | `(H, W)`, `uint8` | exact match |
  | 8-bit BGR | `(H, W, 3)`, `uint8` | exact match |
  | 8-bit BGRA | `(H, W, 4)`, `uint8` | exact match, alpha preserved |
  | 16-bit grayscale | `(H, W)`, `uint16` | exact match, **not** downcast |
  | 16-bit BGR | `(H, W, 3)`, `uint16` | exact match, **not** downcast |
  | 16-bit BGRA | `(H, W, 4)`, `uint16` | exact match, **not** downcast |
  | palette/indexed (PNG, PIL mode `"P"`) | `(H, W, 3)`, `uint8` | **expanded to BGR color -- the palette/index structure is NOT preserved** |

  The palette result directly refutes the assumption "palette PNG -> index map": OpenCV's
  `IMREAD_UNCHANGED` on a palette PNG produced a 3-channel BGR array with the palette's actual
  colors substituted in, not a single-channel array of index values.
- EXIF orientation: `IMREAD_UNCHANGED` does **not** apply EXIF orientation, even without
  `IMREAD_IGNORE_ORIENTATION` set -- a real, documented exception, not an oversight (§9).
- Return type stays generic `Image` (not `ImageU8`), since dtype genuinely varies by source
  (`uint8` or `uint16` observed; other codecs/depths are possible and not enumerated here).

## 6. OpenCV documentation and empirical verification (§2 continued)

Section 5's frozen claims are the direct product of the verification described in §2. The
palette-PNG and 16-bit-preservation findings came from a script that `cv2.imencode`d NumPy arrays
of each described shape/dtype (and, for the palette case, wrote a `PIL.Image` in mode `"P"` with an
explicit palette to produce a genuine indexed PNG, since `cv2.imencode` itself has no "write as
palette" option), then decoded the resulting bytes with each of `IMREAD_COLOR`/`IMREAD_GRAYSCALE`/
`IMREAD_UNCHANGED` and compared shape/dtype/values. The EXIF finding came from a `PIL`-authored
JPEG carrying a real `Orientation=6` EXIF tag (`piexif`), encoded at `10x20`, decoded with `COLOR`
(result `10x20x3` -- rotated), `UNCHANGED` (result `20x10x3` -- not rotated), and `IMREAD_COLOR |
IMREAD_IGNORE_ORIENTATION` (result `20x10x3` -- matches `UNCHANGED`, confirming the ignore-flag and
`UNCHANGED` produce the same un-rotated geometry). All scripts and their venvs were scratch,
throwaway artifacts, deleted after use; none are part of this repository.

`IMREAD_ANYDEPTH`/`IMREAD_ANYCOLOR` were not separately investigated beyond confirming their bare
numeric values exist in OpenCV's `ImreadModes` enum -- they are out of scope for this slice (§20)
since the three chosen modes (§4) already cover this design's frozen use cases without them.

## 7. Return typing (`@overload`, mandatory)

Existing precedent: `augmentation.py`'s `apply_flip`/`apply_crop`/`apply_affine`/`apply_perspective`
already use `@overload` in this codebase, discriminating on parameter *presence* (whether `mask` is
given) rather than a `Literal` value. `load_image` adapts the same `@overload` mechanism to
discriminate on `mode: Literal[...]` instead -- a legitimate, precedented use of the same feature
for a different discriminant.

```python
@overload
def load_image(path: str | os.PathLike[str], *, mode: Literal["color"] = "color") -> ImageU8: ...
@overload
def load_image(path: str | os.PathLike[str], *, mode: Literal["grayscale"]) -> ImageU8: ...
@overload
def load_image(path: str | os.PathLike[str], *, mode: Literal["unchanged"]) -> Image: ...
def load_image(path: str | os.PathLike[str], *, mode: ImageReadMode = "color") -> Image:
    ...  # implementation signature, widened to the union return type
```

`color`/`grayscale` both keep the stronger `ImageU8` return type (dtype is always `uint8` for these
two modes, per §5) rather than falling back to generic `Image`; `unchanged` returns `Image` since
its dtype genuinely varies by source.

Verified with Pyright (`pyright`, `basic` mode, matching this project's own `[tool.pyright]`
config) against four cases, as required:

1. A bare default call, `load_image(p)` -- resolves to `ImageU8`.
2. Each explicit literal-string call (`mode="color"`, `mode="grayscale"`, `mode="unchanged"`) --
   resolves to `ImageU8`, `ImageU8`, `Image` respectively.
3. A variable pre-typed as `ImageReadMode` (e.g. `m: ImageReadMode = "color"`) passed as
   `load_image(p, mode=m)` -- Pyright's literal narrowing keeps the variable's declared literal
   type as long as it is never reassigned, so overload resolution matches correctly.
4. An invalid literal, `load_image(p, mode="bogus")` -- rejected with two Pyright errors
   (`reportCallIssue` and `reportArgumentType`), confirming the invalid value is caught statically,
   in addition to the runtime `require_one_of` check (§11) that catches it for untyped call sites.

## 8. Path contract

Compared directly against `discovery.py`'s own path contract, since both APIs consume a filesystem
path and this design should be consistent with it wherever both apply. `discovery.py`'s private
`_normalize_root` (mirrored, not reused directly, since `load_image` does not validate a directory):

```python
def _normalize_root(root: object, *, name: str = "root") -> Path:
    try:
        raw_root = os.fspath(root)
    except TypeError as exc:
        raise TypeError(
            f"{name} must be a str or os.PathLike[str], got {type(root).__name__}"
        ) from exc
    if not isinstance(raw_root, str):
        raise TypeError(
            f"{name} must resolve to a str, got {type(raw_root).__name__} from os.fspath() "
            "-- a PathLike whose __fspath__() returns bytes is not accepted"
        )
    if raw_root == "":
        raise ValueError(f"{name} must not be an empty string")
    root_path = Path(raw_root)
    root_stat = root_path.stat()          # discovery-specific: load_image has no equivalent
    ...                                    # (directory-ness check does not apply here)
```

`load_image`'s own private `_normalize_path` copies the first three checks verbatim (adjusted for
the `path` parameter name) and stops there -- there is no directory-stat check, because
`load_image` is not a discovery/traversal API and does not need to confirm anything about the path
before attempting to read it; existence and type-of-entry are discovered naturally by the read
itself (below).

Frozen: **`path: str | os.PathLike[str]`**, identical in shape to `discover_images`' `root`
parameter.

Per-case resolution, all either verified directly or a direct, documented consequence of the
`_normalize_path`/`Path.read_bytes()` combination:

| Input | Result |
|---|---|
| `str` | accepted |
| `pathlib.Path` (or other `os.PathLike[str]`) | accepted, via `os.fspath()` |
| custom object implementing `__fspath__() -> str` | accepted, via `os.fspath()` |
| custom object implementing `__fspath__() -> bytes` | `TypeError` -- `os.fspath()` succeeds but returns `bytes`, caught by the explicit `isinstance(raw_path, str)` check |
| `bytes` | `TypeError` -- `os.fspath()` passes `bytes` through unchanged, caught by the same `isinstance` check |
| `bytearray` | `TypeError` -- `os.fspath()` itself raises `TypeError` (not `str`/`bytes`, no `__fspath__`) |
| `""` (empty string) | `ValueError` |
| a string containing a NUL byte | not special-cased by `_normalize_path`; propagates as `ValueError` from Python's own filesystem layer once `Path.read_bytes()` is attempted -- the exact wording is platform-dependent (verified via CI: `"embedded null byte"` on POSIX, `"embedded null character"` on Windows), so only the exception type is part of this contract |
| relative path | accepted unchanged, never resolved to absolute |
| absolute path | accepted unchanged |
| symlink | opened via `Path.read_bytes()`'s ordinary symlink-following semantics -- `load_image` performs no symlink-specific handling of any kind, since it is not a traversal API; a broken symlink surfaces as `FileNotFoundError` |
| directory path | an `OSError` from `Path.read_bytes()`, propagated unwrapped -- the exact subclass is platform-dependent (verified via CI: `IsADirectoryError` on POSIX; Windows has no equivalent errno and raises `PermissionError` instead), so only "a native `OSError` propagates unchanged" is part of this contract, not one specific subclass on every platform |
| missing path | `FileNotFoundError` from `Path.read_bytes()`, propagated unwrapped |
| permission failure | `PermissionError` from `Path.read_bytes()`, propagated unwrapped |

`load_image` never calls `expanduser()`, `resolve()`, `.absolute()`, Unicode normalization, or case
folding on `path` -- consistent with `discover_images`' own documented "never resolved/made
absolute" policy, and with there being no stated need for any of these transformations here.

## 9. EXIF orientation (mandatory)

Verified empirically (§2, §6) on both OpenCV 4.14.0 and 5.0.0, using a real JPEG carrying an
`Orientation=6` EXIF tag:

- `mode="color"`: EXIF orientation is **applied** by OpenCV's own JPEG decode path by default
  (confirmed: a `10x20`-encoded source decoded to `10x20x3`, i.e. rotated per the tag).
- `mode="grayscale"`: same automatic application as `color` (confirmed: same rotated result).
- `mode="unchanged"`: EXIF orientation is **not** applied, even though `IMREAD_IGNORE_ORIENTATION`
  was not set (confirmed: the same source decoded to the un-rotated `20x10x3`, matching `IMREAD_
  COLOR | IMREAD_IGNORE_ORIENTATION`'s result exactly). This is a real, OpenCV-documented exception
  (corroborated by opencv/opencv issues #15786, #23122, #16579, #6673), not an oversight of this
  design.

`load_image` does not add an orientation-normalization layer of its own in any mode -- this
behavior is entirely OpenCV's own decode-pipeline default, delegated as-is. `load_image` does not
expose `IMREAD_IGNORE_ORIENTATION` in this slice (arbitrary/extra flag exposure is out of scope,
§20); a caller who needs to disable auto-orientation for `color`/`grayscale` has no route to that
through `load_image` in this first slice.

This finding was verified against JPEG specifically, the format EXIF orientation applies to; PNG/
TIFF EXIF-orientation handling was not exercised and is not claimed here.

## 10. Filesystem access policy

`load_image` reads a file's bytes exactly once, through `Path.read_bytes()`, and decodes them with
`cv2.imdecode` -- **never** `cv2.imread(str(path), ...)`. This mirrors `dataset.py`'s `_decode_
grayscale` exactly, for the same reason: `Path.read_bytes()` goes through Python's own,
Unicode-capable filesystem path handling, so a path containing characters outside a Windows
machine's active code page still works, whereas `cv2.imread`'s filename-based handling is not
reliable there. By the time `cv2.imdecode` runs, it only ever sees an in-memory buffer -- no
filename is involved in the decode step at all.

No stat-before-read, no extension validation, no format-guessing from the file suffix, no
filesystem write, and no caching of any kind. `load_image` is a single, one-shot, side-effect-free
(besides the one read) function call.

## 11. Empty file, read failures, and decode failures

Three distinct outcomes, never collapsed into one:

1. **A native filesystem error** (`FileNotFoundError`, `PermissionError`, `IsADirectoryError`, or
   any other `OSError`) from `Path.read_bytes()` itself propagates completely unwrapped. This
   mirrors `_decode_grayscale`'s own documented policy exactly: *"Any `OSError` raised by `path.
   read_bytes()` itself... propagates unchanged."*
2. **An empty file** (`read_bytes()` succeeds and returns `b""`): treated as a decode failure,
   raising `ValueError` naming the source path -- mirroring `_decode_grayscale`'s policy of treating
   an empty file as undecodable, without ever calling `cv2.imdecode` on an empty buffer.
3. **A successfully-read but undecodable file**: `cv2.imdecode` does not signal a decode failure
   only by returning `None` -- post-merge review reproduced a real, deterministic case (a tiny PNG
   whose `IHDR` declares dimensions beyond OpenCV's own `CV_IO_MAX_IMAGE_PIXELS` safety limit)
   where `cv2.imdecode` instead *raises* `cv2.error`. Both outcomes are public decode failures:
   `load_image` catches `cv2.error` around the `cv2.imdecode` call specifically (nothing broader --
   not `Exception`, not `OSError`, not `MemoryError`) and re-raises `ValueError` naming the source
   path, chaining the original `cv2.error` as `__cause__`; a `None` result is likewise turned into
   the same `ValueError`, naming the same path. Filesystem errors from `Path.read_bytes()` (case 1
   above) are never caught by this -- only the `cv2.imdecode` call itself is wrapped.

Both `ValueError` cases (empty file, undecodable file -- whether by `None` or `cv2.error`) use one
exception type -- not a separate exception per failure kind -- consistent with `_decode_grayscale`'s
own caller (`build_perceptual_hash_manifest`) treating "empty" and "undecodable" as the same failure
mode (`decoded is None`) before raising its own `ValueError`. This document does not extend that
`cv2.error` normalization to `_decode_grayscale`/`build_perceptual_hash_manifest` itself -- that is
existing, previously shipped, separately maintained behavior and stays out of this document's scope
(§14 remains the frozen relationship).

Validation order, frozen: (1) normalize/validate `path`'s type contract (§8) -- no I/O yet; (2)
validate `mode` is one of the three allowed literals (§12 below) -- still no I/O, so an invalid
call fails fast before any filesystem access; (3) read bytes (native `OSError` propagates); (4)
check for an empty buffer (`ValueError` if empty); (5) `cv2.imdecode` (`cv2.error` normalized to
`ValueError`); (6) check for a `None` result (`ValueError` if undecodable).

## 12. Mode validation

Verified against the real, existing precedent for every other `Literal`-typed closed-choice
parameter in this codebase (§3): `_validation.require_one_of(value, allowed, name)` raises
`ValueError` -- never `TypeError` -- for any value not in `allowed`, including a value of an
entirely different type (a different string, a raw `cv2.IMREAD_COLOR` integer, a plain `int`, a
`bool`, an unrelated `Enum` member, `None`).

**Post-merge review found this incomplete for genuinely arbitrary runtime objects.**
`require_one_of`'s `value not in allowed` membership check relies on `==`/`bool()`, which is only
safe once `value` is known to be directly, unambiguously comparable -- a 0-d NumPy array (e.g.
`np.array("color")`) compares element-wise-equal to a matching string and would be silently
*accepted* as a legal mode rather than rejected, since the underlying `dict` lookup that follows
uses a *different* key than the accepted string; a multi-element NumPy array (e.g.
`np.array(["color", "x"])`) makes `bool()` raise `"truth value of an array... is ambiguous"`
instead of the controlled `ValueError` this API promises. Neither is a hypothetical: both were
reproduced directly against the merged code.

`load_image` therefore gates on `isinstance(mode, str)` **before** calling `require_one_of`, which
is otherwise reused completely unchanged:

```python
if not isinstance(mode, str):
    raise ValueError(f"mode must be one of {_MODES}, got {mode!r}")
require_one_of(mode, ("color", "grayscale", "unchanged"), "mode")
```

Every runtime object -- comparable or not, hashable or not -- resolves to the same controlled
`ValueError` this way: a non-`str` is rejected immediately by the local gate (with a message in
`require_one_of`'s own wording style); a `str` that isn't one of the three literal values is
rejected by `require_one_of` exactly as before. This is a `load_image`-local gate, not a change to
`_validation.require_one_of` itself -- the shared helper, and every one of its fourteen other
existing call sites, is untouched; this document does not propose widening `require_one_of`'s own
contract or auditing its other callers, since none of them are known to receive arbitrary
uncontrolled runtime objects the way a public `mode` keyword argument can.

## 13. Module placement

Three candidates, compared on semantic ownership, likely future API, import-cycle risk, and name
collision/confusion, as required (not defaulted to wherever the existing private decoder happens to
live):

- **`src/improcv/dataset.py`**: already hosts `_decode_grayscale`, `build_perceptual_hash_manifest`,
  `split_dataset`/`DatasetSplit` -- but every one of those is a *dataset-workflow* operation
  (discovery-driven, root-relative, splitting, manifest-building). `load_image` has no dataset
  concept at all: it accepts one arbitrary path and returns one decoded array, usable identically
  whether or not that path came from any dataset-discovery workflow. Placing it in `dataset.py`
  would misstate its actual scope and was explicitly ruled out for that reason -- not "because the
  existing decoder happens to be there," but because dataset-specific ownership does not fit a
  generic single-file primitive.
- **`src/improcv/loading.py`**: descriptive and avoids any naming collision, and gerund-style module
  names are not unprecedented here (`discovery.py`, `denoising.py`). Its weakness: it only
  describes half of the filesystem-boundary-crossing role this module occupies -- a symmetric,
  plausible future write primitive (`save_image`, an explicit non-goal of this slice, §20, but not
  an implausible future one) would not fit a module literally named "loading."
- **`src/improcv/io.py`**: names the actual, single, cohesive responsibility -- crossing the
  filesystem <-> decoded-array boundary in either direction -- and matches an established external
  convention in the same problem space (`skimage.io`, `imageio`'s own naming, `astropy.io`) for
  exactly this kind of function, which is real naming precedent, not merely this project's opinion.
  Collision risk with Python's stdlib `io` module is real in the abstract but not in practice:
  `improcv.io` is only ever reached via its full dotted path (`import improcv.io` or `from improcv
  import io as improcv_io`), never via a bare `import io` inside `improcv` itself, and the same
  stdlib-shadowing shape already exists safely in the ecosystem precedents just cited.

**Decision: `src/improcv/io.py`.** Import-cycle risk: `io.py` depends only on `improcv.types`
(`Image`, `ImageU8`) and `improcv._validation` (`require_one_of`), plus `os`/`pathlib`/`cv2`/
`numpy` -- it does not import `dataset.py` or `discovery.py`, so no cycle exists in either
direction; `dataset.py` could import from `io.py` in the future (§14) without creating one.

## 14. Relationship to `_decode_grayscale`

Three options were compared, as required:

- **(A) Keep the existing private decoder unchanged; `load_image` implements its own, separate
  read/decode logic.**
- **(B) Extract one small shared private low-level read/decode helper**, used by both `_decode_
  grayscale` and `load_image`.
- **(C) Reimplement `build_perceptual_hash_manifest`'s grayscale decoding through the new public
  `load_image`.**

(C) is rejected outright: the task constraint is explicit and non-negotiable here --
`build_perceptual_hash_manifest`'s documented behavior, decode policy, error ordering, and exact
exception semantics **must not change** as a side effect of this design. `_decode_grayscale`
signals failure by returning `None` for its caller to turn into a specific, identifier-qualified
`ValueError` message (`f"failed to decode image {identifier.as_posix()!r} from {str(path)!r}"`);
`load_image` is a fully public function that raises its own `ValueError` directly. Routing the
manifest builder through `load_image` would mean reconciling these two different signaling
conventions at the one shared call site, for a function whose public contract this design is
required to leave untouched -- an unjustifiable risk for zero required benefit.

(B) would eliminate the duplication between `_decode_grayscale`'s body and `load_image`'s `mode=
"grayscale"` path, but that duplication is six lines of an extremely stable, already-proven idiom
(`read_bytes()` -> empty check -> `frombuffer` -> `imdecode`) -- not complex logic. Introducing a
shared private primitive now would add an abstraction whose only job is to reconcile, once again,
two different failure-signaling conventions (`None`-return for `_decode_grayscale`'s caller vs.
`raise` for `load_image`'s direct caller), for a savings of a few lines, contrary to this project's
own stated preference (`CLAUDE.md`: "no functions bundling several independent operations," "no
premature abstraction... until several real use cases justify one").

**Decision: (A).** `_decode_grayscale` is left completely unchanged; `load_image` implements its
own read/decode/validate sequence independently. `build_perceptual_hash_manifest`'s public
behavior, decode policy, error ordering, and documented exception semantics are unaffected by this
design -- verified by inspection that no line of `dataset.py` is touched by it. Revisit only if a
third, genuinely identical call site appears later.

## 15. Format and extension behavior

`load_image` is not a discovery API, so the file's extension/suffix is never inspected, matched
against an allow-list, or used to guess a decoder. Decode capability is determined entirely by
`cv2.imdecode` against the file's actual encoded bytes. Concretely:

- Valid PNG bytes stored under an oddly named or extensionless file: decodes normally -- content,
  not name, governs.
- A corrupt/truncated JPEG: `cv2.imdecode` returns `None` -> `ValueError` (§11).
- A codec OpenCV's build does not support: `cv2.imdecode` returns `None` -> `ValueError` (§11);
  `load_image` does not attempt to distinguish "unsupported codec" from "corrupt file" -- both are
  "OpenCV could not decode these bytes," which is exactly what the frozen `ValueError` means.

No allowed-extensions list of any kind exists in this design.

## 16. Animated/multipage formats (explicit exclusion)

`load_image` does not iterate frames of an animated GIF/APNG/animated WebP or a multipage TIFF, has
no frame-selection parameter, does not call `cv2.imdecodemulti`, and makes no promise about which
frame (if any) a multi-frame source yields. If `cv2.imdecode` for a given format happens to return
a single raster for a multi-frame file (its own internal, undocumented-by-this-project choice of
which frame), `load_image` merely returns whatever that one call produced -- with no frame-order,
frame-count, or frame-timing semantics attached to it.

## 17. Mask non-guarantee

`load_image` has no mask-specific semantics of any kind, for any mode. In particular,
`load_image(pair.mask, mode="unchanged")` is **not** presented here as a safe, general-purpose mask
loader. `UNCHANGED` does not guarantee: preservation of palette-encoded class indices as a label
map (§5, §6 showed the opposite -- palette PNGs are expanded to BGR color, not preserved as
indices); a single-channel result (a mask file could itself be encoded with 3 or 4 channels); a
specific class-index dtype across different mask encodings; or any label validation whatsoever.
`load_image` is exactly and only "decode these bytes with OpenCV's chosen `IMREAD_*` policy,"
nothing more. A dedicated, mask-aware loader (`load_image_mask_pair` or similar) is a separate,
unstarted, future design decision, explicitly out of scope here (§20).

## 18. Relationship to `Mask`

`improcv.types.Mask` (`npt.NDArray[np.uint8]`, documented as a 0/255 binary convention) is not used
as any `load_image` overload's return type, for any mode -- including `unchanged` on an actual mask
file -- because `load_image` makes no binary/label claim, only a decode dtype/shape one (§5, §7).

Separately: reading `augmentation.py` for this design surfaced that its own mask parameters
(`apply_flip`/`apply_crop`/`apply_affine`/`apply_perspective`) are typed as bare `np.ndarray`, not
`Mask`, and accept a broader dtype range than `Mask`'s documented binary 0/255 convention (its own
comments describe "a deliberately narrower dtype contract than images," excluding `int16` only for
the perspective path specifically -- i.e. multi-label integer masks are handled elsewhere in this
codebase, not just strict binary ones). This is noted here as a **pre-existing, separate type-model
documentation gap** between `types.Mask`'s stated convention and `augmentation.py`'s actual
broader-than-binary mask handling. It is **not fixed by this design** and is **not a prerequisite**
for `load_image` -- it is unrelated to what `load_image` returns for any mode.

## 20. Complexity

Reading is `O(encoded file size)` in time, and adds `O(encoded file size)` memory for the `bytes`
object `Path.read_bytes()` returns (`np.frombuffer` over it is a zero-copy view, not an additional
allocation). Decode time and the decoded array's own memory footprint are entirely delegated to the
OpenCV codec and the image's own dimensions/channel count/dtype -- not characterized, bounded, or
benchmarked by this design, since no concrete performance risk was identified for a single-image,
non-batched primitive. No benchmark is added.

## 21. Determinism and reproducibility

For one OpenCV build/version, the same input bytes and the same `mode` produce a deterministic
decode result -- image decoding involves no RNG and no parallelism-induced nondeterminism in
current OpenCV codecs (unlike, for example, `stitch_images`' RANSAC-based estimation). **Bit-for-
bit identical decode output across different OpenCV versions, builds, codecs, or platforms is not
promised** -- consistent with the disclaimer `build_perceptual_hash_manifest`/the perceptual-hash
manifest contract already carries for the same underlying reason.

## 22. Direct `cv2.imdecode` equivalence (central invariant)

For any successful call (no `OSError`, non-empty buffer, successful decode), the following holds
for the same OpenCV build/version:

```text
load_image(path, mode=X) is array-equal (np.array_equal) to
cv2.imdecode(np.frombuffer(path.read_bytes(), dtype=np.uint8), FLAG(X))
computed against the exact same bytes.
```

Beyond the path-contract validation (§8), the empty-buffer check, and the named decode-failure
(§11), `load_image` performs **no additional transformation** on the decoded array -- no resize, no
color conversion beyond what `mode` itself selects, no normalization, no copy-with-modification.
The two `uint8` modes' static type is narrowed via a type-checking-only cast with no run-time effect
on the array's data or memory.

- **Isolation checks**: exactly one `Path.read_bytes()` call per `load_image` call (no re-read, no

- **Typing**: the four Pyright cases already verified in §7, captured as a permanent typing-check

  verification.

## 24. Future property/differential test plan (no Hypothesis; not executed in this design PR)

For **lossless formats only** (PNG): generate deterministic synthetic arrays (fixed seed, small
shapes, covering each dtype/channel combination from §5/§6's tables), encode via `cv2.imencode`,
write to a temp file, load via `load_image(path, mode=X)`, and compare against **`cv2.imdecode`
applied directly to the exact same in-memory encoded bytes with the corresponding flag** -- the
oracle is direct `cv2.imdecode`, never the pre-encode original array, since §22's invariant is
specifically about matching `cv2.imdecode`'s own output, not about lossless round-tripping through
every mode (a `color`-mode load of a 16-bit source, for instance, is correctly *not* equal to the
original array; it is only required to equal `cv2.imdecode(..., IMREAD_COLOR)` on the same bytes).
**JPEG is explicitly excluded** from this property test -- JPEG is lossy, so no pixel-identical
assertion against either the original array or a re-decode is meaningful for it; JPEG is exercised
only by the EXIF-orientation tests (§23), which assert on shape, not pixel values.

## 27. Explicit out-of-scope list

- `load_image_mask_pair` or any other mask-aware/pair-aware loader.
- Mask semantics, mask normalization, or mask label validation of any kind.
- Pair shape/dtype/correspondence validation between an image and a mask.
- Batch loading, dataset iteration, or any multi-file operation.
- Prefetching, background loading, or worker threads/processes.
- Resize-on-load, or any spatial transform applied during/after decode.
- Color conversion beyond the three selected decode modes (e.g. no on-the-fly HSV/Lab output).

- `IMREAD_ANYDEPTH`/`IMREAD_ANYCOLOR`/`IMREAD_IGNORE_ORIENTATION`/`IMREAD_REDUCED_*` or any other
  `cv2.IMREAD_*` flag not explicitly chosen as one of this slice's three modes.
- A metadata API (EXIF, ICC profile, or any other embedded metadata) of any kind.
- EXIF rewriting, stripping, or orientation normalization beyond OpenCV's own delegated default.
- An animated/multipage frame API (`cv2.imdecodemulti`, frame selection, frame count, frame
  timing) of any kind.
- URL or network loading of any kind -- `path` is always a local filesystem path.
- A public in-memory `bytes` buffer decoder (e.g. `decode_image_bytes`) -- only a filesystem-path
  entry point is added in this slice.
- Caching of any kind.
- A write/save API (`save_image` or equivalent).

## 29. Naming review

`load_image` follows this codebase's existing `verb_noun` public-function naming pattern
(`find_contours`, `detect_and_compute`, `discover_images`, `build_perceptual_hash_manifest`,
`compare_perceptual_hash_manifests`). `ImageReadMode` follows the `<Noun><Qualifier>` pattern used
by the fourteen existing `Literal` type aliases that describe a mode/method choice (`FeatureMethod`,
`StitchMode`, `InpaintMethod`, `SeamlessCloneMode`, `RetrievalMode`, `HoughCircleMethod`) -- "Read"
distinguishes it from a hypothetical future write-mode type, consistent with `io.py`'s own
read/write-boundary naming rationale (§13). No alias, shorter name, or "just in case" synonym is
introduced alongside it.

## 30. Alternatives considered

- **`ImageReadMode` as an `Enum`** -- rejected in §3; the sole existing `Enum` precedent's use case
  (serialized manifest field) does not apply to a transient function parameter.
- **Two-mode set (`color`/`unchanged`)** -- rejected in §4 with direct empirical evidence that
  `grayscale` is not interchangeable with `color` + `ensure_gray`, plus real existing internal
  precedent and near-zero marginal cost for keeping it as a third mode.
- **`dataset.py` / `loading.py` as the module** -- both compared and rejected in §13 in favor of
  `io.py`.
- **Sharing a helper with `_decode_grayscale` (Option B) or routing the manifest builder through
  `load_image` (Option C)** -- both compared and rejected in §14 in favor of keeping the two
  decoders fully independent (Option A).
- **Raw `cv2` integer flags as the `mode` type** -- rejected in §3 as conflicting with this slice's
  curated, frozen mode set and this codebase's established closed-choice convention.
