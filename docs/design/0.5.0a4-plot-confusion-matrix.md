# Design: `plot_confusion_matrix` (`0.5.0a4` feature slice)

Status: implemented in `0.5.0a4.dev0` (`src/improcv/visualization/evaluation.py`). Not yet
released. Corrected post-merge, pre-implementation — see §18 for exactly what changed and why (no
feature-scope change; §4 and §6 below already reflect the corrected, final decisions). See §19 for
implementation notes (factual details only; no frozen decision was altered).

## 1. Status / scope

This is the selected next feature slice of the `0.5.0` line, per the `0.5.0a4` product audit
(base `3eb62e40babe335b300d528584982886a6c0d10b`, `0.5.0a4.dev0`, `__all__` count 198), which
ranked a narrow confusion-matrix plotting primitive first among five audited candidates.

This document re-verifies the audit's architectural assumptions from the current repository state
rather than trusting them, re-derives the demo's rendering behavior as evidence rather than
specification, and freezes exact numeric/validation/normalization semantics the audit did not
itself settle — in particular a real, demonstrated bug in the demo's own text-annotation logic
that a public function must not inherit (§3).

## 3. Re-auditing the demo renderer as evidence, not specification

`demos/classification_report.py::_render_confusion_matrix` (lines 374-412 at current base SHA),
read in full:

```python
def _render_confusion_matrix(
    ax: Axes, confusion: im.ConfusionMatrixResult, labels: Sequence[int]
) -> None:
    matrix = confusion.matrix
    positions = list(range(len(labels)))

    ax.imshow(matrix, cmap="Blues", aspect="equal")
    ax.set_xticks(positions)
    ax.set_xticklabels([str(label) for label in labels])
    ax.set_yticks(positions)
    ax.set_yticklabels([str(label) for label in labels])
    ax.set_xlabel("predicted label")
    ax.set_ylabel("true label")
    ax.set_title("Confusion matrix", fontsize=10, loc="left")

    max_value = float(matrix.max()) if matrix.size else 0.0
    for row in positions:
        for column in positions:
            value = int(matrix[row, column])
            normalized = value / max_value if max_value > 0 else 0.0
            text_color = "white" if normalized > 0.5 else "black"
            ax.text(column, row, str(value), ha="center", va="center",
                     color=text_color, fontsize=12)

    ax.text(0.5, -0.16, _CONFUSION_MATRIX_CAPTION, transform=ax.transAxes,
             ha="center", va="top", fontsize=8)
```

Classification of every behavior:

| Behavior | Classification | Disposition for the public function |
|---|---|---|
| `ax.imshow(matrix, ...)` | Essential | Keep — this is the whole point of the function |
| `cmap="Blues"` | Reasonable public default | Keep as fixed default, no parameter (§6) |
| `aspect="equal"` | Reasonable public default | Keep, fixed |
| `set_xticks`/`set_yticks` at integer positions | Essential | Keep — one tick per label, unconditionally |
| `set_xticklabels`/`set_yticklabels` = `str(label)` | Essential | Keep exactly |
| `set_xlabel("predicted label")`, `set_ylabel("true label")` | Essential | Keep exactly — this is `ConfusionMatrixResult`'s own documented contract ("rows are true labels, columns are predicted labels", `evaluation.py:96-97`), not a styling choice |
| `set_title("Confusion matrix", fontsize=10, loc="left")` | Demo-specific styling | **Drop** — `loc="left"` and `fontsize=10` were tuned for this demo's specific multi-panel gridspec layout; matches `plot_histogram`'s own precedent of setting no title at all |
| `value = int(matrix[row, column])` | **Demonstrably wrong/incomplete** | **Fix** — see below, this silently truncates a `float64` weighted matrix |
| `normalized = value / max_value` for text-contrast | **Demonstrably wrong** (for a public function) | **Fix** — see §4, does not correspond to `imshow`'s actual color mapping whenever `matrix.min() > 0` |
| `fontsize=12` for cell text | Demo-specific styling | **Drop** — tuned for the demo's small panel; let matplotlib's own default apply |
| Bottom caption text (`_CONFUSION_MATRIX_CAPTION`) | Demo-specific styling | **Drop** — redundant with the axis labels above; useful in a dense multi-panel report figure, not needed in a standalone plot |

**The `int(matrix[row, column])` bug, made concrete.** `ConfusionMatrixResult.matrix` is
documented as "exactly `int64`... exactly `float64`... when [`confusion_matrix`] was called with an
explicit `sample_weight`" (`evaluation.py:98-101`). For a `float64` matrix such as
`[[1.5, 0.25], [0.0, 3.75]]`, `int(matrix[0, 0])` silently discards the fractional part and
displays `"1"` where the true effective weight was `1.5` — a real, silent, semantically wrong
truncation for any weighted confusion matrix. This design freezes the fix in §3's formatting
policy below; a public function **must not** reproduce this line unchanged.

## 4. Weighted confusion matrices — exact formatting policy (frozen)

**Corrected (§18): the originally-frozen `%g` policy is replaced.** `%g` defaults to 6
significant figures and is *lossy* at both ends of its range, not merely compact — verified
directly:

```python
>>> f"{123456.789:g}"
'123457'          # silently rounds away the fractional part
>>> f"{1234567.0:g}"
'1.23457e+06'     # loses the exact integer value to scientific-notation rounding
```

This is a real information loss, not a disclosed-but-acceptable trade-off — the original design's
framing of it as merely "unlikely to matter in practice" understated the defect. A public function
must not ship a formatter that is *sometimes* exact and sometimes silently approximate depending on
magnitude, with no way for a caller to tell which happened from the rendered text alone.

**Corrected, frozen formatting rule — compared, verified directly, no configuration parameter:**

| Option | `1.5` | `2.0` | `0.25` | `123456.789` | `1e-8` | Exact? |
|---|---|---|---|---|---|---|
| A. `str(float(value))` | `"1.5"` | `"2.0"` | `"0.25"` | `"123456.789"` | `"1e-08"` | **Yes, always** |
| B. `repr(float(value))` | identical to A in Python 3 (verified) | | | | | Yes |
| C. `f"{value:g}"` (original, rejected) | `"1.5"` | `"2"` | `"0.25"` | `"123457"` | `"1e-08"` | No — lossy at large magnitude |
| D. NumPy shortest/unique positional formatting | not needed — Python's own `float.__repr__` already implements shortest-round-trip formatting since Python 3.1; introducing a NumPy-specific formatter would add nothing and a needless coupling | | | | | Yes |

**Frozen rule:**

- `confusion.matrix.dtype == np.int64` → annotation text is `str(int(value))` — unchanged from the
  original design, already exact, matches the demo's existing correct-for-this-dtype behavior.
- `confusion.matrix.dtype == np.float64` → annotation text is `str(float(value))` (equivalently
  `repr(float(value))` — confirmed identical in Python 3) — the shortest decimal string that
  round-trips to the exact same `float64` value, for every magnitude, with no configurable
  precision and no silent rounding.

This also cleanly preserves the dtype distinction the original design wanted: `int64` `2` displays
as `"2"`; `float64` `2.0` displays as `"2.0"` — the trailing `.0` is not noise, it is the
annotation's own signal that this cell came from a weighted (`float64`) matrix, distinguishable at
a glance from an unweighted (`int64`) exact count.

**No remaining precision caveat.** Unlike the rejected `%g` policy, this rule has no accepted
information-loss trade-off to disclose — `str(float(value))`/`repr(float(value))` is exact by
construction for every representable `float64` value, at every magnitude tested
(`123456.789` → `"123456.789"`, not `"123457"`; very large/small magnitudes fall back to
scientific notation, e.g. `1e+16`/`1e-05`, but still exactly, never approximately — verified
directly). No future format/precision parameter is needed to fix a defect this policy does not
have; §11/§16 already correctly treat a future format parameter as optional convenience, not a
correctness fix.

**Wording check (required by the audit):** neither the kept axis labels ("predicted label"/"true
label") nor the dropped caption ever use the word "count" — no wording implies weighted values are
observation counts, and none needs to be added or removed for this reason.

## 5. Color normalization and text contrast — exact policy (frozen)

Verified directly (not assumed), current environment, three cases:

```python
>>> matrix = np.array([[1.5, 0.25], [2.0, 3.75]])  # min = 0.25, not 0
>>> fig, ax = plt.subplots(); im = ax.imshow(matrix, cmap="Blues", aspect="equal")
>>> im.get_clim()
(0.25, 3.75)          # matplotlib's own default: autoscales to (data.min(), data.max())
>>> im.norm(0.25)
0.0
>>> 0.25 / 3.75        # the demo's own formula for this same cell
0.06666666666666667   # WRONG — does not match im.norm(0.25) above
```

This is a real, demonstrated defect in the demo's own `normalized = value / max_value` heuristic:
it implicitly assumes `vmin=0`, but matplotlib's default `imshow` normalization (no `vmin`/`vmax`
given) autoscales to `(matrix.min(), matrix.max())` — whenever a confusion matrix's minimum cell
value is greater than zero (a real, legal case: a weighted matrix, or any matrix with no
zero-support cell at all), the demo's contrast formula and the actual displayed color silently
disagree. The demo itself never hits this because its own fixed example always contains a `0`
cell; a public function cannot assume that.

**Frozen policy:**

1. Fix `vmin=0` explicitly in the `imshow` call — `vmin=0, vmax=float(matrix.max())`. This is
   semantically meaningful for a confusion matrix specifically (a `0` cell — "no observations/no
   effective weight" — is a real, meaningful floor, not an arbitrary choice), and makes the
   original design's implicit assumption actually true.
2. Derive text contrast from the *actual* image artist's norm, never a hand-rederived formula:
   `normalized = image.norm(value)` where `image` is the `AxesImage` object `ax.imshow(...)`
   returns. This guarantees the annotation color is coherent with the real displayed cell color
   by construction, and remains correct even if a future slice changes the normalization policy.
3. Threshold unchanged from the demo: `"white" if normalized > 0.5 else "black"`.

**All-zero matrix**, verified directly: `vmin=0, vmax=0.0` (matplotlib's own degenerate-range
handling, no error, no warning observed) → `image.norm(0)` → `0.0` → black text on the lightest
`"Blues"` shade — legible, no crash. **1×1 matrix**, e.g. `[[5]]`: `vmin=0, vmax=5` →
`image.norm(5) == 1.0` → white text on the darkest shade — legible. Both verified directly, not
assumed.

## 6. Validity of `ConfusionMatrixResult` inputs — validation reuse (corrected, §18)

`ConfusionMatrixResult` (`evaluation.py:92-124`) has **no** `__post_init__` — confirmed directly by
reading its full source — so it is not self-validating; any combination of `matrix`/`labels` can
be constructed by hand. Its own docstring also confirms `confusion_matrix` can legally produce an
**all-zero** matrix (explicit `labels`, empty or all-zero-weight input).

**Corrected finding.** `evaluation.py` already has a private helper, `_require_confusion_matrix_result`
(`evaluation.py:1422-1469`), read in full for this correction. It validates *exactly* the
structural/value invariants plotting needs — and, critically, its own comment (`evaluation.py:1467-1469`)
confirms it **deliberately excludes** the "at least one observation" / non-zero-total check:

> "The 'at least one observation' check is intentionally not here: it requires summing (potentially
> huge) matrix values, which `_compute_classification_metrics` does safely... right before it's
> needed."

That stricter, non-zero-total check lives only in the separate metrics-computation path
(`_compute_classification_metrics`, called from `classification_metrics_from_confusion_matrix`) —
**not** in `_require_confusion_matrix_result` itself. The original design's §15 entry ("Reusing
`evaluation.py`'s own confusion-matrix validation — rejected... would wrongly reject a legal,
non-empty, all-zero confusion matrix") conflated these two different things. `_require_confusion_matrix_result`
does **not** reject an all-zero matrix — only the separate metrics path does, for its own,
unrelated reason (it needs a non-zero denominator to compute ratios). The original design's
underlying goal (all-zero matrices must remain legal for plotting) was correct; the reasoning for
achieving it (write a new, independent validator) was not — the existing helper already gives the
correct behavior for free.

**Corrected decision: `plot_confusion_matrix` reuses `_require_confusion_matrix_result` directly**
(imported privately: `from improcv.evaluation import _require_confusion_matrix_result`), rather
than duplicating the same structural checks in a new private function inside `improcv.visualization`.
Reasons: one source of truth for what makes a `ConfusionMatrixResult` structurally valid; the
existing helper is already exactly right for plotting's needs (no total-based rejection); no risk
of the two validators drifting apart over time; `evaluation.py` stays matplotlib-free (the helper
itself has no rendering concerns, so importing it into `visualization` introduces no matplotlib
dependency in the other direction); and `visualization` privately depending on `evaluation` creates
no import cycle (`evaluation.py` never imports anything from `visualization`, confirmed directly).
The helper stays private — `_require_confusion_matrix_result` is not added to any `__all__` and is
not part of the public API; this is a private, cross-module reuse, not a new public symbol.

**Exact checks performed by the reused helper** (`evaluation.py:1422-1469`, in this exact order —
the design does not reorder or reimplement any of this):

1. `isinstance(confusion, ConfusionMatrixResult)` — `TypeError`.
2. `isinstance(confusion.matrix, np.ndarray)` — `TypeError`.
3. `matrix.ndim != 2` — `ValueError`.
4. Non-square (`matrix.shape[0] != matrix.shape[1]`) — `ValueError`.
5. Empty / `0×0` matrix (`matrix.shape[0] == 0`) — `ValueError` — distinct from an all-zero-but-
   non-empty matrix, which *is* legal (see below).
6. Dtype-specific: for an `int64` matrix, negative values raise `ValueError`; for a `float64`
   matrix, non-finite values (`NaN`/`Inf`) raise `ValueError` and negative values raise
   `ValueError`; any other dtype raises `TypeError` (matches `ConfusionMatrixResult`'s own
   documented "exactly `int64` or exactly `float64`" contract).
7. `isinstance(confusion.labels, tuple)` — `TypeError`.
8. Each label is a plain (non-`bool`) `int` — `TypeError`.
9. `len(labels) != matrix.shape[0]` — `ValueError`.
10. Duplicate values in `labels` — `ValueError`.

| Case | Legal for plotting? | Failure mode |
|---|---|---|
| `confusion` is not a `ConfusionMatrixResult` | No | `TypeError` |
| `confusion.matrix` is not an `np.ndarray` | No | `TypeError` |
| `matrix.ndim != 2` | No | `ValueError` |
| Non-square | No | `ValueError` |
| Empty / `0×0` matrix | No | `ValueError` |
| `matrix.dtype` not exactly `int64`/`float64` | No | `TypeError` |
| Negative values (either dtype) | No | `ValueError` |
| Non-finite values (`float64` only — `int64` cannot represent `NaN`/`Inf`) | No | `ValueError` |
| `labels` not a tuple of plain (non-`bool`) `int` | No | `TypeError` |
| `len(labels) != matrix.shape[0]` | No | `ValueError` |
| Duplicate values in `labels` | No | `ValueError` |
| **Structurally valid, non-empty, all-zero matrix** | **Yes** | Renders — `vmin=vmax=0` handled gracefully (§5); `_require_confusion_matrix_result` never checks the total |
| **1×1 matrix** | **Yes** | Renders normally |
| `int64` matrix | Yes | Exact integer annotations (§4) |
| `float64` matrix | Yes | `str(float(value))` annotations (§4) |

**Frozen validation/error ordering:**

1. `_require_valid_axes(ax)` — `TypeError` if `ax` is neither `None` nor an `Axes`. No figure
   created yet, and `confusion` is not inspected yet either.
2. `_require_confusion_matrix_result(confusion)` — the 10 checks above, in that exact order,
   reused verbatim from `evaluation.py`.
3. Only now: `_resolve_axes(ax)` (creates a figure if `ax is None`).
4. Render (`imshow`, ticks, labels, annotations).

This still mirrors `plot_histogram`'s own "validate before creating a figure" discipline
(`image.py:174-189`) — `ax` is validated first, nothing else is inspected until that passes, and a
figure is created only after every other check has already succeeded.

**Parameter naming — corrected (§18).** The function's first parameter is named **`confusion`**,
not `result`. Two reasons, both from direct repository evidence: (1) `classification_metrics_from_
confusion_matrix(confusion: ConfusionMatrixResult, ...)` (`evaluation.py:457`) already establishes
`confusion` as this project's own name for a `ConfusionMatrixResult`-typed parameter; (2) reusing
`_require_confusion_matrix_result` verbatim means its error messages already say `"confusion must
be a ConfusionMatrixResult"`/`"confusion.matrix must be..."`/`"confusion.labels must be..."` —
naming the public parameter anything else (e.g. `result`) would make the function's own raised
error messages reference a name the caller never typed, a real, avoidable rough edge.

## 7. Module placement (frozen: new file, not `image.py`)

Compared:

- **A. `visualization/image.py`** — the audit's own tentative assumption. Rejected: the module's
  own docstring scopes it to "Image and histogram display helpers" — a confusion matrix is
  evaluation-result visualization, a different concern, and mixing it in sets a bad precedent for
  the ROC/PR-curve plotting this project has already flagged as a likely future slice.
- **B. New `visualization/evaluation.py`** — **chosen**. Semantically correct home for
  evaluation-result plotting; leaves a natural, uncluttered place for future ROC/PR-curve
  functions without touching `image.py`'s scope.
- **C. Another existing module** — no other module is a plausible fit (`evaluation.py` itself is
  matplotlib-free and must stay that way; nothing else in the tree touches rendering).

**A necessary consequence, frozen here for the implementation PR:** `_require_valid_axes`/
`_resolve_axes` (currently private to `image.py`) must be shared with the new file, not
duplicated — two independent copies of the same axes-validation logic would be exactly the kind
of drift risk this project has consistently avoided elsewhere (e.g. `classification_report`'s own
"single source of truth" reasoning). The implementation PR should factor them into a small shared
private module (a plausible, non-frozen name: `visualization/_axes.py`), imported by both
`image.py` and the new `evaluation.py`. The exact filename/location of this shared helper is not
frozen; the requirement that it be shared, not duplicated, is.

Regardless of internal placement, the frozen public import path is:

```python
from improcv.visualization import plot_confusion_matrix
```

**Corrected (§18) — one new private, one-directional dependency.** Per §6's corrected validation
decision, the new module privately imports `_require_confusion_matrix_result` from
`improcv.evaluation`. This is a one-directional dependency (`visualization` → `evaluation`); it
introduces no cycle, since `evaluation.py` never imports anything from `visualization` (confirmed
directly), and it introduces no matplotlib dependency into `evaluation.py`, since only
`visualization` imports matplotlib, never the reverse.

**Frozen signature** (final, incorporating §6's parameter-naming correction):

```python
def plot_confusion_matrix(confusion: ConfusionMatrixResult, ax: Axes | None = None) -> Axes:
```

## 8. Existing visualization conventions — reused unchanged

- `ax: Axes | None = None`, positional-or-keyword (matches both existing functions' exact
  signature style — neither uses keyword-only `*`).
- Validate-before-create ordering (§6), so invalid input with `ax=None` cannot leak an orphaned
  figure — the same reason `plot_histogram` calls `_require_valid_axes` before its own
  image/mask/bins validation and only calls `_resolve_axes` at the very end.
- Returns `Axes`. Never calls `plt.show()`. Never saves to a file.
- `pyplot` imported lazily, only inside `_resolve_axes` — no eager backend resolution merely from
  `import improcv.visualization`.
- The existing `ModuleNotFoundError`→`ImportError` guard in `visualization/__init__.py` covers the
  new function automatically; no separate guard needed.

## 9. Testability — plan (Axes-property assertions, no pixel snapshots)

Following `tests/test_visualization.py`'s established pattern exactly (32 existing tests, zero
pixel/PNG comparisons):

- `plot_confusion_matrix(confusion)` returns an `Axes`; `plot_confusion_matrix(confusion, ax=ax) is ax`.
- `ax=None` creates a new `Axes` (`isinstance(ax, Axes)`, matches `_resolve_axes` tests).
- Exactly one image artist: `len(ax.images) == 1`.
- `np.array_equal(np.array(ax.images[0].get_array()), confusion.matrix)`.
- `ax.images[0].get_cmap().name == "Blues"`; `ax.images[0].get_clim() == (0.0, float(confusion.matrix.max()))`.
- Tick positions/labels: `ax.get_xticks()`/`ax.get_yticks()` match `range(len(labels))`;
  `[t.get_text() for t in ax.get_xticklabels()] == [str(l) for l in confusion.labels]` (and same
  for y).
- `ax.get_xlabel() == "predicted label"`, `ax.get_ylabel() == "true label"`.
- Cell annotation texts: collect `ax.texts`, assert their string content matches the corrected
  formatting policy (§4) — for a `float64` fixture, include at least one value like `123456.789`
  and assert the annotation is the exact string `"123456.789"`, not a `%g`-rounded `"123457"`, to
  lock in the correction this document makes.
- Text-contrast policy: for a fixture with a known `vmax`, assert the darkest cell's annotation
  color is `"white"` and the lightest is `"black"`, matching `image.norm(...)`-derived expectation
  (§5) — not the old, wrong `value/max_value` formula.
- All-zero matrix fixture: renders without error, annotation text is `"0"` for every cell,
  `get_clim() == (0.0, 0.0)`.
- `1×1` matrix fixture: renders without error.
- Reordered / non-contiguous labels fixture (e.g. `labels=(30, 10, 20)` or `(100, 5)`): tick
  labels reflect the given order exactly, never sorted.
- Each row of the validation table in §6 gets its own `pytest.raises` test, including at least one
  manually-constructed, structurally-invalid `ConfusionMatrixResult` per failure mode.
- Invalid `ax` (non-`Axes`, non-`None`) raises `TypeError` before any figure is created —
  `plt.get_fignums()` unchanged across the raise, mirroring
  `test_plot_histogram_does_not_leave_a_figure_open_on_dtype_error`/`..._on_bad_bins` exactly.
- No `plt.show()` call anywhere (grep-level source check, matching this project's existing
  convention of citing an absence rather than assuming it).
- No eager `pyplot` import: a subprocess-level test mirroring
  `test_importing_visualization_does_not_import_pyplot` exactly.
- Missing-`viz`-extra `ImportError` path is already covered by the existing package-level guard
  test; no new test needed specifically for `plot_confusion_matrix`, since the guard fires before
  any function inside the subpackage is even reachable.

## 10. Demo relationship — migration recommended as a separate follow-up (not required here)

Recommended for a future implementation-adjacent PR, mirroring exactly how `classification_report`
itself was implemented first and the demo migrated as an independent follow-up (PR #191, then
PR #194): once `plot_confusion_matrix` exists, `demos/classification_report.py`'s
`_render_confusion_matrix` should be replaced by a call to the public function, with the
demo-specific styling this design explicitly drops (§3: the `loc="left"` title, the small cell
fontsize, and the bottom caption) re-added locally in the demo afterward if the demo still wants
them for its own multi-panel layout. This keeps the public function's contract from being
implicitly widened just to reproduce the full demo panel exactly, and gives a natural
differential-test target (compare the migrated demo's rendered `ax.images[0].get_array()`/tick
labels/annotation texts against the pre-migration values, exactly as `classification_report`'s own
demo migration did for its numeric fields). This design does not require the migration to happen
in the same PR that implements `plot_confusion_matrix`.

## 15. Alternatives considered

- **Reusing `value/max_value` for text contrast (the demo's own formula)** — rejected, demonstrated
  incorrect whenever `matrix.min() > 0` (§5).
- **Truncating float64 matrices with `int(...)` (the demo's own behavior)** — rejected, silently
  discards weighted fractional information (§3, §4).
- **`f"{value:g}"` for float64 annotations (this design's own originally-frozen choice)** —
  **corrected and rejected** (§4, §18): lossy at large magnitude (`123456.789` → `"123457"`),
  which is a real defect a public function should not ship, not a merely-unlikely edge case.
  Replaced by `str(float(value))`, which is exact at every magnitude and no less compact for
  realistic weight values.
- **A `cmap`/`annotate`/`title`/format-string parameter** — rejected for this slice; no forcing
  evidence, and `show_image`/`plot_histogram` both establish the "one fixed sensible default, no
  knob" precedent this project already follows.
- **Placing the function in `visualization/image.py`** — rejected; wrong semantic scope (§7).
- **A top-level `improcv.plot_confusion_matrix` re-export** — rejected; no existing precedent for
  a top-level visualization re-export, and inventing one now is not this design's job (§2).
- **A new, independent structural validator inside `improcv.visualization` (this design's own
  originally-frozen choice)** — **corrected and rejected** (§6, §18): `evaluation.py`'s existing
  private `_require_confusion_matrix_result` already implements exactly the right level of
  validation (structural/value only, no non-zero-total requirement) — duplicating it would only
  create a second copy to keep in sync. The original design's *goal* (all-zero matrices must stay
  legal) was correct; its reasoning that this required a brand-new validator was not.
- **Reusing `classification_metrics_from_confusion_matrix`'s full validation path (including the
  "at least one observation" / non-zero-total check)** — still rejected, and correctly so: that
  check exists only because ratio computation needs a non-zero denominator, a constraint plotting
  never has. This is a different helper from `_require_confusion_matrix_result` (§6) and remains
  out of scope for `plot_confusion_matrix`.

## 18. Post-merge correction record

This document was corrected after PR #195 merged it, before any implementation started. Two
factual/contract issues were found during post-merge review and corrected here; the overall
feature scope (§1-§3, §5, §7-§17 outside the specific edits below) is unchanged and was not
reopened.

1. **Validation reuse (§6).** The original design stated `plot_confusion_matrix` "must validate
   only what plotting itself structurally requires — not reuse or reimplement metrics validation"
   and proposed writing a new private validator inside `improcv.visualization`. Fresh, complete
   inspection of `evaluation.py::_require_confusion_matrix_result` (`evaluation.py:1422-1469`)
   found it already implements exactly that structural/value-only validation, with the
   metrics-specific non-zero-total check explicitly and deliberately absent (confirmed by its own
   comment, `evaluation.py:1467-1469`). The corrected decision reuses this existing private helper
   directly instead of duplicating it. As a direct consequence, the function's first parameter is
   renamed from `result` to `confusion`, matching both `classification_metrics_from_confusion_
   matrix`'s own established parameter name and the reused helper's own error-message wording.
2. **Float64 annotation formatting (§4).** The original design froze `f"{value:g}"`, correctly
   identifying that it avoids `int(...)`-style truncation but incorrectly framing its own
   6-significant-figure rounding at large magnitudes (`123456.789` → `"123457"`) as an acceptable,
   merely-disclosed trade-off. The corrected design freezes `str(float(value))` (equivalently
   `repr(float(value))`) instead — exact at every magnitude, verified directly, with no remaining
   precision caveat to disclose.

No other decision from PR #195 was reopened: the new `visualization/evaluation.py` module, the
`from improcv.visualization import plot_confusion_matrix` public import path with no top-level
re-export, the `198 → 198` / `2 → 3` public-symbol accounting, the `Axes | None` parameter pattern,
the fixed `"Blues"` colormap, the `vmin=0`/`vmax=float(matrix.max())` normalization, the
`AxesImage.norm`-derived text-contrast policy, all-zero-matrix legality, the absence of a
normalization/percentage mode, the absence of `title`/`cmap`/`annotate`/format knobs, the
ROC/PR/report-plotting exclusions, and the deferred demo migration all stand exactly as PR #195
