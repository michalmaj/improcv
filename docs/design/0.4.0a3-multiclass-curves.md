# Design: multiclass one-vs-rest ROC and precision-recall curves (`0.4.0a3` first slice)

Status: design only. No implementation, no public API added yet.

## 1. User problem

```text
I have a multiclass y_true and a score matrix y_score. improcv can already
compute per-class/macro/weighted/micro ROC AUC and average precision
(multiclass_roc_auc_score / multiclass_average_precision_score), but to get
the actual ROC/precision-recall curves per class I have to hand-write a loop
over labels and map each y_score column to roc_curve/precision_recall_curve
myself.
```

This is not a hypothetical gap. `demos/classification_report.py` states it directly in its own
docstring: *"This script does not call `roc_curve`/`precision_recall_curve` and does not render
any curve -- `improcv` does not yet have a public multiclass curve result type, and this demo
shows the stable score-based API, not a design for API that does not exist yet."* `README.md`
documents the same absence at the point multiclass score aggregation shipped: *"No public
multiclass curve types are introduced -- `roc_curve`/`precision_recall_curve` already give a
single class's own curve when called with the matching score column and `positive_label`."*
`ROADMAP.md`'s Phase 5 entry lists binary one-vs-rest curves and multiclass score-level
aggregation as already implemented, with no separate multiclass curve item yet named.

A prior read-only product/architecture audit for `0.4.0a3` recommended this slice over
alternatives (image/mask loading, batching, an evaluation report, duplicate-image grouping,
incremental manifest freshness, indexed/parallel manifest building). **That audit's proposed API
sketch (`MulticlassRocCurve`/`MulticlassPrecisionRecallCurve` as a `labels + curves` wrapper) is
treated here as a candidate, not a decision.** This document re-derives the result representation,
naming, validation semantics, and scope from the current code in `src/improcv/evaluation.py`, and
in one place (§8) explicitly rejects that candidate's `labels + curves` shape in favor of a
different one.

First slice scope, frozen: **per-class one-vs-rest curves only.** Not plotting, not a text/
structured report, not an aggregate (macro/weighted/micro) curve.

## 2. Exact contract inventory of the existing code

Read in full: `src/improcv/evaluation.py` (3358 lines), `src/improcv/__init__.py`,
`src/improcv/_validation.py`, `tests/test_evaluation.py` (5304 lines), `examples/
classification_evaluation.py`, `demos/classification_report.py`, `README.md`, `CHANGELOG.md`,
`ROADMAP.md`, `docs/design/0.4.0a1-manifest-comparison.md`, `docs/design/0.4.0a2-dataset-split.md`.

Signatures and result types that this design must fit alongside, exactly as they exist today:

```python
@dataclass(frozen=True, slots=True, eq=False)
class RocCurve:
    false_positive_rate: npt.NDArray[np.float64]
    true_positive_rate: npt.NDArray[np.float64]
    thresholds: npt.NDArray[np.float64]
    positive_label: int
    def __eq__(self, other: object) -> bool: ...   # np.array_equal per array field
    __hash__ = None

@dataclass(frozen=True, slots=True, eq=False)
class PrecisionRecallCurve:
    precision: npt.NDArray[np.float64]
    recall: npt.NDArray[np.float64]
    thresholds: npt.NDArray[np.float64]
    positive_label: int
    def __eq__(self, other: object) -> bool: ...
    __hash__ = None

def roc_curve(
    y_true: Sequence[int] | npt.NDArray[np.integer],
    y_score: Sequence[float] | npt.NDArray[np.floating] | npt.NDArray[np.integer],
    *,
    positive_label: int,
    sample_weight: Sequence[float] | npt.NDArray[np.floating] | npt.NDArray[np.integer] | None = None,
) -> RocCurve: ...

def precision_recall_curve(...) -> PrecisionRecallCurve: ...   # same signature shape as roc_curve

def multiclass_roc_auc_score(
    y_true: Sequence[int] | npt.NDArray[np.integer],
    y_score: npt.NDArray[np.floating] | npt.NDArray[np.integer],
    *,
    labels: Sequence[int] | npt.NDArray[np.integer],
    average: Literal["macro", "weighted", "micro"] | None = "macro",
    sample_weight: Sequence[float] | npt.NDArray[np.floating] | npt.NDArray[np.integer] | None = None,
) -> float | npt.NDArray[np.float64]: ...

def multiclass_average_precision_score(...) -> float | npt.NDArray[np.float64]: ...  # same shape
```

Key private helpers already implementing every piece of validation/normalization the new
functions need (all internal to `evaluation.py`; none of this lives in `_validation.py`, which is
a general geometry/image-argument helper module shared across unrelated public functions like
`resize`/`threshold` -- it has no evaluation-specific normalization and should not gain any for
this slice):

- `_normalize_explicit_labels(labels) -> tuple[int, ...]` -- type/empty/duplicate checks.
- `_normalize_label_sequence(y_true, "y_true") -> list[int]` -- type/element checks for `y_true`.
- `_normalize_score_matrix(y_score, n_rows, n_cols) -> npt.NDArray[np.float64]` -- 2-D-only,
  dtype/shape/NaN/Inf/signed-zero/exact-integer-representability checks, returns a new
  C-contiguous `float64` copy.
- `_normalize_sample_weight(sample_weight, n) -> npt.NDArray[np.float64]` -- same contract as
  `y_score`'s per-element numeric rules, non-negative, at least one positive value required.
- `_compute_effective_class_support(true_list, labels_tuple, weights, function_name) ->
  npt.NDArray[np.float64]` -- computes each label's effective support and raises `ValueError`
  naming *every* label with zero effective support at once.

`multiclass_roc_auc_score`'s validation order (traced directly from its body, lines 2053-2072):
`require_one_of(average, ...)` -> `_normalize_explicit_labels(labels)` -> reject `len(labels) < 2`
-> `_normalize_label_sequence(y_true, "y_true")` -> reject empty `y_true` -> reject any `y_true`
value not in `labels` -> `_normalize_score_matrix(y_score, ...)` -> `_normalize_sample_weight(...)`
if given -> (for `average != "micro"`) `_compute_effective_class_support(...)` -> per-column loop
calling `roc_auc_score`/`average_precision_score` -> postcondition check.

## 3. Input surface -- kept identical to the existing multiclass score functions

The new functions accept exactly the same types, in the same shapes, as `multiclass_roc_auc_score`/
`multiclass_average_precision_score`, with no narrowing:

```python
y_true: Sequence[int] | npt.NDArray[np.integer]
y_score: npt.NDArray[np.floating] | npt.NDArray[np.integer]
labels: Sequence[int] | npt.NDArray[np.integer]
sample_weight: Sequence[float] | npt.NDArray[np.floating] | npt.NDArray[np.integer] | None = None
```

No narrowing is introduced for any contractual reason:

- `y_true` stays `Sequence | ndarray` (not `ndarray`-only) -- `_normalize_label_sequence` already
  accepts a plain `list`/`tuple`, which is how `examples/classification_evaluation.py` calls
  `multiclass_roc_auc_score` today (`y_true = [20, 10, 30, ...]`, a plain `list[int]`); narrowing
  to `ndarray`-only would break that exact, already-published calling convention for a sibling
  function.
- `y_score` stays 2-D `ndarray` (`floating | integer`), never a `Sequence`-of-`Sequence`s --
  this is already `_normalize_score_matrix`'s own, deliberate restriction (documented reason:
  ragged-row detection and unvectorized per-element validation for nested lists is not worth it
  when a real caller's `y_score` already comes from a `predict_proba`/`decision_function`-style
  `ndarray`). The new functions reuse `_normalize_score_matrix` verbatim, so they inherit this
  restriction unchanged, not as a new narrowing decision of their own.
- `labels` stays `Sequence | ndarray` of integers, unsorted, required (no `labels=None` inference)
  -- identical to `multiclass_roc_auc_score`, for the same reason: column order in `y_score` has
  no canonical inference source.
- `sample_weight` stays `Sequence[float] | ndarray[floating] | ndarray[integer] | None` --
  identical to every other ranking function's `sample_weight`.

## 4. Validation matrix -- exact result for every listed case

Both new functions share one precheck order (§7 explains why ROC and PR share it exactly). Every
`ValueError`/`TypeError` message below is either reused verbatim from the existing helper it comes
from, or follows that helper's exact message pattern with the new function's own name substituted.

| Case | Result |
|---|---|
| `labels` empty | `ValueError("labels must not be empty")` -- from `_normalize_explicit_labels`. |
| `labels` length == 1 | `ValueError("multiclass ranking scores require at least 2 labels")` -- same explicit check and message `multiclass_roc_auc_score` already raises right after normalizing `labels`; reused verbatim since the reason is identical (a one-vs-rest curve needs at least one negative class to exist in the label universe, exactly the reasoning already documented for the score functions). |
| duplicate labels | `ValueError("labels must not contain duplicate values")` -- from `_normalize_explicit_labels`. |
| unsorted labels | **Not an error.** Legal and the default expectation -- `curves[i]` corresponds to `labels[i]` in exactly the order given (§10). |
| `y_true` empty | `ValueError("y_true must not be empty")` -- explicit check mirroring `multiclass_roc_auc_score`'s own. |
| `y_true` value outside `labels` | `ValueError(f"y_true[{index}] = {value} is not present in labels")` -- exact message pattern already used by `multiclass_roc_auc_score`/`multiclass_average_precision_score`. |
| `y_score` wrong ndim | Not an `ndarray` at all -> `TypeError`. An `ndarray` with `ndim != 2` -> `ValueError(f"y_score must be 2-D, got shape {value.shape}")` -- from `_normalize_score_matrix`. |
| `y_score` wrong row count | `ValueError(f"y_score must have shape ({expected_rows}, {expected_columns}), got {value.shape}")` -- one combined shape check covers rows and columns together, from `_normalize_score_matrix`. |
| `y_score` wrong column count | Same combined-shape `ValueError` as above. |
| `y_score` NaN/Inf | `ValueError("y_score must contain only finite values (no NaN or Inf)")` -- from `_normalize_score_matrix`. |
| `y_score` non-representable integer score | `ValueError(f"y_score[{row}, {column}] is not exactly representable as float64")` -- from `_exact_integer_matrix_to_float64`, naming the exact offending cell. |
| invalid `sample_weight` (wrong container/dtype/length) | `TypeError`/`ValueError` per `_normalize_nonnegative_weight_sequence`'s existing contract (wrong container type -> `TypeError`; wrong length, NaN/Inf, non-representable integer -> `ValueError`), reached via `_normalize_sample_weight`. |
| `sample_weight` negative value | `ValueError("sample_weight must contain only non-negative values")`. |
| all-zero `sample_weight` | `ValueError("sample_weight must contain at least one positive value")` -- from `_normalize_sample_weight`. |
| class with zero effective support | `ValueError(f"{function_name} requires positive effective support for every label; missing labels: {tuple(missing)}")` -- from `_compute_effective_class_support`, naming every missing label at once, with `function_name` = `"multiclass_roc_curve"` / `"multiclass_precision_recall_curve"`. |

Exact validation order for both new functions (no `average` parameter to check first, unlike the
score functions -- §6):

1. `labels_tuple = _normalize_explicit_labels(labels)`
2. reject `len(labels_tuple) < 2`
3. `true_list = _normalize_label_sequence(y_true, "y_true")`
4. reject empty `true_list`
5. reject any `true_list` value not in `set(labels_tuple)`
6. `score_matrix = _normalize_score_matrix(y_score, len(true_list), len(labels_tuple))`
7. `weights = None if sample_weight is None else _normalize_sample_weight(sample_weight, len(true_list))`
8. `class_support = _compute_effective_class_support(true_list, labels_tuple, weights, function_name)`
   -- unconditional, every time, for both functions (no `average="micro"` branch exists in this
   slice to skip it under, unlike the score functions).
9. per-column loop calling `roc_curve`/`precision_recall_curve`.
10. wrapper-level postcondition check (§22).

## 5. Validation/normalization reuse plan

No new public or private helper is introduced for validation. The implementation (in a later PR)
imports and calls the five existing private helpers listed in §2 directly, exactly the way
`multiclass_roc_auc_score`/`multiclass_average_precision_score` already do -- this is not a new
reuse pattern, it is the same one applied to a new pair of sibling functions in the same module.
No public helper is designed "just for this": every one of these helpers is already private,
already shared by two existing public functions, and gains a third and fourth caller without any
change to its own signature or contract.

## 6. No `average` parameter

The new functions do not accept `average`. They always return the full per-class collection --
there is no `None`/`"macro"`/`"weighted"`/`"micro"` mode to select in this slice (§13 covers why
aggregate curves are out of scope). Consequently, step 1 of `multiclass_roc_auc_score`'s validation
order (`require_one_of(average, ...)`) has no counterpart here, and the `average="micro"` branch
that lets the score functions skip `_compute_effective_class_support` does not exist -- the new
functions always compute effective support for every label (§4, §7).

## 7. ROC vs precision-recall support semantics

Both new functions share one precheck: **every label named in `labels` must have positive
effective support**, computed by the same unconditional call to `_compute_effective_class_support`
(§4, step 8) for both. This is deliberate, not an oversight that conflates the two curves' real
differences:

- **ROC.** `roc_curve` itself requires both positive *and* negative effective support for its
  `positive_label`. Once every named label has positive effective support and there are at least 2
  of them (already guaranteed by steps 1-2), every label automatically also has positive effective
  *negative* support -- the other labels' effective samples -- exactly the reasoning
  `multiclass_roc_auc_score`'s own docstring already states for its non-micro path: *"Once every
  named label has positive effective support, and there are at least 2 of them, every class also
  has positive effective negative support automatically... `roc_curve`'s own per-class
  negative-support check remains in place as a second line of defense, but is never expected to
  trigger here."* `multiclass_roc_curve` inherits this unchanged.
- **Precision-recall.** `precision_recall_curve` does not require negative effective support at
  all -- a class that is effectively all-positive is legal (precision is `1.0` at every real
  threshold). `multiclass_precision_recall_curve` shares the same positive-support-only precheck
  as ROC (step 8 is identical code for both functions), but never adds ROC's negative-support
  requirement on top of it, because the underlying `precision_recall_curve` call never needs it.

There is no `average="micro"` exception to carve out here (unlike the score functions), since this
slice does not implement a micro curve (§13) -- so the "does not require per-class effective
support" relaxation the score functions document for `average="micro"` never applies here.

## 8. Result representation -- the central decision

Four variants were compared.

### A. Plain tuple

```python
def multiclass_roc_curve(...) -> tuple[RocCurve, ...]: ...
def multiclass_precision_recall_curve(...) -> tuple[PrecisionRecallCurve, ...]: ...
```

Pros: zero new public types; each `RocCurve` already carries `positive_label`, so no ordering
information is actually lost; matches the module's existing "per-class, no wrapper" precedent for
`average=None` (`multiclass_roc_auc_score(..., average=None)` already returns a bare `ndarray`,
not a wrapped type). Cons: the return type is generic -- `tuple[RocCurve, ...]` reads the same
whether it came from this function or from any other code that happens to build a tuple of
`RocCurve` objects, so it does not name the multiclass-curve concept at the type level. More
importantly: **a tuple return type cannot later gain a named field (e.g. a future, separately
decided micro curve) without changing the function's return type outright** -- a breaking change
to every caller's type annotation, not an additive one.

### B. Wrapper holding only `curves`, with `labels` as a derived property

```python
@dataclass(frozen=True, slots=True)
class MulticlassRocCurve:
    curves: tuple[RocCurve, ...]

    @property
    def labels(self) -> tuple[int, ...]:
        return tuple(curve.positive_label for curve in self.curves)
```

(analogously `MulticlassPrecisionRecallCurve` wrapping `tuple[PrecisionRecallCurve, ...]`). Only
one stored field; `labels` is computed, never stored, so there is no second copy of the label order
that could ever disagree with `curves`. Gives the result a distinct, self-documenting type name and
a stable place to add an optional field later (e.g. a `micro` curve, as a genuinely separate, later
API decision -- §13) without breaking the return type's fundamental shape.

### C. Wrapper storing both `labels` and `curves` (the audit's proposed shape)

```python
@dataclass(frozen=True, slots=True)
class MulticlassRocCurve:
    labels: tuple[int, ...]
    curves: tuple[RocCurve, ...]
```

This is **explicitly rejected**, not accepted by default because a prior audit suggested it. It
creates a redundant-state invariant, `labels[i] == curves[i].positive_label`, that variant B simply
does not have (there `labels` cannot disagree with `curves`, because it is not separately stored).
Answering the design's own required questions about this invariant:

- **Who validates it on manual construction?** Nobody, by default -- a plain `@dataclass` does not
  cross-check fields against each other.
- **Is `__post_init__` needed?** Yes, to enforce the invariant at all. But no other curve-family
  dataclass in this module (`RocCurve`, `PrecisionRecallCurve`) has ever needed a `__post_init__`
  -- they are plain field bags, always constructed by trusted internal code. The *only* dataclass
  in this module designed to support real hand-construction is `ConfusionMatrixResult`, and its
  precedent shows how heavy that support actually is: a full, separate, explicitly documented
  re-validation entry point (`classification_metrics_from_confusion_matrix`'s own re-validation of
  a hand-built `ConfusionMatrixResult`), motivated by a genuine use case (aggregating confusion
  matrices across batches). `MulticlassRocCurve`/`MulticlassPrecisionRecallCurve` have no analogous
  use case for hand construction from separately-sourced `labels`/`curves` -- inventing
  `__post_init__` validation for a construction path nothing actually needs is unjustified
  complexity.
- **What happens with an inconsistent hand-built object, absent `__post_init__`?** It silently
  exists, with `labels[i] != curves[i].positive_label` for some `i` -- a real correctness hazard
  for any code that trusts the invariant, with no compensating benefit.
- **Is duplicating the data worth it at all?** No. `curves[i].positive_label` already contains
  every bit of information `labels[i]` would duplicate.

### D. Generic shared container

A single generic type (e.g. `CurveCollection[TCurve]`) parameterized over `RocCurve |
PrecisionRecallCurve`, aliased for the two concrete cases. Rejected: ROC and PR curves already need
distinct, separately documented public names (their fields mean different things -- false/true
positive rate vs. precision/recall), so a generic base still ends up requiring two concrete public
names via aliasing, buying nothing in API-surface reduction while adding real typing complexity
(`Generic[TCurve]`, a bound `TypeVar`, and the aliasing itself needing its own documentation).

### Decision: **Variant B**

Two new types, `MulticlassRocCurve` and `MulticlassPrecisionRecallCurve`, each a frozen, slotted
dataclass with exactly one stored field (`curves: tuple[RocCurve, ...]` /
`tuple[PrecisionRecallCurve, ...]`) and one derived, read-only `labels` property. This is the
smallest surface that still gives a stable extension point (§16 explains the trade-off against
Variant A's "0 new types" minimum explicitly).

## 9. Equality/hash semantics -- verified, not assumed

Verified empirically (small standalone script, not shown in this document, run against a
stand-in `RocCurve`-shaped class with the exact same custom `__eq__`/`__hash__ = None` pattern used
in `evaluation.py`) before writing this section:

- **Default dataclass `__eq__` is already correct** for a wrapper whose only field is a
  `tuple[RocCurve, ...]`. Python's tuple equality compares element-by-element using each element's
  own `__eq__`; since `RocCurve.__eq__` already returns a plain `bool` (never raising NumPy's
  "truth value of an array is ambiguous" error, because it uses `np.array_equal` internally), tuple
  equality over `RocCurve` elements returns a plain `bool` too, with no special handling needed.
  Verified directly: comparing two wrappers with equal, unequal, and identical `curves` tuples all
  produced correct plain `bool` results with the dataclass-generated `__eq__`, no `TypeError`, no
  ambiguous-truth-value error.
- **No custom `__eq__` is added.** The default is correct and simpler; adding a hand-written
  `__eq__` here would only duplicate what the default already does correctly.
- **Hashability.** `RocCurve`/`PrecisionRecallCurve` are explicitly unhashable (`__hash__ = None`).
  A dataclass's *default* generated `__hash__` (were one generated) would call `hash()` on the
  `curves` tuple, which calls `hash()` on each `RocCurve` element, which raises `TypeError`
  (verified directly: `unhashable type: 'RocCurve'`). So the wrapper ends up unhashable either way
  -- but relying on that incidental, lazily-raised `TypeError` (whose message names `RocCurve`, not
  the wrapper type) is less clear than every other dataclass in this module, which all declare
  `__hash__ = None` explicitly with a stated reason. **Decision: declare `__hash__ = None`
  explicitly** on both new types, for consistency with `ConfusionMatrixResult`/
  `ClassificationMetrics`/`RocCurve`/`PrecisionRecallCurve`, even though it is not strictly
  required for correctness.
- **`repr`.** The default dataclass `repr` is kept -- verified it renders as
  `MulticlassRocCurve(curves=(RocCurve(...), RocCurve(...)))`, which is exactly as informative as
  any other dataclass `repr` in this module; no custom `__repr__` is needed.
- **Manual construction.** `MulticlassRocCurve(curves=(...))` is a legal, always-consistent
  construction by definition (Variant B eliminates the invariant Variant C would need to guard --
  §8), so no re-validation function analogous to `classification_metrics_from_confusion_matrix` is
  needed for this type.
- **Frozen, slots.** Both `True`, matching every other result dataclass in the module.

Final field declaration for both types:

```python
@dataclass(frozen=True, slots=True)
class MulticlassRocCurve:
    curves: tuple[RocCurve, ...]

    @property
    def labels(self) -> tuple[int, ...]:
        return tuple(curve.positive_label for curve in self.curves)

    __hash__ = None  # type: ignore[assignment]


@dataclass(frozen=True, slots=True)
class MulticlassPrecisionRecallCurve:
    curves: tuple[PrecisionRecallCurve, ...]

    @property
    def labels(self) -> tuple[int, ...]:
        return tuple(curve.positive_label for curve in self.curves)

    __hash__ = None  # type: ignore[assignment]
```

Note these do not need `eq=False` plus a hand-written `__eq__` (unlike `RocCurve` itself) --
`eq=True` (the dataclass default) is correct here, as verified above; only `__hash__` needs the
same explicit `None` override the rest of the module already uses.

## 10. Labels ordering

Contract: `curves[i]` corresponds exactly to `labels[i]`, in the exact order `labels` is given --
never sorted. Worked example with a deliberately unsorted `labels`, matching the same
`(20, 10, 30)` example `examples/classification_evaluation.py` already uses for the sibling score
functions:

```python
labels = (20, 10, 30)  # intentionally not sorted
result = multiclass_roc_curve(y_true, y_score, labels=labels)

assert result.labels == (20, 10, 30)
assert result.curves[0].positive_label == 20
assert result.curves[1].positive_label == 10
assert result.curves[2].positive_label == 30
```

This falls out structurally from the implementation (§5, §22): the per-column loop iterates
`labels_tuple` in order and appends to `curves` in the same order, exactly mirroring
`multiclass_roc_auc_score`'s own `for column, label in enumerate(labels_tuple):` loop.

## 11. Per-class direct-equivalence guarantee (central public invariant)

**Decision: bit-for-bit, not merely semantically identical.** For every `i`:

```python
multiclass_roc_curve(y_true, y_score, labels=labels, sample_weight=w).curves[i]
== roc_curve(y_true, y_score[:, i], positive_label=labels[i], sample_weight=w)
```

and analogously for `multiclass_precision_recall_curve`/`precision_recall_curve`. This is the same
strength of guarantee `multiclass_roc_auc_score`'s own docstring already makes for its per-class
scores (*"`result[i]` is bit-for-bit identical to calling `roc_auc_score(...)` directly... since
this function computes each class's score by calling that same public function once per column on
already-validated inputs, rather than reimplementing or duplicating its arithmetic"*), and it holds
here for the identical structural reason: the implementation (§5) does not reimplement any ranking
arithmetic -- it calls the public `roc_curve`/`precision_recall_curve` once per column, passing the
same already-normalized `true_list`/`score_matrix[:, column]`/`weights` the score functions already
pass to `roc_auc_score`/`average_precision_score` per column today. This is not a new, unverified
reuse pattern; it is the exact call shape already exercised (and tested, via
`test_multiclass_per_class_bit_identical_to_binary`) for the score functions, applied to the two
curve functions.

## 12. `sample_weight`

Identical contract to the existing ranking functions' `sample_weight` (§3): `Sequence[float] |
ndarray[floating] | ndarray[integer] | None`, non-negative, at least one positive value required,
validated once via `_normalize_sample_weight` (§4). Verified cases: a plain `Sequence`, an integer
`ndarray`, a `float16`/`float32`/`float64` `ndarray`, a zero-weight row (removed before threshold
building by the underlying `roc_curve`/`precision_recall_curve` call, per their own existing
contract), an all-zero `sample_weight` (rejected -- §4), NaN/Inf (rejected -- §4), a negative value
(rejected -- §4), and a huge exact/non-exact integer weight (exact -> accepted and converted;
non-exact -> rejected, per `_normalize_sample_weight`'s existing integer-representability check).

The same validated `weights` array is passed unchanged to every one-vs-rest column's
`roc_curve`/`precision_recall_curve` call -- so the same sample carries the same weight in every
returned curve, exactly like `multiclass_roc_auc_score`'s non-micro path. **The micro-mode
per-class weight repetition (`np.repeat(weights, n_classes)`, used only to build the flattened
binary problem for `average="micro"`) is not reused here at all** -- there is no micro curve in
this slice (§13), so that flattening logic has no counterpart to reuse or duplicate.

## 13. No aggregate curve in this slice

### Macro / weighted curve

Deliberately deferred, not implemented. Unlike a *scalar* macro/weighted average (a simple mean
over already-computed per-class numbers, which `_canonical_mean`/`_weighted_average` already do
generically), a macro/weighted *curve* would require choosing a common axis to average multiple
curves' points against -- e.g. a shared FPR or recall grid to interpolate each per-class curve onto
before averaging. No such grid/interpolation policy exists anywhere in this module today, and
choosing one (linear interpolation? nearest-threshold? how many grid points?) is a real, undecided
API design question this slice does not need to answer to deliver its core value (§16 keeps
`curve interpolation grid` and `curve averaging` explicitly out of scope).

### Micro curve

**Mathematically well-defined, deliberately deferred to a later, separate slice -- not
undefined and not ambiguous.** It would use exactly the same flattening
`multiclass_roc_auc_score(..., average="micro")` already implements today (`_flatten_multiclass_ovr`:
build the C-order one-hot target and ravel the score matrix, then call the binary
`roc_curve`/`precision_recall_curve` once on the flattened problem) -- there is nothing
mathematically unresolved about it. It is excluded from this slice because it is a genuinely
separate public result (a single curve for the *flattened* problem, not "one curve per class") and
therefore a separate API decision -- shipping it alongside the per-class contract in the same PR
would silently double this slice's scope (adding a mode dimension to the return shape) before the
core per-class contract has even shipped and been used.

## 14. Relationship to the existing score APIs

`multiclass_roc_curve` and `multiclass_roc_auc_score` are related but not interchangeable:
`auc(curve.false_positive_rate, curve.true_positive_rate)` for `curve = result.curves[i]` is
bit-for-bit identical to `multiclass_roc_auc_score(..., average=None)[i]` -- the same relationship
`roc_auc_score`/`auc(*roc_curve's rate arrays)` already have for the single-class case.

**For precision-recall, this equivalence does NOT hold**, and the design/demo/docs must never
suggest it does: `auc(curve.recall, curve.precision)` for `curve =
multiclass_precision_recall_curve(...).curves[i]` computes the *trapezoidal* area under the PR
curve, a distinct quantity from `multiclass_average_precision_score(..., average=None)[i]`
(non-interpolated average precision). The module's own docstring is explicit about this for the
binary case (*"a distinct quantity from `average_precision_score`... that this module deliberately
does not expose under a separate name"*), and it applies unchanged per class here. Any future
README/example/demo text introducing these functions must state both relationships side by side,
never implying `auc(pr_curve) == average_precision`.

## 15. Naming

Compared:

- `MulticlassRocCurve` / `multiclass_roc_curve`
- `MulticlassRocCurves` / `multiclass_roc_curves`
- `MulticlassRocCurveResult` / (function name unaffected by this variant)

(and the same three-way comparison for the precision-recall counterpart).

**Key question, answered deliberately rather than by mechanical analogy to `roc_curve`:** since the
result holds multiple per-class curves, is a singular name still right? Yes -- but the reasoning is
not "because `roc_curve` is singular." It is that **this project's own `multiclass_*` naming family
is already singular regardless of return shape**: `multiclass_roc_auc_score` returns a *collection*
of per-class scores for `average=None` (an `ndarray`, not one number), yet the function name stays
singular, because the name describes the singular *concept* being computed multiclass-wise ("the
ROC AUC score, extended to multiclass"), not a guarantee about the return value's shape.
`multiclass_roc_curve` follows the identical pattern: "the ROC curve, extended to multiclass" -- one
recipe (one-vs-rest per class), applied and returned together. Introducing a plural
(`multiclass_roc_curves`) here would be the first break in that established family's naming logic,
for a cosmetic gain that does not offset the inconsistency with its two existing siblings.

`MulticlassRocCurveResult` is rejected for a different, concrete reason: the `Result` suffix
already exists in this module (`ConfusionMatrixResult`), but there specifically to disambiguate the
wrapper from a competing "bare matrix" concept a reader might otherwise assume `ConfusionMatrix`
alone refers to. `RocCurve`/`PrecisionRecallCurve` (the direct precedent for a *curve* result) use
no such suffix, because there is no competing "bare `RocCurve`-shaped raw value" to disambiguate
from. `MulticlassRocCurve` has the same non-ambiguity property, so the no-suffix precedent applies,
not the `Result`-suffix one.

**Decision:** `MulticlassRocCurve` / `multiclass_roc_curve`, `MulticlassPrecisionRecallCurve` /
`multiclass_precision_recall_curve`.

## 16. Public API budget

The smallest theoretical surface is 2 new functions, 0 new types (Variant A, §8). This design
spends 2 extra public types beyond that minimum, in exchange for the one property Variant A
structurally cannot offer: a return type that can gain an optional field later (e.g. a future,
separately-decided micro curve) without changing its fundamental shape from a bare tuple to an
object -- a breaking change Variant A would eventually force if any wrapping is ever added. This
is the "stable point for future extension" this section is required to weigh against raw minimalism,
and it is judged worth 2 types here specifically because both types are trivial (one stored field,
one derived property, no new validation logic of their own).

**Final budget: 2 new public functions, 2 new public types, 0 new public helpers, 0 new
dependencies.**

## 21. Complexity

For `N` samples and `C` labels, calling the binary curve function once per column costs what
`roc_curve`/`precision_recall_curve` already cost per call: `O(N log N)` time (dominated by sorting
that column's scores), `O(N)` memory for that one call's output arrays (README's own documented
bound for the binary functions). Honest bound for the multiclass wrapper, accounting for what a
naive `O(C*N)` claim would miss:

- **Time: `O(C * N log N)`.** `C` independent per-column sorts, each `O(N log N)` -- not `O(C*N)`,
  which would only hold if no sorting were required.
- **Memory: `O(C * N)`,** not the binary functions' own `O(N)`. Two contributions: (1)
  `_normalize_score_matrix` allocates one `(N, C)` `float64` copy up front (`O(N*C)` on its own);
  (2) the `C` returned curves' combined output size is bounded by `C * (N + 1)` in the worst case
  (each column's curve has at most `N + 1` points, one per distinct score plus the `+inf`
  sentinel) -- so total output memory scales with `C`, unlike a single binary call.

## 22. Postconditions

Internal, `RuntimeError`-raising checks on the wrapper (mirroring this module's existing style of
paranoid internal invariant checks, e.g. `_check_multiclass_score_postconditions`):

- `len(result.curves) == len(labels_tuple)` -- structurally guaranteed by construction (one loop
  iteration per label), asserted anyway as defense-in-depth, matching the module's existing style.
- Curve ordering is exact: `result.curves[i]` was built from `labels_tuple[i]`, never reordered.
- `result.curves[i].positive_label == labels_tuple[i]` for every `i` -- also structurally
  guaranteed (each `roc_curve`/`precision_recall_curve` call passes `positive_label=labels_tuple[i]`
  directly, and `RocCurve`/`PrecisionRecallCurve` store that argument unmodified), asserted anyway.
- Each nested `RocCurve`/`PrecisionRecallCurve` has *already* passed its own binary postcondition
  check (`_check_roc_curve_postconditions`/`_check_pr_curve_postconditions`) inside the
  `roc_curve`/`precision_recall_curve` call that produced it -- the wrapper-level check does not
  need to re-verify per-curve array invariants (finiteness, monotonicity, read-only-ness,
  non-aliasing), only the wrapper-level structural invariants above.
- No new aliasing risk: `curves` is a plain tuple over already-independent, already-read-only
  `RocCurve`/`PrecisionRecallCurve` objects; wrapping them in a tuple introduces no new memory
  sharing.

**Variant B (§8) eliminates one whole invariant structurally**, which is itself a design advantage
worth stating explicitly here: because `labels` is a derived property, not a stored field, there is
no `labels[i] == curves[i].positive_label` cross-field invariant to check at all -- Variant C's
central consistency hazard (§8) simply does not arise for the chosen shape.

## 23. Test plan (future implementation PR)

**Core:** 2 classes; 3+ classes; unsorted labels; sparse/large label values; `float64`/`float32`/
integer `y_score` dtypes; `Sequence` `y_true`; `ndarray` `y_true`.

**Equivalence (the central invariant, §11):** every returned `RocCurve` compared for exact equality
against a direct `roc_curve(y_true, y_score[:, i], positive_label=labels[i], sample_weight=w)` call;
same for `PrecisionRecallCurve`/`precision_recall_curve`.

**Validation (§4, one test per row of that table):** empty `labels`; one label; duplicate labels;
`y_true` value outside `labels`; empty `y_true`; wrong `y_score` ndim; wrong row count; wrong
column count; NaN/Inf in `y_score`; non-exact-representable integer `y_score`; invalid
`sample_weight` container/dtype/length; all-zero `sample_weight`; zero effective support for one
label.

**Weights:** plain `Sequence`; integer `ndarray`; `float64` `ndarray`; a zero-weight row (removed
from that row's contribution, sample identity preserved across every one-vs-rest curve).

**Result semantics:** ordering (`curves[i]` <-> `labels[i]`, unsorted-labels example from §10);
equality (equal wrappers, unequal-by-one-curve wrappers); hashability (`hash()` raises `TypeError`);
`repr`; manual construction (`MulticlassRocCurve(curves=(...))` round-trips correctly); confirming
both new types and both new functions are reachable as `improcv.MulticlassRocCurve` etc. (top-level
export check, §17).

**Isolation:** no `matplotlib` import anywhere in `evaluation.py`; no `cv2` dependency in this
computation path at all (it is pure NumPy, like the rest of the module); no filesystem I/O.

## 24. Randomized differential test plan (no Hypothesis, no scikit-learn reference)

At least 2000 small, deterministically-seeded (`numpy.random.Generator`, fixed seed) multiclass
problems, varying: 2-8 classes; unsorted label orderings; tied scores within a column; duplicate
scores across samples; negative scores; large-magnitude and small-magnitude finite scores;
`sample_weight` present/absent; zero-weight rows. For every generated problem, compare every
returned per-class curve against the existing, already-shipped, already-tested public binary
`roc_curve`/`precision_recall_curve` called directly on the matching column -- **the existing public
binary functions are the contractual reference, not scikit-learn** (this module already documents
several deliberate departures from `scikit-learn.metrics`'s behavior, so scikit-learn is not a
valid oracle for improcv's own contract).

## 25. Public typing

- `MulticlassRocCurve`/`MulticlassPrecisionRecallCurve`: plain (non-generic) dataclasses. No
  `TypeVar`/`Generic` is introduced -- Variant D (§8) already showed a generic base buys nothing
  here, since ROC and PR still need two separate concrete names either way.
- `curves: tuple[RocCurve, ...]` / `tuple[PrecisionRecallCurve, ...]` -- a fixed-element-type
  variadic tuple, matching how `ConfusionMatrixResult.labels: tuple[int, ...]` and similar existing
  fields are already typed in this module.
- `labels` is typed as a `@property -> tuple[int, ...]`, not a stored field -- so it appears in
  type checking exactly like any other read-only attribute, with no `Optional`/generic complexity.
- Function signatures reuse the exact existing `Sequence[int] | npt.NDArray[np.integer]` /
  `npt.NDArray[np.floating] | npt.NDArray[np.integer]` union shapes already used by
  `multiclass_roc_auc_score`, verbatim -- no new type aliases are introduced for this slice.

## 28. Alternatives considered for this slot

### `load_image` (generic single-image loading)

A real next candidate, but a separate slice, not designed here. Note for whoever picks it up next:
the prior product audit's own treatment of this candidate already narrowed the original
"image/mask loading" problem down to a more minimal "generic single-image loading" shape
(`load_image(path, *, mode=cv2.IMREAD_COLOR)`, with no mask-pair-specific semantics at all). That
narrowing is exactly what let it pass its own feasibility gate -- `Mask`'s binary `0`/`255`
convention (`src/improcv/types.py`) cannot honestly be attached to an arbitrary on-disk mask
(multiclass label map, palette-indexed PNG, float mask) without either corrupting it or inventing
unresolved semantics `discover_image_mask_pairs`'s own docstring explicitly declines to define
(*"it never opens, decodes, or inspects file contents... that is left entirely to the caller"*).
The cost of that same narrowing is real too: a generic single-image loader closes less of the
original discovery -> memory workflow gap than a mask-aware loader would have, which is exactly why
it was not chosen for this slot instead of the curve types.
