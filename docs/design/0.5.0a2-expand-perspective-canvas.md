# Design: `expand_perspective_canvas` (`0.5.0a2` feature slice)

Status: implemented and released in `0.5.0a2` (`src/improcv/augmentation.py`). See §7 below for
one wording clarification made during implementation (no frozen decision was altered).

## 1. Status / scope

This is the selected second feature slice of the `0.5.0` line. A fresh, skeptical product audit
(this development line, `0.5.0a2.dev0`) selected `expand_perspective_canvas` — the perspective
counterpart to the already-shipped `expand_affine_canvas` (`0.4.x` line) — over 17 other
candidates, on the strength of a discovered, reusable, already-cross-version-verified safety
invariant (`_require_perspective_matrix_geometry`, `src/improcv/augmentation.py:1764-1814`).

**Important correction to the audit's own framing, made explicit here and carried through this
entire document:** the audit's provisional signature (`expand_perspective_canvas(params:
PerspectiveParameters) -> PerspectiveParameters`) is correct, but its claim of "0 changed
existing public types" understated the real contract. `PerspectiveParameters`
(`augmentation.py:221-256`) today has no `output_size` field, and `apply_perspective` always
renders to `params.source_size` (`augmentation.py:1379`: "Output spatial size always equals
`params.source_size` (this slice does not expand the canvas)"). A homography's `matrix` alone
cannot express an enlarged destination raster — `matrix` controls *coordinate mapping*,
`dsize`/`output_size` controls *destination raster extent*, and these are independent pieces of
information for a general (non-affine) projective transform exactly as they already are for
`AffineParameters` (`augmentation.py:201`: `output_size: tuple[int, int] | None = field(default=None,
kw_only=True)`). This design therefore explicitly extends `PerspectiveParameters` with an
analogous field — a real, additive, backwards-compatible public-type change, not "zero type
changes." See §3 and §6 for the exact honest accounting.

This document freezes the exact contract before any implementation. It is normative: an
implementation PR must not silently redefine anything frozen here. If empirical evidence during
implementation contradicts a decision below, that is a STOP condition (§35 of this document's
own numbering — see the final section), not something to route around quietly.

## 2. Product rationale

`sample_perspective`/`apply_perspective` (`augmentation.py:1179-1449`) let a caller sample and
replay a perspective (projective) augmentation, but the output is always cropped to
`params.source_size` — any content the sampled homography pushes outside the source frame is
silently lost, with no opt-out. `expand_affine_canvas` (`augmentation.py:1002-1176`) already
solved exactly this problem for the affine sibling: "Grow `params`' output canvas so
`apply_affine` no longer crops any transformed content" (`augmentation.py:1003`). No perspective
equivalent exists. `apply_perspective`'s own docstring states the gap directly (line 1379,
quoted above); the module docstring (lines 20-25) lists "perspective canvas expansion... remain[s]
out of scope for this slice"; `ROADMAP.md` explicitly names it as the next planned augmentation
item.

Doing this correctly for a genuine (non-affine) projective transform is **not** a trivial
generalization of the affine case: a homography's transformed footprint can, for a
sufficiently distorted matrix, have points that map to infinity or "flip through" a projective
horizon, making a finite bounding canvas ill-defined for that matrix. This is exactly why the
product audit initially flagged this candidate as needing serious mathematical justification
before selection (see the audit's own candidate-K analysis) — and exactly why the discovery
below is the decisive piece of evidence.

**Decisive finding:** `_require_perspective_matrix_geometry` (`augmentation.py:1764-1814`) —
already used by `sample_perspective` at construction time and by `_require_perspective_parameters`
on every `apply_perspective` call — already implements and empirically verifies (its own
docstring: "verified directly against OpenCV 4.9 and 5.0" for the `float32`-quantization case,
and "verified directly (OpenCV 5.0, degenerate input points)" for the determinant case) a
scale-invariant check that a homography's homogeneous denominator keeps one consistent sign
across the source rectangle's 4 corners. §11 below proves this exact technique, applied to a
different (slightly larger) corner set, is mathematically sufficient to make canvas expansion
honest: reject only genuinely horizon-crossing homographies, and correctly grow-bound everything
else. **The hard mathematical sub-problem is already solved and already shipped** — this design
reuses it, not reinvents it.

## 4. API budget correction from the product audit

The audit reported "+1 top-level symbol, 0 new public types" without qualification. The honest,
complete accounting (see §6) is:

- **+1 new top-level public function**: `expand_perspective_canvas`.
- **+0 new public types**: correct — no new dataclass/enum/result type is introduced.
- **+1 additive, backwards-compatible, keyword-only field** on the *existing* public type
  `PerspectiveParameters`: `output_size`.
- **+0 changed existing function signatures**: `apply_perspective`'s parameter list is unchanged
  (see §19) — only its *behavior* gains a new case, exactly mirroring how `apply_affine` already
  works today without ever having changed its own signature when `output_size` was added to
  `AffineParameters`.
- **Default behavior unchanged**: `sample_perspective` always produces `output_size=None`;
  `apply_perspective(image, params)` for any `params` with `output_size=None` (i.e. every
  `PerspectiveParameters` that exists today, and everything `sample_perspective` will ever
  continue to produce) behaves byte-for-byte identically to today.

This is a real, additive public-type extension — not "zero changes to existing public types." It
is the same class of change `AffineParameters` already went through when `output_size` was added
to it (a change this design doc's own reading confirms already shipped and is already stable).

## 5. Exact public API

```python
def expand_perspective_canvas(params: PerspectiveParameters) -> PerspectiveParameters: ...
```

One positional parameter, one return value, no keyword arguments, no defaults to freeze beyond

## 6. `PerspectiveParameters.output_size` — mandatory data-model decision

### Option A — extend `PerspectiveParameters` (chosen)

```python
output_size: tuple[int, int] | None = field(default=None, kw_only=True)
```

Added as a fourth field, after the existing three (`matrix`, `source_size`,
`destination_points`), keyword-only for the identical compatibility reason
`AffineParameters.output_size` already is: `PerspectiveParameters`'s original 3-positional
construction (`PerspectiveParameters(matrix, source_size, destination_points)`) remains legal
unchanged, and `__match_args__` — verified directly via a throwaway `dataclass` reproduction
(Python 3.11+, `slots=True, frozen=True`, one field added with `field(default=..., kw_only=True)`)
— **automatically excludes keyword-only fields**, so `PerspectiveParameters.__match_args__`
remains exactly `("matrix", "source_size", "destination_points")`, unchanged, without any extra
code (this is standard `dataclasses` behavior since Python 3.10, not something requiring a
manual override — confirmed empirically, not merely assumed, per §22/§27).

**Compatibility assessment (all confirmed, none contradicted):**
- Existing 3-positional construction remains legal: yes (keyword-only fields with a default never
  affect earlier positional fields).
- `__match_args__` remains the original 3 field names: yes, automatically, confirmed by direct
  reproduction.
- `sample_perspective` behavior unchanged: yes — it never sets `output_size`, so every
  `PerspectiveParameters` it produces has `output_size=None` (identical to how `sample_affine`
  never sets `AffineParameters.output_size` today).
- `repr` gains the field: yes, as an additive, expected dataclass-generated `repr` consequence —
  not a promise of a stable serialized format (this project makes no such promise for any
  dataclass `repr` today, including `AffineParameters`'s own).
- Equality must account for `output_size`: yes — `PerspectiveParameters.__eq__` gains one more
  compared field, mirroring `AffineParameters.__eq__`'s own `and self.output_size ==
  other.output_size` (line 214) exactly.
- Manually-constructed parameters may supply it keyword-only: yes, `PerspectiveParameters(matrix,
  source_size, destination_points, output_size=(200, 150))` is legal, exactly mirroring
  `AffineParameters`'s existing keyword-only fields.
- Validation must include it: yes — `_require_perspective_parameters` gains one call to the
  already-generic `_require_optional_output_size(params.output_size)`, mirroring
  `_require_affine_parameters`'s existing line 1626 verbatim.
- No hashing: unaffected — `__hash__ = None` already applies to the whole class.
- No pickle/backward-storage guarantee: unaffected — the project makes no such promise for any
  dataclass today, and this design introduces none.

### Option B — add an `output_size` parameter to `apply_perspective` (rejected)

Would separate replay state across `params` (the transform matrix) and a call-site argument (the
destination size), meaning a single `PerspectiveParameters` value would no longer be a
self-contained, replayable description of "the transform to apply" — the caller would need to
remember and re-supply the intended output size at every `apply_perspective` call site, and two
different callers replaying the "same" expanded transform could silently disagree on canvas size.
This also diverges from the affine replay model already shipped and stable
(`AffineParameters.output_size` + `apply_affine` reading it from `params`, never from a call
argument) for no offsetting benefit. **Rejected** — inferior to Option A on both self-containment
and precedent-consistency grounds.

### Option C — return a separate public result/type or tuple (rejected)

Would require either a new public dataclass (e.g. `ExpandedPerspectiveParameters` or a
`(PerspectiveParameters, tuple[int,int])` tuple return) — either directly violates the "0 new
public types" budget this design is held to (§30 of the product audit; §4 above), or (for a bare
tuple) discards the type-safety and self-documentation `AffineParameters.output_size`'s field
name already provides, and would require `apply_perspective` to grow a second parameter anyway
(collapsing into Option B's rejected shape). **Rejected.**

**Decision: Option A**, with no concrete incompatibility found during this analysis — the strong
default the audit anticipated is confirmed, not merely assumed.

## 7. `PerspectiveParameters.output_size` semantics (frozen)

- `output_size` is `(width, height)` or `None`.
- `None` (the only value `sample_perspective` ever produces) means `apply_perspective` renders to
  `source_size`, exactly as today.
- A non-`None` value participates in replay truth together with `matrix`: once `output_size` can
  differ from `source_size`, `matrix` alone no longer determines the destination raster extent,
  mirroring `AffineParameters`'s own documented reasoning (§3) verbatim. **Clarified wording**
  (implementation-time correction, not a behavior change): `sample_perspective` never sets
  `output_size` — it is always `None` on a freshly sampled `PerspectiveParameters`.
  `expand_perspective_canvas` is the canonical library operation that computes and sets a
  non-`None` value. This does not mean `expand_perspective_canvas` is the *only* legal source of
  a non-`None` value — exactly as §6's own compatibility analysis already establishes, a manually
  constructed `PerspectiveParameters` may also legally supply a validated non-`None` `output_size`
  keyword-only, identically to `AffineParameters.output_size`. The original draft of this
  sentence ("set only by `expand_perspective_canvas`") was an imprecise shorthand that read as
  contradicting §6; this is the intended, internally consistent meaning.
- Validated via the already-generic `_require_optional_output_size` (§3, §6) — same policy and
  same `_OPENCV_SIZE_MAX = int(np.iinfo(np.int32).max)` ceiling `AffineParameters.output_size`
  already uses.
- **Empirically confirmed valid for `warpPerspective` too, not merely assumed from
  `warpAffine`:** direct experiments (§27) confirm `cv2.warpPerspective` accepts an arbitrary
  positive `dsize` different from the source image's shape, on both OpenCV 4.9.0 and 5.0.0,
  producing the expected output shape with no crash; an out-of-`int32`-range `dsize` (`2**31`,
  one past `_OPENCV_SIZE_MAX`) raises `cv2.error` via OpenCV's own Python-argument overload
  resolution on both versions (not a silent misbehavior); a negative `dsize` component
  (`(-5, 10)`) raises **no exception at all** on either version (silently accepted by OpenCV's
  argument parser, then presumably mishandled downstream) — confirming, exactly as
  `warp_perspective`'s own existing docstring already states for the general case ("OpenCV
  silently ignores an invalid `dsize`... so this must be checked here rather than left to
  `cv2.warpPerspective`"), that `_require_optional_output_size`'s own positive-only check is
  necessary, not redundant, and is already sufficient — no new perspective-specific ceiling logic
  is needed.

## 8. Idempotency (frozen)

Mirrors `expand_affine_canvas` exactly, no evidence found to justify deviating:

```python
if params.output_size is not None:
    raise ValueError(
        "params already define an output_size; expand_perspective_canvas requires "
        "unexpanded parameters (it is not idempotent)"
    )
```

No attempt is made to infer whether a manually-set `output_size` originated from this function —
exactly as `expand_affine_canvas` makes no such inference today. No idempotency guarantee is
made or implied.

## 9. Pixel-cell footprint (mandatory, frozen)

Uses the identical continuous source footprint convention `expand_affine_canvas` already uses:

```
[-0.5, width - 0.5] x [-0.5, height - 0.5]
```

with homogeneous corners `(-0.5, -0.5, 1)`, `(width-0.5, -0.5, 1)`, `(width-0.5, height-0.5, 1)`,
`(-0.5, height-0.5, 1)` — **not** the pixel-*center* corners `(0,0)...(w-1,h-1)`
`_perspective_source_corners` (§3) already uses for `sample_perspective`/`apply_perspective`'s
existing validation.

**Why the pixel-cell footprint is the relevant no-crop geometry:** a discrete pixel at integer
index `(i, j)` represents a continuous sample located at that integer coordinate, but the pixel
itself occupies the half-open unit cell `[i-0.5, i+0.5) x [j-0.5, j+0.5)` in continuous image
space (the standard pixel-center-sampling convention this project already documents and relies on
for `expand_affine_canvas`). "No content is cropped" therefore means the *entire union of pixel
cells* — not merely the lattice of sample-center points — must fit inside the computed output
canvas after the transform. Using only pixel-center corners would under-count by exactly half a
pixel on every side, silently re-introducing a small but real crop at the source rectangle's own
edge pixels — precisely the bug class `expand_affine_canvas` already avoids by using this same
footprint for its affine case.

## 10. Acceptance-domain distinction — existing validation is preserved unchanged (mandatory)

`_require_perspective_matrix_geometry` checks the projective horizon over the **pixel-center**
source rectangle (`_perspective_source_corners`), which is sufficient for today's fixed-canvas
`apply_perspective` contract (output always equals `source_size`, so only the pixel-center-to-
pixel-center mapping needs to be finite/well-behaved). **This design does not broaden that
existing check.** `_require_perspective_matrix_geometry`'s call sites and corner set remain
byte-for-byte unchanged — `sample_perspective` and `apply_perspective`'s own validation are
untouched by this feature.

Instead, `expand_perspective_canvas` performs an **additional, stricter** horizon check of its
own, applying the identical mathematical technique (§11) to the larger pixel-cell footprint
corners (§9). Concretely (implementation detail, not frozen verbatim here, but the *decision* is
frozen): the shared "check one consistent denominator sign across N given corner points" logic is
factored so both the existing pixel-center check and the new pixel-cell check can call it against
different corner sets, without changing the existing check's own corner set, error conditions, or
call sites.

**This is legal and expected, and is frozen as intentional, not a bug:**

```python
apply_perspective(image, params)      # succeeds
expand_perspective_canvas(params)     # raises ValueError
```

whenever the homography's horizon lies only in the half-pixel fringe strictly outside the
pixel-center rectangle but inside (or crossing) the pixel-cell footprint. This avoids a
backwards-incompatible tightening of `apply_perspective`'s own, already-shipped, already-tested
validation — `apply_perspective` keeps accepting every `PerspectiveParameters` it accepts today,
with byte-for-byte identical behavior for `output_size=None`.

## 11. Horizon proof (mandatory)

For a `3x3` homography `H` with rows `h0, h1, h2` where `h2 = (h20, h21, h22)`, a homogeneous
source point `p = (x, y, 1)` maps to `q = H p = (X, Y, W)` with `W = h20*x + h21*y + h22`, and the
Euclidean destination is `(X/W, Y/W)`, defined if and only if `W != 0`.

**`W` is an affine-linear functional of `(x, y)`** (linear in `x, y` plus a constant `h22`). A
standard fact about affine functionals over a convex region: for any point `p` in the convex hull
of a set of vertices `{v_i}`, `p = sum(lambda_i * v_i)` for some `lambda_i >= 0` with
`sum(lambda_i) = 1`, and because `W` is affine, `W(p) = sum(lambda_i * W(v_i))` — a convex
combination of the vertex values. **If `W` has one strict, consistent sign at every vertex of a
convex polygon, that same sign holds for `W` at every point inside and on the boundary of that
polygon** (a convex combination of same-signed values, with weights summing to 1, cannot be
zero or of the opposite sign). The pixel-cell footprint rectangle is manifestly convex (it is an
axis-aligned rectangle), so checking `W`'s sign at its 4 corners is sufficient to prove `W` never
reaches zero anywhere in the closed rectangle.

This is exactly the mathematical justification already implicitly relied on by
`_require_perspective_matrix_geometry`'s existing corner check (applied to the pixel-center
rectangle, itself also convex) — §10 confirms this design does not alter that existing
application, only adds a second one over a different (still convex) corner set. No new
mathematical machinery beyond what the codebase already implicitly trusts is introduced.

**Scale invariance:** replacing `H` with `c*H` for nonzero scalar `c` replaces `q = (X,Y,W)` with
`(cX, cY, cW)`, and `X/W = (cX)/(cW)` is unchanged for any `c != 0` — the Euclidean mapping is
identical regardless of scale. The *sign* of `W` flips when `c < 0` and is preserved when `c > 0`;
checking "all-positive or all-negative" (exactly what `_require_perspective_matrix_geometry`
already does, and what the new pixel-cell check will do identically) is therefore the necessary
and sufficient scale-invariant formulation — confirmed, not merely asserted, by direct experiment
(§27): `H`, `1e-200 * H`, and `1e200 * H` (all finite) reach the identical accept/reject decision
and the identical Euclidean projection for representative test points.

## 12. Bounds-extrema proof (mandatory)

Given `W` keeps one strict sign over the closed pixel-cell rectangle `R` (§11), the map
`p -> (X(p)/W(p), Y(p)/W(p))` is continuous and well-defined over all of `R` (division by a
never-zero, continuous function is continuous).

**Key fact used (standard projective geometry, not an affine-specific shortcut):** a projective
transformation maps straight lines to straight lines, *as long as the line does not cross the
transform's vanishing line* (`W = 0`). Since `W` never reaches zero anywhere on `R` (§11), **every
edge of `R` — a straight line segment — maps to a straight line segment** in destination space,
not a curved arc. This is the general fact `expand_affine_canvas`'s own proof sidesteps by relying
on affine-linearity trivially preserving straightness; for a genuine (non-affine) homography this
must be established via horizon-freeness instead, which §11 already proved.

Because `H` is invertible on `R` (guaranteed by the numerical-full-rank check already in
`_require_perspective_matrix_geometry`, unchanged per §10) and `W` never vanishes there, the
restriction of the map to `R` is a homeomorphism (continuous bijection with continuous inverse)
onto its image. `R`'s boundary (a simple closed rectangle) therefore maps to a simple closed
quadrilateral (four straight transformed edges joined end-to-end at the four transformed
vertices) — not necessarily convex for an arbitrary hand-constructed matrix, but always simple
(non-self-intersecting), since a homeomorphism cannot introduce a self-crossing. `R`'s interior
maps exactly onto that quadrilateral's interior.

**Now the elementary fact that closes the proof:** for a straight line segment between two
endpoints `P1 = (x1, y1)` and `P2 = (x2, y2)`, parametrize `P(t) = (1-t)*P1 + t*P2` for `t in
[0, 1]`. The coordinate `x(t) = (1-t)*x1 + t*x2` is a *linear* function of `t`, hence monotonic
(or constant) over `[0, 1]` — its extrema over the segment occur **only** at `t=0` and `t=1`, i.e.
at the endpoints, never in the interior. The same holds for `y(t)`. Since every one of the
transformed quadrilateral's 4 edges is such a straight segment (established above), each edge's
own `x`/`y` range is bounded by its two endpoints — and because the filled quadrilateral (simple
polygon, convex or not) is exactly the union of its boundary and interior enclosed by that
boundary, the whole shape's axis-aligned bounding box equals the axis-aligned bounding box of
just its 4 vertices.

**This directly answers the task's own concern ("could an extremum hide in an edge interior
beyond the transformed endpoints?"): no — proven above, not assumed, and the proof holds
regardless of whether the transformed quadrilateral is convex**, unlike a proof that relied on
convexity (which `sample_perspective`'s own construction-time proof establishes only for its own
sampled transforms specifically — this design does not assume convexity for arbitrary
hand-constructed `PerspectiveParameters`, deliberately using the strictly weaker and always-true
straight-edge argument instead).

**This proof holds — no STOP condition from §12 of the task is triggered.**

## 13. Union-canvas semantics (mirrors `expand_affine_canvas`)

Bounds are computed from the **union** of the original source pixel-cell footprint and the
transformed pixel-cell footprint — never the transformed footprint alone — exactly preserving
`expand_affine_canvas`'s own "never smaller than `source_size` in either dimension" contract
(`augmentation.py:1016`) for the perspective sibling:

```
source_left, source_top = -0.5, -0.5
source_right, source_bottom = width - 0.5, height - 0.5
transformed_left = min(transformed[:, 0])
transformed_top = min(transformed[:, 1])
transformed_right = max(transformed[:, 0])
transformed_bottom = max(transformed[:, 1])

left = min(source_left, transformed_left)
top = min(source_top, transformed_top)
right = max(source_right, transformed_right)
bottom = max(source_bottom, transformed_bottom)
```

identical in structure to `expand_affine_canvas`'s own lines 1111-1121, with `transformed[:, 0]`/
`transformed[:, 1]` now being the *Euclidean* (post-divide) coordinates from §14 rather than
`expand_affine_canvas`'s trivial (no-divide-needed) affine transform.

## 14. Homogeneous transformation calculation

Float64 calculation for all four pixel-cell corners:

```python
corners = np.array([
    [-0.5, -0.5, 1.0],
    [width - 0.5, -0.5, 1.0],
    [width - 0.5, height - 0.5, 1.0],
    [-0.5, height - 0.5, 1.0],
], dtype=np.float64)

with np.errstate(over="ignore", invalid="ignore"):
    transformed_h = corners @ matrix.T  # shape (4, 3): (X, Y, W) per corner

w = transformed_h[:, 2]
# horizon check (§10/§11) happens before this division is trusted
with np.errstate(over="ignore", invalid="ignore", divide="ignore"):
    transformed_x = transformed_h[:, 0] / w
    transformed_y = transformed_h[:, 1] / w

if not np.all(np.isfinite(transformed_x)) or not np.all(np.isfinite(transformed_y)):
    raise ValueError(
        "expand_perspective_canvas: transforming the source footprint through params.matrix "
        "does not produce finite coordinates"
    )
```

**Frozen handling:**
- **Overflow** (e.g. an astronomically large but individually finite `matrix` entry): suppressed
  via `np.errstate(over="ignore")` during the matmul and the divide, exactly as
  `expand_affine_canvas` already does for its own (simpler, divide-free) transform — a resulting
  `inf`/`nan` is caught by the finiteness check below, not by letting NumPy warn/raise.
- **NaN/infinity in the result:** caught by the explicit `np.isfinite` check immediately after
  division — raises `ValueError` naming the operation, mirroring `expand_affine_canvas:1105-1109`.
- **Zero or extremely small denominator:** the horizon check (§10, performed *before* this
  division, using the same `w` values' signs) already guarantees `w` keeps one consistent sign
  across all 4 corners and is checked via the scale-normalized, rank-aware technique in §11 — this
  calculation does not re-derive that guarantee, it relies on the prior check having already
  raised `ValueError` for any matrix that would make this division unsafe. `divide="ignore"` is
  used defensively (should be unreachable given the prior check, but avoids an unnecessary NumPy
  runtime warning if floating-point noise makes `w` computed here infinitesimally different from
  the `w` computed by the horizon check's own independent, denominator-normalized calculation).
- **Huge finite projected coordinate:** not rejected by this step (only non-finite values are);
  handled downstream by the OpenCV `dsize` ceiling check (§7/§15), exactly as
  `expand_affine_canvas` already handles a huge-but-finite affine result.

`cv2.perspectiveTransform` is **not** used as the sole mathematical oracle here — the direct
matrix-multiply-and-divide computation above is the frozen implementation, matching the technique
`_require_perspective_matrix_geometry` and `expand_affine_canvas` already use (direct NumPy linear
algebra, not an OpenCV round-trip) for determinism and to avoid a second, unnecessary `float32`
requantization. `cv2.perspectiveTransform` **may** be used only as an empirical cross-check
during implementation (§27 already performs an equivalent empirical cross-check via
`cv2.getPerspectiveTransform` + direct matmul comparison, confirming agreement).

## 15. Integer snapping / output size

Reuses `_snap_near_integer` (§3) unchanged — its ULP-scale-only tolerance discipline is not
affine-specific (it operates on plain `float` spans and a `magnitude` parameter, with no
dependency on how those spans were computed):

```python
magnitude_x = max(1.0, abs(left), abs(right), float(width))
magnitude_y = max(1.0, abs(top), abs(bottom), float(height))

span_x = _snap_near_integer(right - left, magnitude=magnitude_x)
span_y = _snap_near_integer(bottom - top, magnitude=magnitude_y)
# finiteness / positive-span checks mirror expand_affine_canvas:1130-1136

output_width = math.ceil(span_x)
output_height = math.ceil(span_y)
if output_width > _OPENCV_SIZE_MAX or output_height > _OPENCV_SIZE_MAX:
    raise ValueError(...)  # mirrors expand_affine_canvas:1140-1144
```

**No decimal-place rounding is introduced** — identical discipline to `expand_affine_canvas`.
Output dimensions must be positive and fit the OpenCV `dsize` ceiling (§7).

**Floor/current `warpPerspective` maximum-parsing verification (§27):** confirmed directly, no
absurd allocation performed — a `dsize` of `2**31` (one past `_OPENCV_SIZE_MAX`) is rejected by
OpenCV's own Python-argument overload resolution (`cv2.error`, "Can't parse 'dsize'") on **both**
OpenCV 4.9.0 and 5.0.0, before any image buffer is allocated — confirming the intended maximum
parsing contract is identical across both supported major versions, verified via bounded
argument-parsing experiments only (never by allocating a near-`int32`-max image).

## 16. Canvas-origin shift — mandatory derivation

For computed `shift_x = -0.5 - left`, `shift_y = -0.5 - top` (identical formula to
`expand_affine_canvas:1146-1147`, snapped near-integer the same way), define:

```
T = [[1, 0, shift_x],
     [0, 1, shift_y],
     [0, 0, 1]]

H_expanded = T @ H
```

**Proof of equivalence** (project-with-`H_expanded` == project-with-`H`-then-translate):

For homogeneous source point `p = (x, y, 1)`, let `q = H p = (X, Y, W)`. Then:

```
q' = H_expanded p = (T @ H) p = T @ (H p) = T @ q
```

`T`'s bottom row is `(0, 0, 1)`, so `q' = (X + shift_x*W, Y + shift_y*W, W)` — **the third
(homogeneous) component is exactly the original `W`, unchanged**, since `T`'s bottom row leaves
the third input component (`W`) untouched and adds nothing from `X`/`Y` into it. Therefore the
Euclidean destination under `H_expanded` is:

```
((X + shift_x*W)/W, (Y + shift_y*W)/W) = (X/W + shift_x, Y/W + shift_y)
```

— exactly the original Euclidean point `(X/W, Y/W)` translated by `(shift_x, shift_y)`, for
**any** `W != 0`. This is proven algebraically above, not merely tested — and independently
confirmed numerically (§27) for a representative non-affine `H` and an arbitrary test point:
`project(H, p)` then shift equals `project(T @ H, p)` to float64 precision.

**Bottom-row preservation (horizon invariance under the shift):** `(T @ H)`'s bottom row is row 2
of `T` times all of `H`: since `T`'s row 2 is exactly `(0, 0, 1)`, `(T @ H)[2, :] = 0*H[0,:] +
0*H[1,:] + 1*H[2,:] = H[2, :]` — **`H_expanded`'s bottom row is algebraically identical to `H`'s
own bottom row**, proving the canvas-origin shift can never move the projective horizon (the
homogeneous denominator `W` is a function of the bottom row alone, per §11). Confirmed
numerically (§27): `H_expanded[2, :] == H[2, :]` exactly (bit-for-bit, not merely approximately)
for a representative non-affine `H` and non-trivial `shift_x`/`shift_y`.

No second `cv2.getPerspectiveTransform` solve is performed, and no unnecessary `float32`
requantization occurs anywhere in this derivation — `H_expanded` is computed via one `float64`
matrix product from the original `float64` `matrix`.

## 17. `destination_points` semantics — frozen (Option A)

### Option A — preserve `destination_points` unchanged (chosen)

`destination_points` continues to mean exactly what `PerspectiveParameters`'s own docstring
already says today (§3): "the four `(x, y)` destination corners actually used to build `matrix`
via `cv2.getPerspectiveTransform`... recorded *after* the `float32` quantization." After
`expand_perspective_canvas` computes `H_expanded`, `destination_points` is copied **unchanged**
from the input `params` — it continues to describe the *original sampling draw*, not the
post-expansion, post-translation destination geometry.

This mirrors `AffineParameters`'s own established metadata contract exactly: `angle`,
`translation`, `scale`, `shear`, `axis_scale` are all "sampling metadata only... never used to
reconstruct or cross-check the matrix" (§3), and `expand_affine_canvas` already copies all of them
unchanged (`augmentation.py:1170-1174`) while only `matrix` and `output_size` change. No
"fabricated re-quantization history" is introduced — `destination_points` after expansion is
simply silent about the canvas-origin translation, exactly as `AffineParameters.translation`
remains silent about `expand_affine_canvas`'s own shift (§3's own documented caveat: *"the *visible
offset of content relative to the new canvas origin* is not guaranteed to equal
`params.translation` verbatim"* — the perspective sibling inherits an identical caveat for
`destination_points`).

**Required docstring clarification** (frozen wording, to be included verbatim or near-verbatim in
the implementation): *"For parameters returned by `expand_perspective_canvas`,
`destination_points` continues to describe the original `sample_perspective` draw and does not
reflect the canvas-origin translation `expand_perspective_canvas` applies — exactly as
`AffineParameters.translation` remains silent about `expand_affine_canvas`'s own shift."*

### Option B — translate `destination_points` (rejected)

Would make the field track final destination coordinates post-expansion, but would erase its
current, precisely-documented meaning as "exactly what the solver saw" (the actual `float32`-
quantized points passed to `cv2.getPerspectiveTransform`) — replacing a precise historical record
with a derived, recomputed value that no longer corresponds to any real solver call. **Rejected**
— no convincing contract reason favors this over Option A, and it would break the
"metadata-is-not-truth, never reconstructed" invariant this project applies uniformly across
`AffineParameters` and `PerspectiveParameters` alike.

**Decision: Option A.** Not ambiguous, not left open for implementation to decide.

## 18. Metadata-vs-truth contract (frozen)

With §17's Option A adopted, mirroring `AffineParameters` explicitly:

- **Replay truth:** `matrix` + `output_size` together (once `output_size` can differ from
  `source_size`, `matrix` alone no longer determines the destination raster extent — see §2/§7).
- **Sampling/debug metadata (never replayed, never cross-checked):** `destination_points`.

`apply_perspective` must never reconstruct or numerically cross-check `matrix` from
`destination_points` — this is already true today (§3, confirmed by direct reading) and remains
unchanged by this design. This distinction is frozen for the `PerspectiveParameters` docstring.

With `output_size` adopted:


— the identical one-line pattern `apply_affine` already uses (§3, line 979).

## 20. Singleton-channel behavior (frozen)

`(H, W, 1)` restoration must use the **output**-size-derived expected spatial shape
`(output_height, output_width)`, not `image.shape[:2]` (which is only correct today because
output always equals source size) — exactly generalizing `_apply_affine_to_array`'s own existing

output_width))`). Confirmed empirically (§27): OpenCV squeezes a trailing singleton channel
dimension identically for `warpPerspective` as for `warpAffine`/`flip` on both supported OpenCV
versions. **No channel-count contract change** — 2-D and `(H, W, 1)` inputs are both still

## 21. Mask behavior (frozen — no semantic expansion)

No mask-semantic changes of any kind. The existing perspective mask contract (§3,
`_PERSPECTIVE_MASK_DTYPES` in `augmentation.py`) — `uint8`/`uint16` only, deliberately excluding
`int16` due to a real, documented, platform-specific OpenCV `warpPerspective` crash on Windows

feature. `interpolation=cv2.INTER_NEAREST`, `border_mode=cv2.BORDER_CONSTANT`, and
`mask_border_value` remain exactly as they are today. The expanded output canvas applies
**identically** to `image` and `mask` — both are warped to the same `output_size` (confirmed by
direct experiment, §27: a `uint16` mask with `INTER_NEAREST` warped to an expanded `dsize`
preserves dtype and contains only values already present in the input mask plus the border-fill
value, matching the existing no-new-intermediate-values guarantee `apply_affine`/
`apply_perspective` already make for the fixed-canvas case). No `int16` widening, no new mask
type, no new mask parameters.

## 22. Hand-constructed parameters (frozen)

`apply_perspective` today already permits a manually-constructed `PerspectiveParameters` for a
`source_size` with `width == 1` or `height == 1`, as long as the matrix itself passes validation
(§3: "unlike `sample_perspective`, which refuses to construct one" — `sample_perspective` requires
both dimensions `>= 2` for a well-defined 4-distinct-corner correspondence, but `apply_perspective`
has no such restriction for a hand-built `params`).

**`expand_perspective_canvas` preserves this existing hand-constructed domain — it does not
additionally reject `width == 1` or `height == 1`.** The pixel-cell footprint remains a nonzero-
area rectangle even for a single-pixel dimension (e.g. `width == 1` gives an x-range of
`[-0.5, 0.5]`, span `1.0`, still a well-defined rectangle with 4 distinct corners for the
purposes of §11's convexity argument, which only requires a genuine rectangle — it does not
require `width >= 2`). No automatic rejection is introduced merely because `sample_perspective`
itself needs `>= 2 x >= 2` for its own, different reason (a well-defined *4-distinct-source-point*
correspondence for `cv2.getPerspectiveTransform`, not a requirement of the pixel-cell geometry
used here).

## 24. Pure-affine homography oracle (mandatory, empirically executed)

Constructed an `AffineParameters` with a representative `2x3` matrix `A` and an equivalent
`PerspectiveParameters` with `H = [[A[0]], [A[1]], [0, 0, 1]]` (bottom row exactly `[0, 0, 1]`),
identical `source_size`, and directly verified (§27, current-stack run, representative case):

- The perspective corner projection (matmul + divide, §14) matches the direct affine transform
  (matmul only, no divide) to `1e-9` absolute tolerance for all 4 pixel-cell corners.
- `H`'s bottom row is exactly `[0.0, 0.0, 1.0]` (bit-for-bit), confirming the affine case is a
  literal special case of the general perspective computation, not merely an approximation of it.
- The `T @ H` bottom-row-preservation and project-then-shift-equals-project-with-`H_expanded`
  identities (§16) hold for this affine-equivalent `H` exactly as they do for a genuinely
  non-affine `H` (also separately verified for a non-affine case in the same experiment run).

This confirms `expand_perspective_canvas`, when fed an affine-equivalent `PerspectiveParameters`,
computes geometrically identical bounds/shift/output-size to what `expand_affine_canvas` already
computes for the literal `AffineParameters` — the perspective implementation strictly generalizes
the affine one rather than diverging from it for the degenerate affine case. A bounded
implementation-time test suite (§33) should cover identity, translation, rotation, shear, and
anisotropic scale as affine-equivalent perspective cases, plus one near-right-angle case
exercising `_snap_near_integer`'s tolerance discipline (mirroring `expand_affine_canvas`'s own
existing test rationale, §3, for the 90-degree-snapping edge case) — this design freezes the
*oracle technique* and confirms it produces agreement in a representative case; the full case
matrix is implementation-time work, not re-derived here.

## 25. Horizon test taxonomy (frozen, bounded)

- **A. Horizon crosses the existing pixel-center rectangle:** already rejected today by
  `_require_perspective_parameters`/`_require_perspective_matrix_geometry`, completely unaffected
  by this feature (§10) — `expand_perspective_canvas` never even reaches its own footprint check
  for such a `params`, since `_require_perspective_parameters` (called by `apply_perspective` at
  construction/replay time, and reused by `expand_perspective_canvas` for its own baseline
  validation) already raises first.
- **B. Horizon does not cross the pixel-center rectangle but does cross the half-pixel pixel-cell
  fringe:** `apply_perspective` remains legal (unaffected); `expand_perspective_canvas` raises
  `ValueError` from its own additional footprint check (§10, §11) — this is the case this design
  exists to correctly distinguish, frozen as intentional in §10.
- **C. Horizon lies near but strictly outside the full pixel-cell footprint:** expansion is legal
  if all projected bounds remain finite (§14) and the resulting `output_size` is representable
  within the OpenCV `dsize` ceiling (§15) — confirmed reachable and stable via the "near-horizon-
  but-valid" experiment (§27): a homography with a small-but-consistently-signed denominator over
  the full footprint warps successfully with a deterministic output shape on both OpenCV
  versions.
- **D. Horizon-free, but the resulting span exceeds the OpenCV `dsize` ceiling:** `ValueError`,
  mirroring `expand_affine_canvas`'s own existing `_OPENCV_SIZE_MAX` check (§15) exactly.

**Error message ownership** (sufficient for implementation-time tests, not over-pinning native
wording): case A's message is owned by the existing, unchanged
`_require_perspective_matrix_geometry`/`_require_perspective_parameters` (already stable,
already tested); cases B/D's messages are owned by `expand_perspective_canvas`'s own new
validation, and should name the operation (`"expand_perspective_canvas: ..."`) exactly as
`expand_affine_canvas`'s own messages already do, distinguishing the two failure kinds by
message content (footprint horizon vs. `dsize` ceiling) without pinning exact floating-point
values in either.

## 26. Near-horizon numerical policy (frozen — no arbitrary epsilon)

No epsilon exclusion zone is introduced. `_require_perspective_matrix_geometry`'s existing policy
— strict, scale-normalized sign/no-zero semantics, no epsilon margin — is reused verbatim for the
new pixel-cell check (§10, §11). Confirmed directly via experiment (§27): a "near-horizon-but-
valid" homography (small-but-consistently-signed denominator across the footprint) both passes
the strict sign check and warps successfully with a deterministic, correctly-shaped result on
both OpenCV versions — the strict, epsilon-free policy does not spuriously reject a genuinely
valid transform close to (but not crossing) the horizon. Introducing an arbitrary margin would
have no principled scale to set it at (per §11's scale-invariance proof, "close to the horizon"
is not itself a scale-invariant notion in raw coordinate units) and was not needed to make any
experiment pass — **finite-coordinate and output-size guards (§14, §15) are preferred over, and
found sufficient in place of, any arbitrary numerical margin.**

   is not triggered) — it is exactly the kind of floor-vs-current numerical variation this
   project's standing practice expects to find and correctly tolerates via a robust check
   (SVD-rank) rather than a fragile one (raw determinant).
8. Modest near-horizon-but-valid homography: consistent denominator sign confirmed over the
   pixel-cell footprint; `warpPerspective` succeeds with deterministic, correctly-shaped output —
   on both.
9. Affine-equivalent oracle (§24): corner-projection agreement, exact bottom-row preservation,
   and `T @ H` equivalence all confirmed — on both.
10. Scale invariance (§11, §28): `H`, `1e-200 * H`, `1e200 * H` all reach the identical
    accept/reject decision and the identical Euclidean projection — on both.

**No material supported-version contradiction was found; no STOP condition from §35 is
triggered by these experiments.**

## 28. Matrix scale invariance (confirmed — see §11, §27 item 10)

Verified directly, not merely asserted: `H`, `1e-200 * H`, and `1e200 * H` (all finite) produce
the identical accept/reject decision (§11's sign-consistency check) and the identical Euclidean
projection for a representative test point, to `rtol=1e-6` (the loosened tolerance reflecting the
`1e200`/`1e-200` scale extremes' own floating-point precision limits, not a weakening of the
underlying exact algebraic identity proven in §11/§16). Byte-identical raw matrix values across
different scales are correctly **not** required — only the geometric bounds and normalized replay
behavior need agree, exactly as the design's own framing anticipates.

## 29. Read-only / ownership invariants (frozen — mirrors `expand_affine_canvas` exactly)

- `H_expanded` (the new `matrix`): `float64`, shape `(3, 3)`, an independent buffer (never a view
  into the input `params.matrix`), `order="C"` (matching this project's existing convention for
  `expand_affine_canvas`'s own `expanded_matrix`, §3), and marked read-only via
  `.setflags(write=False)` before being placed on the returned `PerspectiveParameters`.
- The original `params.matrix` is never mutated — `H_expanded = T @ H` is a new array from
  `@` (matrix multiplication never mutates its operands).
- `output_size`: a plain `(int, int)` tuple, matching `AffineParameters.output_size`'s own type
  exactly.
- `destination_points`: copied unchanged from the input `params` (§17/§18) — same tuple-of-tuples
  of Python `float`, no new quantization or recomputation.

## 30. No new public type (confirmed)

Hard target met: **1 new public function, 0 new public types.** The additive `output_size`
field on the existing public type `PerspectiveParameters` is exactly the case §30 of the product
audit's own instructions explicitly allows ("The additive `output_size` field on
`PerspectiveParameters` is allowed if the design accepts it"). No second result dataclass, canvas
object, enum, or policy object is introduced anywhere in this design — confirmed by the complete
analysis above, not merely asserted.

## 31. Public-contract budget restatement (honest accounting)

- **+1** new top-level public symbol: `expand_perspective_canvas`.
- **+0** new public types.
- **+1** optional, keyword-only, backwards-compatible field on the existing public type
  `PerspectiveParameters`: `output_size`.
- **+0** changed existing function call signatures (`apply_perspective`'s parameter list is
  unchanged; only its internal behavior gains a new, `output_size`-driven case).

  and everything `sample_perspective` will ever continue to produce (§7, §19).

This is the real final budget — not "zero existing API changes."

## 32. Explicit non-goals

- No RNG use of any kind (deterministic, exactly like `expand_affine_canvas`).
- No resampling of `PerspectiveParameters` (no re-draw, no retry).
- No new `PerspectiveParameters`-adjacent public type.
- No resize, no crop, no photometric augmentation.
- No bounding-box/keypoint/polygon transform.
- No `Compose`-pipeline integration.
- No batch/vectorized canvas expansion.
- No automatic repeated/idempotent expansion (§8).
- No defined behavior for a horizon-crossing full pixel-cell footprint beyond a clear `ValueError`
  rejection (§10, §25 case A/B).
- No interpolation-mode changes (§21 — `apply_perspective`'s existing `interpolation`/
  `border_mode`/`border_value`/`mask_border_value` parameters and defaults are entirely
  unaffected).
- No mask dtype widening (§21 — `_PERSPECTIVE_MASK_DTYPES` unchanged).
- No `destination_points` reconstruction from `matrix`, in either direction (§17, §18).
- No new OpenCV dependency or version-range change — the existing `opencv-*>=4.9,<6` extras
  ranges are untouched; every low-level primitive this design needs
  (`cv2.warpPerspective` with an independent `dsize`, `np.linalg.matrix_rank`) is already used
  elsewhere in this exact module today.

## 35. Alternatives considered

- **Do nothing (leave the affine/perspective asymmetry as-is):** rejected by the product audit's
  own SELECT_FEATURE outcome (this document does not re-litigate that decision, only its data-
  model consequence).
- **Restrict `expand_perspective_canvas` to only `sample_perspective`-produced `params` (reject
  all hand-constructed input):** rejected — `apply_perspective` itself already accepts
  hand-constructed `params` today (§22), and no evidence was found that canvas expansion needs a
  narrower domain than replay itself already has, beyond the horizon check that already exists
  for exactly this reason.
- **Silently clamp a horizon-crossing or oversized result instead of raising:** rejected —
  contradicts this project's uniform "raise `ValueError`, never silently return a degenerate
  result" policy, already established by `sample_perspective`/`apply_perspective`'s own existing
  behavior (§3: *"`cv2.warpPerspective` does not raise for a singular or horizon-crossing
  matrix... this must be checked here rather than left to OpenCV"*) and by `expand_affine_canvas`'s
  own existing `ValueError`-on-overflow behavior.
- **Add an epsilon-margin horizon tolerance:** rejected, see §26 — no principled scale exists for
  such a margin, and no experiment required one.

## 37. STOP conditions (for the future implementation PR)

An implementation PR must STOP and report, rather than silently routing around the issue, if any
of the following occurs:

1. The base SHA this design was written against no longer matches `main` in a materially
   conflicting way (e.g. `PerspectiveParameters`/`AffineParameters`/`apply_perspective` have
   changed shape since this document was written).
2. `PerspectiveParameters` cannot gain `output_size` without a real backwards-compatibility break
   not identified in §6 (none is currently known).
3. The transformed-corner-extrema argument (§12) is found not to hold for some legal
   `PerspectiveParameters` this design did not anticipate (none is currently known — the proof in
   §12 does not depend on convexity, only on horizon-freeness, which is independently guaranteed
   by §10/§11).
4. The full-footprint horizon test is found to require an arbitrary, unstable epsilon policy after
   all (none was needed in this design's own experiments, §26/§27).
5. OpenCV 4.9 and 5.x are found to materially disagree on required supported behavior beyond the
   already-documented, already-tolerated numerical-fingerprint difference in §27 item 7.
6. Expanded replay is found to need a new public type after all (none is currently known — §30).
7. `apply_perspective`'s current `output_size is None` behavior cannot remain unchanged for some
   reason not identified here.
8. `destination_points` semantics cannot be made truthful under §17's Option A after all.
9. The implementation contract is found to require growing into a general projective-geometry
   framework (multiple homography composition, arbitrary polygon clipping, etc.) beyond the single
   grow-only canvas operation frozen here.

No such condition is currently known to apply — this design is accepted for implementation as
written.
